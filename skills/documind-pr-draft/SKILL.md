# DocuMind PR 초안 생성 스킬

## 목적

PR을 만들기 전에 사용자가 승인할 수 있도록 변경 범위와 검증 결과를 리뷰어용 형식으로 압축한다.

## 입력 확인

1. 관련 GitHub issue 번호와 제목
2. 현재 브랜치
3. 변경 파일 목록
4. 핵심 변경 내용
5. 실행한 테스트와 결과
6. 완료 범위가 issue 전체인지 일부인지
7. 리뷰어가 집중해서 봐야 할 위험 지점

## 절차

1. `git status --short`로 변경 파일을 확인한다.
2. `git diff --stat` 또는 실제 diff를 보고 PR 범위가 현재 issue에 맞는지 확인한다.
3. `docs/`, `memory-bank/`, 루트 `AGENTS.md`는 로컬 운영 자료이므로 기본 PR 포함 대상에서 제외한다.
4. 검증 결과가 없으면 "미실행"으로 표시하고 이유를 적는다. 결과를 꾸며 쓰지 않는다.
5. issue가 완전히 끝나면 `Closes #번호`, 일부 범위면 `Related #번호`를 사용한다.
6. push 또는 PR 생성 전 사용자에게 초안을 먼저 보여준다.

## 출력 형식

```markdown
## PR 제목
[영역] 한 줄 요약

## PR 본문 초안
### 관련 이슈
Closes #번호

### 작업 내용
- 변경 축 1
- 변경 축 2

### 리뷰 포인트
- 리뷰어가 집중해서 볼 위험 또는 설계 판단

### 변경 파일
- `path/to/file`: 역할

### 확인한 내용
- 확인 항목, 결과, 해석을 함께 쓴다.
- 명령만 줄줄이 나열하지 않는다.

### 후속 범위
- 이번 PR에서 의도적으로 남긴 작업을 리뷰어 관점으로 적는다.
```

## 작성 원칙

- DocuMind PR 제목과 본문은 기본적으로 한국어로 작성한다. 영어 변수명, API명, 파일명은 그대로 쓰되 처음 등장할 때 사용자가 헷갈릴 수 있으면 `영어(한국어 뜻)` 형식으로 풀어 쓴다.
- PR 본문은 작업 보고서가 아니다. 긴 학습 설명, 상세 로그, 면접 포인트는 `docs/` 보고서나 사용자 설명으로 분리한다.
- 변경 내용은 "무엇을 바꿨는가 + 어떤 동작을 유도하는가"로 쓴다.
- 리뷰 포인트는 큰 PR일수록 반드시 쓴다.
- `확인한 내용`은 명령 목록이 아니라 "확인 항목 / 결과 / 해석" 중심으로 작성한다. 명령은 필요한 경우 짧게만 적는다.
- 변경하지 않은 항목을 길게 나열하지 않는다. PR diff(변경 내역)에 없는 파일과 경로는 리뷰어가 확인할 수 있으므로, 회귀 위험이나 범위 오해를 막는 데 꼭 필요한 경우에만 짧게 언급한다.
- `비고`처럼 사용자에게 말하는 듯한 모호한 섹션명은 피하고, `후속 범위`, `미실행 검증`, `리뷰 포인트`처럼 리뷰어가 판단할 수 있는 제목을 쓴다.
- 사용자 승인 전에는 push, PR 생성, ready 전환, merge를 진행하지 않는다.
