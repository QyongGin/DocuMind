## 1. 목표와 범위 ✅

### 1.1 한 문장 목표

**인하공업전문대학 전용 챗봇을 만들어 학교에 정식 서비스로 제안하고, 채택되면 학교 서버에 직접 배포·운영한 뒤 학교 담당자에게 인계한다.**

### 1.2 확정된 범위

| 항목 | 결정 |
|---|---|
| 사용자 | 재학생, 예비 입학생·학부모, 교직원 (모두). **인하공업전문대학에 궁금한 모든 사람**을 위한 챗봇이다 — 채용 지원자, 협력 업체(입찰), 외국인 방문자 등도 포함 (2026-10-02 사용자 확인). 문서를 고를 때 "학생이 물을 일이 없다"를 기준으로 빼지 않는다 |
| 주제 | 입시, 학사, 장학·등록금, 학과·캠퍼스 생활 (모두) |
| 문서 범위 | 공개 문서 + 내부 문서 (내부 문서는 학교 협조가 필요) |
| 완성 수준 | 학교 정식 서비스. 제안 후 채택되면 **학교 서버에 직접 배포하고 운영**한다 |
| 유지보수 | 운영이 안정되면 **학교 담당자에게 인계**한다 (2026-09-30 확정). 인계받을 수 있는 형태로 만드는 것이 목표에 포함된다 |
| 학교와의 소통 | 아직 없음. 먼저 만들어서 제안한다 |
| 시범 운영 | 제안 전 시범 운영은 **하지 않는다** (2026-09-30 확정). 제안 근거는 평가 수치와 시연이다 |
| 일정 | 마감 없음. 완성도를 우선한다 |

### 1.3 이미 정해진 제약 (기존 프로젝트 규칙)

- **온프레미스**: 데이터가 기관 밖으로 나가지 않는다. 개인정보보호법(PIPA) 대응이 이 프로젝트의 핵심 강점이다.
- **개발·검증 환경**: 데스크탑 로컬 GPU(RTX 4070 Super, 12GB) 1대. 데스크탑은 전기 요금 때문에 **작업할 때만 켠다** (2026-09-30). 클라우드는 쓰지 않되, **모델 학습만 AWS EC2 g5.xlarge(A10G 24GB)에서 한다** (2026-10-01 예외, AWS에 올릴 데이터 범위는 §4.6).
- **1인 개발**
- **ML·파인튜닝은 수단이다**: 필수가 아니며, 파이프라인 단계마다 맞는 방법을 고른다 (2026-09-30 사용자 결정).
- **모델 라이선스**: 챗봇에 쓰는 모델(생성·임베딩·재순위)은 학교 공식 서비스에 쓸 수 있는 라이선스여야 한다. EXAONE은 이 조건 때문에 후보에서 제외했다 (2026-10-01, E5).

### 1.4 이 목표에서 바로 따라 나오는 것 📝

아래는 1단계 답변에서 논리적으로 따라 나오는 사항이다. 3·4단계에서 확정한다.

1. **두 구간 구조**: 학교와 아직 소통이 없고, 내부 문서와 학교 서버는 학교 협조가 있어야 쓸 수 있다. 따라서 진행은 두 구간으로 나뉜다.
   - **학교 협조 전**: 공개 문서만으로 "제안할 만한" 완성도를 증명하는 구간
   - **학교 협조 후**: 내부 문서 추가, 학교 서버 배포, 실제 운영
2. **개발 환경과 운영 환경의 분리**: 개발·검증은 데스크탑에서 하고, 실제 운영은 학교 서버(역시 온프레미스)에서 한다. 학교 서버 사양은 아직 모른다.
3. **사용자별 접근 권한**: 예비 입학생·학부모는 학교 계정이 없다. 반면 내부 문서는 교직원이나 재학생에게만 보여야 한다. 따라서 공개 영역과 로그인 영역의 구분, 문서별 권한 관리가 필요하다.
4. **학교 전체 규모의 운영 요건**: 동시 접속 처리, 백업, 모니터링, 개인정보 처리 정책, 문서 최신화(매년 바뀌는 모집요강, 기한이 있는 공지)가 필요하다.

### 1.5 성공 기준 ❓

- 실제 인하공전 문서로 측정할 수 있게 된 뒤(2~3단계) 수치로 정한다.
- 후보 지표: 주제별 정답률, 문서 커버리지, 응답 시간, 동시 사용자 수, 환각(잘못된 답변) 비율, 거절 정확도

### 2.1 지금 챗봇이 할 수 있는 것 (기능)

**사용자 화면** (`/`, 로그인 없이 사용 가능)

- 질문하면 답변이 글자 단위로 흘러나온다(SSE 스트리밍). 중간에 멈출 수 있다.
- 출처로 문서명, 페이지, 미리보기를 보여준다.
- 답변에 좋아요·싫어요를 남길 수 있다.
- 로그인하면 대화 이력을 보고 지울 수 있다.

**관리자 화면** (`/admin`)

- 대시보드: 문서·청크·카테고리 수, 피드백 비율
- 문서 관리: 업로드(진행률 표시), 카테고리 추가, 청크 보기, 삭제
- 시스템 프롬프트 편집

**학교 서비스 관점에서 없는 것**

| 없는 것 | 설명 |
|---|---|
| 계정 | 회원가입, 학생 로그인(탭 UI만 있고 동작 안 함), 관리자 추가, 비밀번호 변경 화면이 없다. 일반 사용자(USER) 역할은 코드에 정의만 있고 부여되지 않는다 |
| 권한 | 사용자·역할별 문서 접근 제한이 없다. 모든 질문이 전체 문서를 검색한다 |
| 검색 범위 지정 | 카테고리나 문서를 골라 질문할 수 없다. 카테고리는 AI 서버에 전달조차 되지 않는다 |
| 이어지는 대화 | 이전 대화를 AI에 넘기지 않는다. 질문마다 처음부터 답한다 |
| 문서 운영 | 문서 교체·재업로드, 실패 재처리, 중복 검출, 연도·버전 관리가 없다 |
| 관리·분석 | 채팅 로그 조회 화면이 없고, 통계는 피드백 합계뿐이다 |

### 2.2 시스템 구조와 코드 상태

**구성**: frontend(React) → backend(Spring Boot + MySQL) → ai-server(FastAPI) → Ollama(EXAONE 3.5 7.8B, qwen3-embedding 4B) / ChromaDB. 외부에 공개되는 포트는 frontend 하나다.

**AI 서버 처리 흐름**

1. 파싱: PDF는 OpenDataLoader, DOCX·XLSX는 MarkItDown, PPTX는 python-pptx(미커밋)
2. 청킹: 마크다운 헤더 기준 2단 분할
3. 표 → TableFact(행·열·값) 분해
4. 저장: 임베딩해서 ChromaDB(컬렉션 3개)에 넣고, BM25(Kiwi 형태소) 인덱스도 만든다
5. 질의 분석 → 하이브리드 검색 → 우선 근거 선택
6. 조건이 맞으면 LLM 없이 바로 답하고, 아니면 EXAONE이 생성한다

**규모와 품질**

| 부분 | 규모 | 상태 |
|---|---|---|
| ai-server | 12,107줄 (그중 `main.py` 7,057줄) | 7월 감사 판정: "비대하지만 엉키지 않음". 계약 모듈(`rag_contracts.py` 등)은 잘 분리돼 있다. pytest 16건 |
| backend | 엔티티 7개, API 23개 | 테스트 81개. 단, H2 DB로 돌려서 실제 DB 마이그레이션은 검증되지 않는다 |
| frontend | 화면 4개 | 테스트 없음 |
| CI | 없음 | PR을 자동으로 검사하지 않는다 |

**확장을 막는 구조**

- 진행률, BM25 인덱스, 형태소 분석기가 서버 프로세스 메모리 안에 있다(전역 상태). 그래서 서버 프로세스를 1개로만 돌릴 수 있다. 여러 개로 늘리면 삭제한 문서가 다른 프로세스에서 계속 검색되는 문제가 생긴다.
- 표 사실 조회가 질문마다 전체 표 사실을 가져온다. 문서가 많아지면 느려진다.

### 3.7 문제 사이의 관계

1. **A가 출발점이다.** 실제 문서(A1)와 믿을 만한 평가셋(A2)이 없으면, B를 개선해도 효과를 측정할 수 없고 학교에 보여줄 수치(E)도 만들 수 없다.
2. **A1을 풀면 B2와 A4가 바로 커진다.** 문서를 늘리는 순간 문서 간 섞임과 연도 충돌이 나타나므로, 세 문제는 함께 다뤄야 한다.
3. **C2는 내부 문서의 전제 조건이다.** 내부 문서는 학교 협조 후에 들어오지만, 권한 구조는 그 전에 설계해 둬야 한다.
4. **D2보다 F2가 먼저다.** 서버 프로세스를 여러 개로 늘리려면 전역 상태부터 걷어내야 한다.
5. **E1(제안)은 B1과 E4가 받쳐줘야 한다.** 품질 수치와 실사용 근거가 있어야 제안이 설득력을 갖는다.
6. **D1은 다른 문제와 상관없이 가장 먼저 확인한다.** 확인은 읽기만 하면 되고, 문제가 사실이면 지금 있는 색인이 위험하다.
7. **시범 운영을 하지 않으므로 A2의 비중이 커진다.** 제안 근거가 평가 수치와 시연뿐이라, 실제 문서로 만든 믿을 만한 평가셋이 사실상 유일한 증거다.
8. **인계 계획 때문에 C3·D4·F2가 "인계 가능성" 문제가 된다.** 관리 기능, 운영 자동화, 단순한 코드 구조는 학교 담당자가 넘겨받을 수 있느냐와 직결된다.
9. **사용자가 겪은 불편 세 가지(B3·B5·B6)는 모두 B1의 세부 증상이다.** 정답률 숫자 하나로는 보이지 않으므로, 평가셋에서 따로 측정해야 한다 (환각, 과잉 거절, 출처 정확도).

### 3.8 ML·파인튜닝이 들어갈 자리

- B1·B2·B3·B5의 해결 수단 후보다. 구조 개선(청킹, 검색 범위 지정)으로 풀지, ML(임베딩 파인튜닝, 리랭커, 라우터 분류기, 생성 모델 행동 교정)로 풀지는 4단계에서 문제별로 고른다.
- 어느 쪽이든 A2(실제 문서 기반 평가셋)가 먼저 있어야 효과를 증명할 수 있다.

## 4. 실행 계획 ✅

> **방법**: §3의 문제를 서로의 관계(§3.7)에 따라 묶어서 마일스톤(M0~M6)으로 만들었다. 마일스톤마다 확인할 수 있는 완료 기준을 둔다.

### 4.0 계획 원칙

1. **순서**: 출발선 정리 → 측정 기준 → 품질 → 서비스 기능 → 운영 준비 → 제안 → (협조 후) 실제 운영. 앞 단계가 뒤 단계의 전제 조건이다.
2. **한 번에 하나 바꾸고 측정한다**: temperature=0 결정론 측정을 유지한다. 모든 품질 변경은 실제 문서 평가셋으로 전후를 비교한다.
3. **휴리스틱 금지**: 특정 학과명이나 금액을 조건문으로 처리하지 않고 구조로 푼다 (기존 원칙 유지).
4. **ML·파인튜닝은 수단이다**: 계획은 설계 6단계(§4.6)에서 세우고, 평가셋이 생긴 뒤(M1 이후) 문제마다 구조 개선과 ML 중 효과가 증명된 쪽을 고른다. 기반 모델은 ① 라이선스로 거르고 ② 학습 전에 평가셋으로 비교해 고르고 ③ 그다음 학습한다.
5. **인계를 처음부터 준비한다**: 운영 문서를 마일스톤마다 함께 갱신하고, 마지막에 몰아서 쓰지 않는다.
6. **학교 협조 없이 할 수 있는 것을 먼저 끝낸다**: M0~M5는 협조 없이 진행할 수 있다. M6만 협조가 필요하다.
