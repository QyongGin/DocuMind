# M2 1단계 — AI 서버 기본 검색 방식을 순위 융합으로, 기본 생성 모델을 Gemma 4 12B로 (#169, 2026-10-15)

> ADR-0032(검색 순서는 사람이 만든 규칙 대신 순위 융합으로, 2026-10-15 확정)를 운영 기본값에 반영하고, 데스크탑에서 옵션 없이 보낸 요청이 순위 융합 경로로 E3와 같은 결과를 내는지 확인했다.
> 관련: 이슈 #169, ADR-0031(M2 검색 실험에서 답을 만드는 모델 = Gemma 4 12B), ADR-0032, `검색개선-설계-20261014.md` §3 1단계

## 1. 결론

- 운영 요청(백엔드가 쓰는 `/query/stream` 포함)이 설정값 `AI_RETRIEVAL_MODE`(기본 `rrf`)를 따라 순위 융합으로 답한다. 설정값 하나로 규칙 경로(`rules`)로 되돌릴 수 있다. [코드·실측]
- 데스크탑에서 옵션 없이 돌린 개발셋 결과는 E3(같은 모델·순위 융합, 생성만 다시 돌림)와 모든 지표가 같은 수준이고, 같은 Gemma 4 12B의 규칙 경로보다 정답률(53.7% → 76.9%)·오답률(6.0% → 0.7%)·과잉 거절(34.7% → 18.2%)이 의미 있게 낫다. [실측]
- 데스크탑 12GB에서는 Gemma 4 12B(문맥 8,192)와 임베딩 모델이 함께 GPU에 올라가지만 메모리가 97% 차고, 응답 시간 꼬리가 길다(상위 5% 11.2초, 최대 43.4초). M2 2단계(상위 k·문맥)와 3단계(재순위 모델 추가)에서 이 여유를 먼저 본다. [실측]

## 2. 바꾼 것 [코드]

| 곳 | 바꾼 것 | 이유 |
|---|---|---|
| `ai-server/main.py` | `AI_RETRIEVAL_MODE`(`rrf`·`rules`, 기본 `rrf`)를 읽는 `_env_choice`. `QueryRequest.retrieval_mode`·`_prepare_query` 기본값이 이 설정을 따르고, `/query/stream`도 요청의 검색 방식을 넘긴다 | 백엔드는 검색 방식을 보내지 않으므로 서버 기본값이 운영 경로를 정한다. 스트리밍 경로가 빠지면 운영 요청만 규칙으로 남는다 |
| `ai-server/main.py` | 기본 생성 모델 `gemma4:12b-it-qat` | ADR-0031: M2 검색 실험에서 답을 만드는 모델. EXAONE 3.5는 연구용 라이선스 |
| `docker-compose.yml`·`docker-compose.gpu.yml`·`.env.example` | 같은 기본값과 `AI_RETRIEVAL_MODE=rrf` | 설정 한 곳에서 되돌리기 |
| `tools/corpus` 평가 실행기 | 검색 방식을 요청마다 적어 보낸다(기본 `rrf`). 이 칸이 없는 옛 실행 기록은 `rules`로 본다 | 이전에는 `rules`일 때 요청에 넣지 않았다 — 서버 기본값이 바뀌면 '규칙'으로 기록된 실행이 실제로는 순위 융합으로 돌 수 있었다 |

- 규칙 세 개와 우선 경로 답 코드는 한 릴리스 동안 `rules`로 남긴다. M2 2단계 뒤 지운다(#169 남은 작업).
- `/debug/rag-trace`는 아직 규칙 경로를 따로 재현한다. 운영 경로와 다른 후보 순서를 보여 줄 수 있어, 규칙 코드를 지울 때 함께 순위 융합으로 바꾼다.

## 3. 확인

### 테스트 [실측]

- ai-server 98 passed(1 skipped), tools/corpus 192 passed(가나대학 합성 데이터).
- 변이 확인 5/5: 기본값을 `rules`로, 스트리밍이 검색 방식을 안 넘김, 설정값 정리(공백·대소문자) 안 함, 실행기가 검색 방식을 안 보냄, 옛 실행 기록을 `rrf`로 봄 — 하나씩 망가뜨리자 모두 테스트가 실패했고 바꾼 파일만 되돌렸다.

### 운영 지표 [실측]

| 항목 | 이번(Gemma 4 12B·순위 융합, 실시간) | E1(EXAONE 3.5·순위 융합) |
|---|---|---|
| 응답 시간 중앙 / 상위 5% / 최대(첫 문항 제외) | 4.33초 / 11.24초 / 43.4초 | 2.44초 / 4.21초 / 6.3초 |
| 프롬프트 토큰 중앙 / 최대 | 2,999 / 6,207 | 2,752 / 5,766 |
| 출력 토큰 중앙 / 최대 | 44 / 353 | — |
| GPU(`ollama ps`, `nvidia-smi`) | Gemma 8.0GB + 임베딩 4.1GB 모두 100% GPU, 11,959 / 12,282MiB | — |

- 느린 문항은 출력이 짧은데도 생성 시간이 길었다(예: 출력 45토큰에 43.4초). 질문 준비(임베딩·검색)는 첫 요청의 모델 올리기 말고는 빨랐다. GPU 메모리가 거의 차서 생성이 간헐적으로 느려진 것으로 본다. [판단]
- 생성 문맥 8,192에서 가장 긴 프롬프트 6,207 + 출력 상한 512 = 6,719라 여유가 있다. 문맥을 7,168로 줄이면 메모리가 줄어들지만, 근거 수(상위 k)를 정하는 M2 2단계에서 문맥과 함께 정한다.

## 4. 남은 것

- M2 2단계(상위 k와 문맥): 이번 실행을 출발점으로, 응답 시간 꼬리와 GPU 메모리를 함께 본다.
- M2 2단계 뒤: 규칙 세 개·우선 경로 답 코드, 관련 점검 스크립트·테스트를 지우고 `/debug/rag-trace`를 순위 융합 경로로 바꾼다(#169).
- 모델 선정 계획(`모델선정-비교계획-20261015.md`) ①: 근거 인용 후 답 프롬프트 문구 확정 뒤 두 모델 실행.
- 데스크탑 `.env`는 이번에 바꾼 값(Gemma 4 12B, `rrf`) 그대로 둔다. 되돌리려면 `.env.bak-20261015-before-169`.
