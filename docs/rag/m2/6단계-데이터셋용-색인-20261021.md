# M2 6단계 ① — 데이터셋용 색인 (2026-10-21)

> 계획: `A.X-기준-계획-20261017.md` §4 6단계(총괄계획 M1 9번, 이슈 #128). 결정: ADR-0038(학습 몫 묶음마다 한 판), ADR-0010(데이터셋용 색인 분리).
> 절차: `docs/development/local-gpu/데이터셋-색인-절차.md`. 실행 기록(로컬): 대장 `uploads` 표의 대상 `dataset`, `Assets/corpus/index_ids/`(색인별 대장 ID 목록).

## 1. 결론

1. 학습 몫 묶음마다 한 판(문서 2,186개, 묶음 1,475개)을 서비스와 같은 코드로 별도 compose 프로젝트(`documind_dataset`)에 색인했다. 2,186개 모두 성공, 실패 0, 처리 약 3시간(177분). [실측]
2. **두 색인이 나뉘었다.** 데이터셋 색인에 든 문서 2,150개는 모두 학습 몫(유효한 판 472 · 보관 판 1,678)이고 평가 몫은 0이다. 서비스 색인 698개에는 보관 판이 0이다(#128 완료 기준). [실측]
3. **같은 코드로 같은 결과가 나왔다.** 두 색인에 함께 있는 유효한 판 472개의 문서별 원문 청크 수·표 사실 수가 472 / 472 같다. [실측]
4. 색인 항목 120,479개(원문 청크 11,798 · 표 사실 108,681), Chroma 볼륨 3.9GB. 표 사실의 77%(83,323)가 보관 판 PDF에서 나왔다. [실측]
5. 글이 없어 색인 항목이 없는 문서가 36개다(그림만 있는 PDF 포스터·카드뉴스 33, 빈 HTML 1, HWPX 2). 학습 예시를 만들 수 없을 뿐 다른 문서에 영향은 없다. 처리 결과가 빈 문서를 '완료'로 표시하는 일은 알려진 문제다(총괄계획 M4). [실측]

## 2. 바꾼 것 [코드]

| 자리 | 전 | 후 |
|---|---|---|
| 업로드 도구 데이터셋 대상(`corpus upload --set dataset`) | 학습 몫·개인정보 통과 행 전부 — 내용 중복·빈 파일로 '제외'된 207개까지 | '색인'·'보관' 행 중 묶음마다 한 판(`one_version_per_group`): 유효한 판이 있으면 그 판, 없으면 게시일이 가장 늦은 보관 판(같은 날 글과 첨부는 함께) |
| 데이터셋 스택 | 없음 | `docker-compose.dataset.yml`: 화면 끔, 백엔드·AI 서버·Ollama 포트를 데스크탑 안쪽 주소(18180·18100·11535)에만, DB·색인 볼륨은 따로, 모델 볼륨은 서비스 스택 것을 함께 씀 |
| 나뉨 확인 | 업로드 기록(`uploads` 표)으로만 볼 수 있음 | `deploy/index_ledger_ids.py`: 색인에 실제로 든 문서의 대장 ID 목록 |

- 업로드 기록과 색인은 다를 수 있다: 서비스 업로드 기록은 701개인데 색인은 698개다(2026-10-03 같은 글 사본 3개를 지움). 그래서 나뉨은 색인 자체로 확인한다.
- 테스트(가나대학 합성 대장): 묶음마다 한 판 고르기(유효 판 우선, 게시일 없는 유효 판도 앞섬, 같은 날 글·첨부 함께, 제외·평가 몫 빼기). 커밋 뒤 규칙 다섯 가지를 망가뜨려 모두 테스트가 잡는 것을 확인했다(처음에 하나 — 유효 판 우선 — 를 못 잡아 테스트를 보강).

## 3. 결과 [실측]

| 형식 | 올림 | 색인에 든 문서 | 처리 시간 합 | 문서당 중앙 · 최대 | 원문 청크 | 표 사실 |
|---|---|---|---|---|---|---|
| HTML | 1,444 | 1,443 | 58.7분 | 2초 · 347초 | 3,163 | 3,877 |
| PDF | 409 | 376 | 99.5분 | 5초 · 411초 | 5,994 | 98,604 |
| HWP | 312 | 312 | 17.5분 | 2초 · 25초 | 2,404 | 5,509 |
| XLSX · PPTX · DOCX · HWPX | 21 | 19 | 1.6분 | 2초 | 237 | 691 |
| 합계 | 2,186 | 2,150 | 177분 | | 11,798 | 108,681 |

- 문서 묶음: 유효한 판이 있는 묶음 427(문서 474 중 472에 항목), 보관 판만 있는 묶음 1,048(문서 1,712 중 1,678에 항목).
- 자원(데스크탑, 색인 끝난 직후): Chroma 컨테이너 메모리 3.9GiB, 색인 볼륨 3.9GB, MySQL 볼륨 234MB, GPU 5.4GB(임베딩 모델). 서비스 스택은 데이터셋 작업 동안 멈췄다(한 번에 한 스택, 절차 문서).
- 처리 시간은 어림(ADR-0038의 2~5시간) 안이었다. PDF는 문서당 평균 14.6초로 서비스 색인 때(가장 큰 평가 몫 PDF를 빼고 약 17초)보다 조금 짧았다. 처리 시간은 업로드 기록의 앞 문서와의 간격으로 쟀다 — HTML 최대 347초는 표본 10개와 전체 실행 사이의 대기(비밀번호 입력)가 섞인 값이다.

## 4. 남은 것과 한계

- 첫 질문 때 BM25 색인과 표 사실 메모리 캐시(108,681개, 서비스의 약 2.4배)를 만드는 시간·메모리는 아직 재지 않았다. 학습 예시 근거 붙이기 첫 실행에서 잰다.
- 보관 판 PDF의 표 사실이 많아, 학습 예시의 근거 블록에 표 사실이 서비스보다 자주 들어올 수 있다. 근거 모양은 학습 예시 첫 묶음에서 확인한다.
- 데이터셋 색인을 다시 만들 때(새 학기 공지 등)는 데이터셋 스택만 백업하고 다시 만든다(`deploy/backup.sh documind_dataset`). 서비스 색인은 건드리지 않는다.
