# 색인할 때 표 청크에 표 번호 남기기 (2026-11-25)

> 이슈 #269. 상태: 맥북 구현과 확인, 데스크탑 작업용 색인 다시 색인과 확인 끝. 서비스 색인은 아직 그대로다. 다음 PR(표 번호로 표 전체를 모아 근거 블록에 넣는 조립)은 블록 모양 합의 뒤.
> 앞 기록: `표-질문-문제-정의-20261121.md`(원인: 서버가 원본 표를 주지 않음).

## 결론

- 색인 항목 메타데이터에 `table_numbers`(정수 배열)를 더했다. 문서 안 표 번호이고, 표가 없는 항목에는 키를 넣지 않는다.
- 다음 PR은 `{"$and": [{"document_id": "7"}, {"table_numbers": {"$contains": 3}}]}` 하나로 그 표의 조각을 모두 꺼낼 수 있다(합성 데이터 테스트로 실제 Chroma에서 확인).
- 평가 근거 문서 103개를 현재 코드로 다시 자르면, 근거에 나온 표 블록 427개 중 393개에 번호가 붙는다. 원문 청크는 11-16 평가 도구 지도와 번호까지 같다(868/868) [실측].

## 1. 문제

표 하나가 약 800자 청크 여럿으로 나뉘어 색인되는데, 청크에 어느 표의 조각인지가 남지 않는다. 그래서 표 조각 하나가 검색돼도 같은 표의 나머지 행을 모을 수 없다. 11-16 평가 도구는 색인 밖에서 같은 일을 했지만(`#259` 표 번호 지도), 서버 색인에는 없었다.

## 2. 메타데이터 키와 값 모양

| 항목 | 정한 것 |
|---|---|
| 키 | `table_numbers` |
| 값 | 정수 배열, 오름차순, 1부터. 예: 표 둘의 조각이 든 청크는 `[2, 3]` |
| 표가 없을 때 | 키를 넣지 않음 |
| 조회 | `document_id`(문자열) 조건과 `{"table_numbers": {"$contains": 번호}}`를 `$and`로 |

근거 [원문]: 지금 쓰는 판(`chromadb/chroma:1.5.5`, 파이썬 클라이언트 1.5.5)의 공식 문서는 "Metadata arrays can contain strings, integers, floats, or booleans."라고 하고, 배열은 한 가지 형만 담고 빈 배열은 받지 않는다고 적는다. 배열 안 값으로 거르는 연산자는 `$contains`·`$not_contains`다.
- https://docs.trychroma.com/docs/querying-collections/metadata-filtering
- https://docs.trychroma.com/docs/collections/add-data

설치된 클라이언트 1.5.5 코드도 같은 검사(`_validate_metadata_list_value`: 비지 않고 한 형)와 `$contains` 연산자를 갖고 있다 [원문]. 테스트에서 `EphemeralClient`에 넣고 `$contains`로 꺼내 봤다 [실측].

버린 대안 [판단]:

| 대안 | 버린 이유 |
|---|---|
| JSON 문자열(`"[2, 3]"`, 기존 `retrieval_source_block_ids` 방식) | Chroma 메타데이터 조건으로 문자열 안을 거를 수 없다. 조립 때 문서의 모든 청크를 꺼내 파이썬에서 걸러야 한다 |
| 대표 표 하나(스칼라 정수) | 표 둘이 든 청크에서 한 표를 잃는다. 평가 근거 문서에도 표 둘의 조각이 든 청크가 있다(5절) |
| 키 여러 개(`table_number_1`, `table_number_2` …) | 꺼낼 때 키마다 `$or`가 필요하고 상한을 정해야 한다 |
| 문서까지 든 문자열(`"7:T3"`) | 문서를 다시 올리면 `document_id`가 바뀌므로 값만으로 전역에서 유일해지지 않는다. 정수와 `document_id` 조건이면 충분하다 |

## 3. 번호 규칙

11-16 평가 도구의 규칙을 서버 모듈 `ai-server/table_numbering.py`로 옮겨 적었다(서버는 평가 도구를 import하지 않는다). 표 아래 주석 고르기와 조각 잇기는 옮기지 않았다(다음 PR 범위).

| 규칙 | 내용 |
|---|---|
| 표 | 로더 글(PDF는 쪽마다)에서 마크다운 표 줄이 이어진 덩어리. 두 행·두 열 미만은 표가 아니다 |
| 쪽을 넘는 표 | OpenDataLoader JSON의 `previous table id`·`next table id`로 이어진 표를 한 번호로. 마크다운 표와 JSON 표는 같은 쪽에서 글 겹침(세 글자 조각 0.5 이상)으로 짝 짓는다 |
| 원문 청크 | 청크의 표 줄 덩어리마다, 그 행이 절반 이상 든 표에 붙인다. 청크 쪽 범위는 같은 점수일 때만 쓴다 |
| 표 원문 블록 | OpenDataLoader 표 원문 블록(`…_odl_N`)은 같은 쪽 JSON 표와 글 겹침으로 붙인다 |
| 번호 순서 | 로더 글 순서의 마크다운 표가 먼저, 마크다운 표와 짝 없는 JSON 표가 그 뒤(쪽 순서). 입력 글과 순서만으로 정해져 다시 색인해도 같다 |

특정 문서 이름, 학과명, 기호를 조건에 쓰지 않는다.

## 4. 어디에 붙나

| 색인 항목 | 번호 |
|---|---|
| 원문 청크(`raw`), 거기서 만든 source block·retrieval chunk·표 사실 | 그 청크에 든 표 번호 전부(원문 청크 메타데이터를 복사해 만들어 함께 받는다) |
| OpenDataLoader 표 원문 블록(`source_block`)과 그 표 사실(`table_fact`) | 그 블록의 JSON 표 번호 |

- 원문 청크에서 만든 표 사실은 부모 청크로 따라갈 수 있지만, 복사 구조상 같은 값을 받는다. 뜻은 "이 항목의 글이 나온 원문 청크에 든 표"다 [판단].
- 청크 글, 청크 id, 항목 수는 그대로다. 마크다운 경로와 OpenDataLoader 경로 모두 테스트로 고정했다.
- `EMBED_TABLE_RAW_CHUNKS`를 끄면 표 든 원문 청크가 documents 컬렉션에 없다. 조립은 원문 청크마다 항상 있는 source_blocks 컬렉션에서 꺼내는 편이 안전하다 [판단].

## 5. 맥북 확인 (임베딩 없이) [실측]

세는 규칙을 먼저 정하고 셌다.

- 대상: 11-16 지도를 만든 평가 근거 문서 103개. 현재 코드의 업로드 단계(로딩, OpenDataLoader JSON, 정규화, 나누기, 중복 정리, 짧은 청크 합치기, 겹침)로 다시 잘라 `_build_index_documents`를 부른다.
- 분모(11-16과 같은 근거): 11-14 기준선 실행(표 질문 고르는 몫, 개발셋)의 최종 근거에 나온 서로 다른 청크 가운데, 마크다운 표 줄이 한 줄이라도 든 원문 청크와 표 원문 블록 전부.
- 분자: 다시 색인한 같은 청크 id의 항목에 `table_numbers`가 있는 수.

| | 분모 | 다시 자른 글이 근거 글과 같음 | 지금 번호 | 11-16 지도 번호 |
|---|---:|---:|---:|---:|
| 원문 청크 | 411 | 411 | 382 | 382 |
| 표 원문 블록 | 16 | 7 | 11 | 16 |
| 합 | 427 | | 393 | 398 |

- 11-16 기록의 분모는 429였다. 같은 규칙으로 다시 센 분모는 427이고, 2개 차이의 원인은 확인하지 못했다. 분자 398은 같다.
- 원문 청크 근거에서 번호가 없는 29개: 표로 보지 않는 덩어리(한 행이나 한 열) 25개, 표 4개(PDF 2, HWP 2). 11-16 기록은 25개와 6개였다.
- 표 원문 블록은 #264·#266 뒤로 글과 순번이 바뀌었다. 덤프의 표 원문 블록 441개 중 같은 id에 같은 글은 104개, 다른 글 233개, 없어진 id 104개다. 그래서 id로 맞춘 비교(16 대 11)는 같은 블록끼리의 비교가 아니다.
- 다시 자른 전체: 표로 보는 덩어리가 든 원문 청크 873개 중 867개, 표 원문 블록 470개 중 432개에 번호가 붙었다. 표 아닌 청크에 붙은 것 1개(표의 한 행 조각).
- 지도와 같은 묶음: 둘 다 번호를 붙인 원문 청크 868개는 번호까지 모두 같다. 처음 정한 규칙(지도 표마다 가장 많이 겹친 내 번호로 바꿔 비교)으로는 842/868이었고, 다른 26개는 모두, 표 둘이 든 청크 때문에 두 번호가 같은 수로 비겨 작은 번호를 고른 탓이었다. 두 쪽 번호 순서 규칙이 같으므로 번호를 바로 비교해 868/868로 고쳐 셌다(결과를 본 뒤 세는 법을 바꿨다). 같은 글인 표 원문 블록 103개도 모두 같은 묶음이다.
- 다시 색인 같음: 표 원문 블록이 있는 PDF 문서 하나를 두 번 색인해 모든 항목의 번호가 같았다.

## 7. 구현 위치에서 고른 것과 버린 것 [판단]

| 고른 것 | 버린 것과 이유 |
|---|---|
| 새 모듈에 규칙, `main.py`는 입력 모으기와 메타데이터 넣기만 | `main.py` 안에 쓰기: 이미 6,700줄이다 |
| 평가 도구 규칙을 옮겨 적기 | 평가 도구 import: 서버가 `tools/corpus`에 기대면 배포 이미지에 평가 도구가 들어가야 한다 |
| 표 원문 블록은 글 겹침으로 JSON 표에 붙이기(평가 도구와 같음) | 어댑터가 표 원문 블록에 JSON 표 id를 넘기게 고치기: 더 정확하지만 표 사실 생성 쪽을 건드려 이번 범위 밖이다 |
| 로더 글을 업로드 단계에서 그대로 넘김(`loader_docs`) | 정규화한 글: 11-16 지도가 로더 글로 만들어 같은 결과를 견줄 수 있게 했다 |

## 8. 데스크탑 작업용 색인 확인 (2026-11-25) [실측]

서비스 색인 볼륨을 새 작업용 볼륨으로 복사하고(서비스 볼륨은 읽기만), 이 브랜치의 AI 서버로 모든 문서를 같은 `document_id`로 지우고 다시 넣었다. 문서 698개, 실패 0, 53분.

세는 규칙: 원문 청크는 source_blocks에서 id에 `_odl_`이 없는 항목(원문 청크마다 하나), 표 원문 블록은 `_odl_`이 든 항목. 평가 근거 분모는 5절과 같다.

| 항목 | 전 | 후 |
|---|---:|---:|
| 문서 | 698 | 698 |
| 원문 청크(id 집합 같음, 글 해시 같음 3,206) | 3,206 | 3,206 |
| retrieval chunk | 3,206 | 3,206 |
| 표 원문 블록 | 448 | 479 |
| 표 사실 | 45,878 | 46,309 |

- 표 원문 블록과 표 사실 수가 늘어난 것은 서비스 색인이 #266(목록 안 표도 표 사실로) 전 코드로 만들어졌기 때문이다. 표 원문 블록 id 집합도 그래서 달라졌고, 같은 id에 같은 글은 111개다.
- 번호: 표로 보는 덩어리가 든 원문 청크 1,047개 중 1,041개, 표 원문 블록 479개 중 439개, 표 사실 46,309개 중 45,550개. 표 아닌 원문 청크에 붙은 것 1개.
- 평가 근거 427개 중 393개(원문 청크 382/411, 표 원문 블록 11/16). 맥북에서 센 값과 같다.
- 서버 Chroma(1.5.5)에 배열이 그대로 저장되고, `document_id`와 `$contains` 조건으로 한 표의 원문 청크 둘과 표 원문 블록 하나가 함께 나왔다(PDF 문서 하나로 먼저 확인).
- 질의 경로: 작업용 서버에 표 질문 3개(고르는 몫)와 근거에 표가 없는 개발셋 질문 2개를 넣어 5개 모두 HTTP 200, 답과 근거 8개가 왔다. 답의 품질은 재지 않았다.

## 9. 남은 것

- 서비스 색인에는 아직 번호가 없다. 다음 PR(조립)과 함께 다시 색인한다.
- 따로 볼 것: 번호가 안 붙은 표 원문 블록 38개(470개 중)의 원인. 어댑터가 JSON 표 id를 표 원문 블록에 넘기면 글 겹침 짝짓기가 필요 없다. 11-16 분모 2개 차이.
