# M2 표 근거 실험 설계 — 표를 읽고 나누고 모델에 주는 방법을 실측으로 고른다

> 상태: 확정(2026-11-14), 실행 전. 10절의 값으로 시작하고, 실행하며 바꾸는 값은 10절에 날짜와 이유를 적는다. 앞 문서: `표-근거-개선-설계-20261113.md`(문제 정의, 진행 방식 결정). 후보의 근거: `../research/표-근거-처리방법-후보-조사-20261114.md`(아래 '방법 조사'), `../research/PDF-표-읽기-도구-후보-조사-20261114.md`(아래 '도구 조사'), `../research/표-범례-각주-처리-조사-20261113.md`(아래 '범례 조사').

## 1. 목적과 범위

목적: 표와 표에 딸린 글(범례, 주석)이 근거인 질문에 챗봇이 맞게 답하도록, 아래 네 가지를 같은 조건에서 재서 고른다.

1. PDF를 읽는 도구
2. 표 청크를 만드는 법
3. 프롬프트에 표 근거를 넣는 법
4. 답을 내보내기 전에 검증하는 법

고정하는 것: 생성 모델(학습 전 A.X 4.0 Light), 검색 설정, 근거 수, 기준 날짜, 온도. 운영 구성 실행(`20261110-m2-base-dateon-asof1031`)의 기록과 같게 둔다. HWP, HTML, DOCX 로더는 바꾸지 않는다.

배경 [실측, 앞 문서 2절]: 개발셋 본 149문항 중 표 근거 45문항에서 실패가 13개다. 근거를 받고도 틀린 표 문항 14개 중 12개가 PDF다. 문항 하나에 결함이 겹쳐 있어 방법 하나의 효과를 문항 수로 따로 셀 수 없었다.

## 2. 재는 문항

### 2-1. 지금 문항으로는 모자라다

- [실측] 평가셋 v3은 348문항이고 표 근거 태그는 63문항이다. 개발셋 본의 표 근거 45문항은 문서 14개에서 나왔고 30문항이 값 하나를 묻는다.
- [실측] 문항의 태그에 범례나 주석이라는 유형이 없다. 근거 인용문에 ※ 주석이 든 문항은 개발셋 본에 10개 있고, 기호의 뜻을 알아야 답하는 문항은 찾지 못했다.
- [판단] 서비스에는 그런 질문이 들어온다. 모집요강의 정원내 모집인원 표는 학과 이름에 `♣`를 붙이고 범례에 `♣ 표시 = 4년제 학사학위(전공심화)과정 운영 학과`라고 적는다. "전공심화과정이 있는 학과는 어디예요?"는 범례와 표 전체를 함께 읽어야 답할 수 있다.

### 2-2. 표 질문 유형 묶음을 새로 만든다

평가셋 설계(`../m1/평가셋-설계-20261004.md` ①)의 태그에 '표 구조' 묶음을 더한다. 답 유형과 채점 규칙은 그대로 쓴다.

| 태그 | 무엇을 읽어야 답하나 | 질문 예 |
|---|---|---|
| 범례의 뜻 | 칸에 기호만 있고 뜻은 범례에 있다 | 정원외 모집인원 표에서 칸이 `◈`인 전형의 모집인원 |
| 범례 표시 행 모으기 | 기호가 붙은 행을 표 전체에서 모은다 | 전공심화과정이 있는 학과는 어디예요? |
| 표 주석의 조건 | 표 아래 ※ 줄이 값의 조건이나 예외를 정한다 | 면접 100% 전형은 면접 점수가 몇 점 이상이어야 뽑혀요? |
| 여러 줄 머리글 | 열 이름이 두 줄 이상이다(수시1차 아래 일반고) | 항공운항과는 수시 1차 일반고 전형으로 몇 명 뽑아요? |
| 합친 칸 | 세로로 합친 칸의 값이 첫 행에만 있다(계열) | 어느 계열에 속한 학과인지가 조건인 질문 |
| 쪽을 넘는 표 | 답이 든 행이 표가 이어진 다음 쪽에 있다 | 다음 쪽으로 넘어간 행의 값 |
| 여러 행 모으기 | 조건에 맞는 행 모두, 합계, 최댓값 | 특기자(어학) 전형으로 뽑는 학과는 어디예요? |
| 표에 없는 값 | 표에 그 행이나 열이 없다(답없음) | 표에 없는 전형의 모집인원 |

- 수량: 태그마다 10~12문항, 합쳐 80~100문항. 태그마다 10문항보다 적으면 한두 문항 차이를 우연과 가를 수 없다 [판단].
- 문서: 평가 몫 문서에서만 만든다(학습에 쓴 문서와 겹치지 않게). PDF를 중심으로 하고, 한 문서에 몰리지 않게 문서마다 문항 수 상한을 둔다. 범례 태그는 범례가 있는 문서가 적어 그 문서에 몰린다. 몇 개 문서에서 나왔는지 함께 적는다.
- 만드는 법: 지금 평가셋과 같다. 정답은 원본 문서의 쪽 그림을 보고 쓴다(색인 글을 보고 쓰면 도구가 틀리게 읽은 표가 정답이 된다). 다른 세션이 정답을 보지 않고 다시 답해 대조하고, 자동 검증을 거쳐, 판정이 갈린 문항만 사람이 본다(`../m1/평가셋-설계-20261004.md` ⑦).
- 나누기: 문서 단위로 고르는 몫 70%와 확인 몫 30%로 나눈다. 후보를 거르고 조합을 정하는 데는 고르는 몫만 쓰고, 확인 몫은 마지막 조합을 한 번 잴 때만 연다. 평가셋 v3의 테스트셋은 열지 않는다.
- 보관: 평가셋 v3 파일은 그대로 두고 같은 파일 형식의 별도 묶음으로 둔다.

### 2-4. 도구 비교용 표 정답

PDF를 읽는 도구는 답을 생성하기 전에 표 단위로 먼저 견준다(도구 조사 6.2).

- 표본: 범례 조사가 뽑은 PDF 61개(표 540개)에서 층을 나눠 표 80~100개를 고른다. 개발셋 실패 14문항의 근거 표 전부, 여러 줄 머리글 표, 세로 병합이 3행 이상인 표, 쪽을 넘긴 표 10개 이상, 범례나 주석이 딸린 표, 무작위 표.
- 정답: 같은 문서의 HWP판이 있으면 HWP 로더의 표 격자를 초안으로 쓴다. 없으면 쪽 그림과 글자 층을 보고 HTML 표로 쓴다. 표마다 딸린 주석과 범례 줄도 정답에 적는다. 사람은 실패 문항의 표와 무작위 20개만 확인한다.

## 3. 후보

이름 뒤 괄호는 조사 문서의 후보 번호다. 근거와 평가 설정은 조사 문서에 있다.

### 3-1. 프롬프트에 표 근거를 넣는 법(색인 그대로, 11개)

| 후보 | 하는 일 |
|---|---|
| 추측 줄 빼기(방법 15) | 「질문 의도 추출 정보」 가운데 표에서 이름과 값을 조합한 줄을 넣지 않는다 |
| 우선 사용 지시만 빼기 | 줄은 두고 "질문 의도 추출 정보가 있으면 우선 사용" 지시문만 뺀다 |
| 표 근거에 원본 표 넣기(방법 1) | 표가 든 근거 블록에만 청크의 원본 표를 넣는다 |
| 같은 표 조각 합치기(방법 17) | 검색된 근거 가운데 같은 표의 조각을 머리글 하나로 합쳐 한 블록으로 둔다 |
| 표 전체로 넓히기(방법 9, 21) | 표 조각이 검색되면 그 표의 모든 조각을 모아 준다. 길이 상한 두 단계로 잰다 |
| 행 문장으로 찾고 원본 청크 주기(방법 10) | 행 문장은 검색에만 쓰고 프롬프트에는 그 행이 속한 원본 청크를 준다 |
| 행 경계 표시(방법 4) | 행마다 열 이름과 값을 괄호로 묶어 준다 |
| 행을 키와 값 묶음으로(방법 5) | 행마다 `{열 이름: 값}`으로 준다. 반대 근거가 있어 대조군이다 |
| 근거 순서 바꾸기(방법 18) | 관련이 높은 근거를 앞과 끝에 둔다 |
| 관련 행을 먼저 옮겨 쓰고 답하기(방법 19) | 답 앞에 근거 표의 해당 행을 그대로 쓰게 한다 |
| 행을 하나씩 확인하게 하기(방법 25) | 조건에 맞는 행을 찾을 때 행마다 확인하게 지시한다 |

### 3-2. PDF를 읽는 도구(표 단위로 먼저 견줌, 6개와 조건부 3개)

| 후보 | 넣는 이유 |
|---|---|
| OpenDataLoader 2.2.1 마크다운 | 지금 방식, 기준선 |
| OpenDataLoader 2.2.1 JSON으로 표 격자 채우기 | 앞 문서 4-5의 안. 도구는 그대로 두고 병합 정보를 쓴다 |
| OpenDataLoader 2.5.22 | 같은 출력 형식에 머리글 처리 개선 |
| OpenDataLoader hybrid | 같은 출력 형식에 Docling 표 모델 |
| Docling | 칸마다 머리글 표시를 준다. PDF 글자를 그대로 쓴다 |
| MinerU 4.2.2 | 그림을 읽는 모델 쪽 대표. 쪽을 넘는 표를 합친다 |
| PaddleOCR-VL-1.6, GLM-OCR, PP-StructureV3 | 위에서 MinerU가 앞설 때만 더한다 |

라이선스와 하드웨어 조건은 도구 조사 질문 4에 있다. 설치 전에 다시 확인한다.

### 3-3. 표 청크를 만드는 법(색인을 다시 만듦, 9개)

3-2에서 남은 도구 위에서 잰다.

| 후보 | 하는 일 |
|---|---|
| 머리글 전체 되풀이(방법 8) | 표를 나눌 때 여러 줄 머리글 전체를 조각마다 되풀이한다 |
| 칸마다 머리글을 붙인 줄(방법 3) | `행 머리글, 열 머리글 = 값`을 칸마다 쓰고 길이로 자르지 않는다 |
| HTML 표(방법 2) | 합친 칸을 `rowspan`과 `colspan`으로 남긴 표로 쓴다 |
| 표를 한 청크로(방법 7) | 길이 상한 안에서는 표를 나누지 않는다 |
| 쪽을 넘는 표 합치기 | 도구가 준 연결 번호로 조각을 한 표로 합친 뒤 나눈다 |
| 기호가 든 주석 줄만 붙이기(방법 12) | 표 바로 뒤 주석에서 표 칸의 기호가 든 줄만 붙인다(범례 조사 ①′) |

| 좌표 규칙으로 가려낸 주석 붙이기 | 표 위아래로 줄 높이 두 배 안의 짧은 글을 주석으로 본다(범례 조사 질문 4) |

| 다른 모델로 검사(방법 30) | 생성 모델과 다른 로컬 모델이 답의 값과 근거 칸을 대조한다 |

### 3-5. 이번에 넣지 않는 것

- 2차로 미룸: 표를 SQL로 다루기(방법 22), 질문 종류별 경로 나누기(27), 표 질문 학습(28), 조각마다 모델이 맥락 문장 쓰기(13), 표 요약 색인(11), 표 설명 한 줄(6), 하위 표 추출(16). 색인할 때 모델 호출이 들거나 부품이 새로 필요하다. 1차 결과에서 여러 행 모으기 태그가 남으면 연다.
- 넣지 않음: 코드 실행(23), 단계별 표 연산(24), 다수결(26). 작은 모델에서 나빴다는 근거가 있거나 호출이 10배다(방법 조사 6장).

## 4. 지표와 판단 기준

기준은 결과를 보기 전에 정했다(10절).

### 4-1. 답 생성 실험(3-1, 3-3, 조합)

- 견주는 법: 같은 날 같은 색인과 같은 검색으로 잰 기준선과 문항별로 짝 비교한다(`evalset compare-runs`).
- 지표: 표 질문 유형 묶음의 맞음 수(전체와 태그별), 개발셋 본의 틀림 수와 답없음 거절 수, 정답 근거가 근거 8개에 들어온 문항 수(검색), 프롬프트 토큰 수와 잘림 수, 응답 시간.
- 거르기: 표 질문 유형 묶음의 고르는 몫에서 기준선보다 맞음이 3문항 이상 많고, 개발셋 본에서 틀림이 2문항 넘게 늘지 않고 답없음 거절이 1문항 넘게 줄지 않으면 조합 단계로 보낸다.
- 채택: 마지막 조합이 아래를 모두 채운다.
  1. 표 질문 유형 묶음의 확인 몫에서 기준선보다 맞음이 많다(짝 비교, 정확 이항 검정 한쪽 p < 0.05).
  2. 개발셋 본에서 틀림과 답없음 거절이 나빠지지 않는다(나빠진 문항이 좋아진 문항보다 많지 않다).
  3. 새 평가 데이터 260문항에서 맞음이 의미 있게 줄지 않는다.
  4. 프롬프트 잘림이 0이고 응답 시간 중앙값이 기준선의 1.5배 안이다.

### 4-2. PDF 도구 비교(3-2)

- 지표: 머리글 경로 일치율(데이터 칸마다 열 머리글 경로가 정답과 같은 비율), 세로 병합 채움 정확도, 숫자 칸 완전 일치율, 쪽을 넘는 표 연결의 정밀도와 재현율, 표와 주석 연결의 정밀도와 재현율, 쪽당 시간, 최대 VRAM, 실패한 문서 수.
- 거르기: 숫자 칸 완전 일치율이 기준선보다 낮은 도구는 뺀다(숫자를 틀리게 읽으면 표 구조가 맞아도 답이 틀린다). 남은 것 중 머리글 경로 일치율이 높은 둘이나 셋만 색인을 다시 만든다.

### 4-3. 답 검증(3-4)

- 지표: 지난 답 기록에서 잡은 틀린 답 수와 잘못 거른 맞는 답 수.
- 거르기: 잘못 거른 맞는 답이 잡은 틀린 답의 절반을 넘으면 뺀다.

## 5. 순서와 시간

| 단계 | 하는 일 | 데스크탑 |
|---|---|---|
| 0 | 표 질문 유형 묶음과 도구 비교용 표 정답을 만든다 | 필요 없음 |
| 1 | 세 갈래를 함께 시작한다: 프롬프트 후보 11개를 하나씩 기준선과 견줌, 도구 6개를 표 단위로 견줌, 검증 2개를 지난 답 기록으로 잼 | 프롬프트와 도구 |
| 2 | 남은 도구마다 '지금 조각 방식' 색인을 기준선으로 만들고, 표 청크 후보 9개를 색인을 다시 만들어 잰다 | 필요 |
| 3 | 단계 1과 2에서 남은 것을 조합해 다시 잰다. 마지막 조합을 확인 몫, 개발셋, 새 평가 데이터로 잰다 | 필요 |
| 4 | 결과 보고서를 내고 고른다. 고른 것만 변경 하나에 PR 하나로 올린다 | 필요 없음 |

시간 어림:

- [실측] 생성은 205문항에 약 9분(문항당 2.8초)이다. [계산] 표 질문 유형 100문항과 개발셋 205문항을 함께 재면 한 번에 약 14분이고, 프롬프트 후보 11개는 약 2시간 40분이다.
- [실측, 2026-10-21] 서비스 색인을 다시 만드는 데 54분이 걸렸다. [계산] 표 청크 후보 9개와 도구별 기준선을 합치면 색인만 9~10시간이다. 표가 있는 문서만 다시 색인해 줄일 수 있는지는 실행 때 확인한다.
- 도구 비교와 채점에서 '애매'로 남는 답의 판정 시간은 재지 않았다. 첫 실행에서 재어 전체 시간을 다시 어림한다.
- [판단] 데스크탑을 20시간 안팎 켜 두는 규모다.

## 6. 실행 규칙

- 한 번에 하나만 바꾼다. 후보마다 설정으로 켜고 끄게 만들고 기본값은 꺼짐이다.
- 기준선은 같은 날 다시 잰다. 온도 0에서도 일부 문항은 문장이 달라지므로, 같은 설정을 두 번 재어 갈리는 문항 수를 먼저 적는다.
- 코드는 실험 브랜치에 두고 develop에는 고른 것만 올린다. 테스트는 지어낸 학교(가나대학) 데이터로 쓴다. 특정 학과명이나 기호를 조건문에 박지 않는다.
- 서비스 색인은 건드리지 않는다. 후보 색인은 새 이름으로 만든다. `docker compose down -v`는 쓰지 않는다. 데스크탑의 파일을 지우는 일은 사람이 한다.
- 도구 설치와 모델 파일 내려받기는 목록, 크기, 라이선스를 먼저 보이고 허락을 받은 뒤에 한다. 학교 문서를 외부 API로 보내지 않는다.
- 채점은 규칙 채점을 먼저 하고, '애매'로 남은 답만 격리된 판정으로 넘긴다. 판정은 후보 이름을 가린 채 한다.
- 평가셋 v3의 테스트셋과 표 질문 유형 묶음의 확인 몫은 5절의 단계 3 전에 열지 않는다.
- 실행마다 설정, 색인 이름, 코드 커밋을 기록한다. 보고서의 숫자는 결과 파일에서 읽어 만든다.

## 7. 결과물

- 결과 보고서(HTML, 로컬 산출물): 결론과 정할 것을 맨 앞에 둔다. 후보별 지표는 그래프로 견주고, 태그별 결과와 기준선보다 나빠진 지표도 함께 보인다.
- 고른 방법의 결정 기록(ADR)과 결과 문서(`docs/rag/m2/`).
- 고른 방법의 코드 PR(변경 하나에 PR 하나).
- 표 질문 유형 묶음(로컬 `Assets/eval/`)과 만든 과정 문서.

## 8. 위험과 한계

- 고르는 몫으로 후보 28개를 거르면 우연히 좋게 나온 후보가 뽑힐 수 있다. 확인 몫을 따로 두고 마지막에 한 번만 여는 이유다.
- 태그마다 10~12문항은 큰 차이만 가른다. 태그별 숫자는 방향을 보는 데 쓰고 채택은 묶음 전체로 판단한다.
- 프롬프트 후보는 지금 색인 위에서 잰다. 표 청크가 바뀌면 순위가 달라질 수 있어 단계 3에서 조합을 다시 잰다.
- 색인을 다시 만들면 검색 결과도 바뀐다. 표 청크 후보의 효과는 검색 지표와 생성 지표를 나눠 본다.
- 근거 글이 늘면 답이 나빠진 측정이 두 번 있었다(앞 문서 2-5). 원본 표를 넣는 후보는 답없음 거절을 첫째로 본다.
- 그림을 읽는 도구는 숫자를 틀리게 읽을 수 있고, 한국어 표에 대한 심사 통과 근거가 없다(도구 조사 5장).
- 근거 블록의 모양이 바뀌면 학습용 프롬프트와 선호 쌍의 틀린 답도 다시 받아야 한다. 학습 데이터 제작(#254, #255)은 이 실험 뒤로 둔다.

## 9. 네 관점

- 서비스: 실제로 들어올 표 질문 유형으로 고르므로, 고른 방법이 사용자가 겪는 품질을 반영한다.
- 비즈니스: 학습 서버 없이 데스크탑으로 잰다. 드는 것은 데스크탑 가동 시간과 문항 검수 시간이다.
- 유지보수: 고른 방법만 코드에 남기고 나머지 설정과 분기는 지운다. 표 질문 유형 묶음은 도구를 바꿀 때마다 다시 쓴다.
- 확장: 새 PDF 도구나 새 방법이 나오면 같은 문항과 같은 기준으로 견줄 수 있다.
