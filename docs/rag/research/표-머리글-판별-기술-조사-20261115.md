# 표 머리글 칸을 확실하게 아는 방법 조사

## 요약

- [실측] 작성자가 파일에 남긴 머리글 표시는 우리 문서에 드물다. 서비스 색인 표 793개 중 153개(19.3%)에만 있고, 그 152개가 학교 홈페이지 HTML의 `th`·`thead`다. 서비스 색인 PDF 표 533개는 0개, HWP 표 60개는 1개다(부록 B).
- [실측·원문] 이름은 머리글이지만 서식 설정인 표시가 많다. HWP 「제목 줄 자동 반복」은 표 1,591개 중 1,564개(98.3%)에 켜져 있고 기본값이 켜짐이다 [3]. DOCX `tblLook` 첫 행은 23개 중 21개, OpenDataLoader 2.5.22의 `is_header`는 표 158개 모두 첫 행에만 붙었다. 이 셋은 어느 줄이 머리글인지 알려 주지 않는다.
- [원문] 머리글 칸을 출력하는 모델은 있다(Docling TableFormer, Table Transformer, SmolDocling·Granite-Docling, 클라우드 API). 그러나 학습 정답의 머리글은 출판사 XML의 `thead`나 정규화 규칙에서 왔고 [12·13·14], 머리글 판별만 따로 잰 정확도를 낸 심사 논문은 찾지 못했다. 7~8B 언어 모델은 머리글 인식 F1이 6~30%였다 [19].
- [실측] 우리 PDF 표 정답에서 구조 규칙과 Docling이 머리글 줄 수에 동의한 표는 75개 중 62개이고, 그중 60개가 맞았다. 둘이 다른 13개에서는 규칙이 9개, Docling이 4개 맞았다. Docling이 맞힌 4개는 모두 머리글이 없는 양식 표다(3장 질문 4).
- [실측] 데스크탑에서 같은 표 정답으로 MinerU 4.2.2, Table Transformer v1.1, Granite-Docling-258M을 더 쟀다. 머리글 경로는 0.464, 0.685, 0.080으로 모두 구조 규칙(0.954)보다 낮다. Table Transformer는 규칙과 다를 때 하나도 맞히지 못했고, MinerU와 Granite-Docling은 우리 표에 머리글 표시를 하나도 내지 않았다(3장 질문 4 (다)).
- [판단] 권고: 「뜻이 분명한 파일 표시가 있으면 먼저 쓰고, 없으면 설계의 구조 규칙」. 꾸밈 표시는 쓰지 않는다. 모델을 더해 견주는 일은 지금 숫자로는 얻는 것보다 잃는 표가 많아 미룬다. 규칙의 근거를 키우는 길은 사람 확인 28표를 끝내는 것이다(6장).

## 1. 배경과 조사 질문

- 왜 조사하나: 표 오답 수정 설계 초안(`표-오답-수정-설계-20261114.md` 4-2절, 로컬 보관)은 PDF와 HWP 표의 머리글 줄 수를 칸 병합 모양으로 정하는 구조 규칙으로 「추정」한다. 추정이 아니라 머리글을 알려 주는 표시나 모델이 있으면 그쪽이 낫다.
- 정하려는 것: 설계 4-2절의 「머리글 줄 수를 정하는 법」을 그대로 둘지, 파일 표시나 모델을 앞에 둘지.
- 이미 답한 것: 공개 구현의 머리 줄 처리, 구조 규칙 7가지의 실측, PDF에서 칸 구조를 얻는 길은 [표 머리글 구조 조사](표-머리글-구조-직렬화-조사-20261114.md)(아래 「구조 N」) 질문 1~3과 부록 B에 있다. PDF 도구 후보의 라이선스와 속도는 [PDF 표 읽기 도구 조사](PDF-표-읽기-도구-후보-조사-20261114.md)(「PDF N」)에 있다. 여기서는 되풀이하지 않는다.
- 조사 질문:
  1. 문서를 만든 사람이 파일에 남긴 머리글 표시가 형식마다 무엇이고, 우리 문서에 얼마나 있나
  2. 머리글 칸을 출력으로 알려 주는 모델과 도구에는 무엇이 있고, 근거가 얼마나 되나
  3. 머리글 판별이라는 과제 자체의 근거(정답 데이터, 규칙과 모델의 비교, 여러 신호를 견주고 다르면 미루기, 반대 근거)
  4. 우리 자료로 지금 잴 수 있는 것(형식별 개수, 규칙과 Docling이 같은 표와 다른 표의 정답 일치율)

## 2. 범위와 방법

- 자료 기준: `AGENTS.md` §4와 이 폴더 README 머리말. 근거는 표준 문서, 도구·모델을 만든 회사·기관의 공식 문서와 기술 보고서, 게재처를 확인한 심사 논문(A 등급)만 쓴다. 공식 저장소의 릴리스 노트와 코드는 「그 도구가 하는 일」의 사례로만 쓴다(B 등급). 개인 저장소, 프리프린트, 블로그, 검색 요약은 원문을 찾는 실마리로만 썼다.
- 기간: 2025~2026년 자료를 먼저 봤다. 2012~2023년 논문은 「그런 현상이 있다」는 근거로만 쓰고 숫자를 지금 후보로 옮기지 않는다.
- 포함 / 제외: 파일 형식 7개(PDF, HWP, HWPX, DOCX, PPTX, XLSX, HTML)의 머리글 표시, 머리글을 출력하는 모델과 도구, 머리글 정답 데이터와 판별 논문. 줄 모양과 직렬화, 행 이름 고르기, 집계·시점 질문은 다른 조사가 맡아 뺐다.
- 검색한 곳과 날짜: 2026-11-15. 표준·공식 문서(Adobe가 공개한 ISO 32000-1 사본, 한컴 공식 파일 형식 문서 2종, Microsoft Learn, Microsoft Support, Google Cloud, Adobe Developer, Hugging Face 모델 카드), GitHub 릴리스 API, CVF Open Access, ECVA, ACL Anthology, AAAI, VLDB, arXiv 원문. 웹 검색 3회.
- 고른 기준 / 뺀 기준: 논문은 `venue_check.py`로 게재처를 확인했다(OpenAlex, Crossref). 게재처를 찾지 못한 것은 출판사 누리집에서 직접 확인했다(VLDB 워크숍 1편). 프리프린트만 있는 것은 뺐다(부록 A).
- 건수: 후보 목록 세 개에 이름이 오른 자료는 형식 표준·라이브러리 51행, 모델·도구 19항목, 과제 논문·데이터셋 25항목이다(목록마다 단위가 달라 더하지 않는다). 원문을 받아 대조한 것은 A 등급 24건과 B 등급 4건으로 참고 문헌 28건이다. 뺀 자료는 부록 A. 인용 문장과 숫자 50개를 `quote_check.py`로 원문 글에서 대조했다(모두 있음, 두 단 배치 PDF는 평문으로 바꿔 다시 대조).
- 제작사·기관 체크리스트: Adobe 찾음 [1·10] · 한글과컴퓨터 찾음 [2·3] · Microsoft 찾음 [4~8·12·14·20·26] · Google 찾음 [9] · IBM 찾음 [11·13·15·16] · Baidu 찾음 [18] · 상하이 AI 연구소(MinerU) 찾음 [17] · AWS 앞선 조사 [구조 24] · Hancom(OpenDataLoader) 찾음 [24·25] · 국가표준 KS X 6101 원문은 열지 못함(한컴 HWPML 문서와 우리 HWPX 파일로 대신 확인).
- 막힌 페이지: 없음. ISO 32000-2, ISO 14289(PDF/UA), ECMA-376 전문, KS X 6101은 내려받지 않았다(부록 A).
- 직접 잰 것: 수집 문서 3,591개의 형식별 머리글 표시 개수, 표시가 실제 머리글과 맞는지 표본, OpenDataLoader 2.2.1의 구조 트리 옵션, 표 정답 85개로 규칙·Docling·OpenDataLoader 2.5.22의 머리글 줄 수(맥북, 앞선 도구 출력). 데스크탑(RTX 4070 Super 12GB)에서 MinerU 4.2.2, Table Transformer v1.1, Granite-Docling-258M을 새로 돌려 같은 지표를 쟀다(부록 B).

## 3. 질문별 결과

### 질문 1. 형식별 머리글 표시와 우리 문서의 개수

**결론** [실측] 뜻이 분명한 표시가 우리 문서에 쓰인 곳은 학교 홈페이지 HTML뿐이다. 나머지 형식은 표시가 없거나, 있어도 서식 설정이다.

| 형식 | 머리글 표시(정의) | 뜻인가 꾸밈인가 | 우리 로더가 읽나 | 수집 전체 | 서비스 색인 | 표시가 맞는가(표본) |
|---|---|---|---|---|---|---|
| HTML | `th`, `thead`, `scope` [구조 23] | 뜻 | `th`만 읽음(`TableGrid` 규칙 3). `thead`, `scope`는 안 읽음 | 1,221개 중 174개(14.3%) | 191개 중 152개(79.6%) | `th` 표 16개 중 16개, `td`로만 된 `thead` 표 5개 중 5개가 실제 머리글 |
| PDF | 구조 트리의 `TH`, `THead`, `Scope` [1] | 뜻(만든 프로그램에 따라 서식) | 안 읽음 | 파일 792개 중 태그 188개, `TH`가 있는 표 37개(파일 15개). 표본 61개 문서의 표 844개 중 13개(1.5%) | 파일 59개 중 태그 2개, 표 533개 중 0개 | 37개 중 20개 맞음, 11개 틀림, 6개 판단 못 함 |
| HWP 5.0 | 칸의 「제목 칸」 [3], 표의 「제목 줄 자동 반복」 [2] | 제목 칸은 뜻, 반복은 꾸밈 | 둘 다 안 읽음 | 제목 칸 1,591개 중 13개(0.8%), 반복 1,564개(98.3%) | 제목 칸 60개 중 1개 | 제목 칸 13개 중 12개는 0행만 표시(실제 머리글), 1개는 구역 줄 |

| DOCX | 행의 `w:tblHeader`(머리글 행 반복) [4], 표의 `w:tblLook` 첫 행·첫 열 [5] | `tblHeader`는 뜻, `tblLook`은 꾸밈 | `tblHeader`는 읽음(mammoth가 `thead`·`th`로 바꿈) | 23개 중 `tblHeader` 0개, `tblLook` 첫 행 21개 | 9개 중 0개, 첫 행 9개 | — |
| PPTX | `a:tblPr`의 `firstRow`, `firstCol` [6] | 꾸밈 | 안 읽음(MarkItDown이 첫 행을 늘 머리로 [26]) | 5개 중 `firstRow` 1개 | 해당 문서 없음 | — |
| XLSX | 표 개체의 `headerRowCount` [7], 인쇄 제목 행 | 표 개체는 뜻 | 안 읽음(MarkItDown이 첫 행을 늘 머리로 [26]) | 시트 7개 중 표 개체 0개, 인쇄 제목 0개 | 해당 문서 없음 | — |

- 셈 단위: 2행 2열 이상인 표. HTML은 서버 로더와 같은 길로 표를 고른다(칸 하나짜리 표 풀기, 표 안의 표 빼기). 「수집 전체」는 대장에 파일이 있는 모든 문서(색인·보관·제외), 「서비스 색인」은 대장의 색인 상태가 「색인」인 문서다. 서비스 색인 PDF의 표 수는 OpenDataLoader 2.2.1이 찾은 표다.

**형식별 정의와 확인한 것**

- PDF [원문]: ISO 32000-1의 14.8.4.3.4절 표 337은 `TH`를 "A table cell containing header text describing one or more rows or columns of the table."로 정의하고, `THead`는 여러 쪽에 걸친 표에서 쪽마다 다시 그릴 수 있는 머리 행 묶음이다 [1]. 14.8.5.7절 표 349의 `Scope`는 `TH`에만 쓰고 그 칸이 행, 열, 둘 다 중 어디에 걸리는지 적는다 [1].
- PDF [원문]: 같은 표 337 아래 주석은 "The association of headers with rows and columns of data is typically determined heuristically by applications."이고 "Such heuristics may fail for complex tables"라고 적는다 [1]. 표준도 머리글 연결은 보통 읽는 프로그램의 추정이라고 본다.
- PDF [실측]: `TH`가 있는 표 37개는 Word 18개, PowerPoint 11개, 브라우저 인쇄 7개, InDesign 1개에서 나왔다. Word가 만든 18개는 모두 첫 행과 본문 모든 행의 첫 칸을 `TH`로 붙였다. 만든 프로그램 표시에 한글(Hwp, Hancom)이 든 PDF 384개는 하나도 태그가 없다.
- PDF [실측, 표본 판단]: `TH` 행이 실제 머리글과 맞은 표 20개, 틀린 표 11개(전체 폭 제목 줄, 「1, 2, 3」 단계 목록의 첫 행, 서명 칸, 범례 표), 칸 글이 구조 트리에 없어 판단하지 못한 표 6개다. 표 정답과 겹친 2개 중 1개는 맞고(머리글 1줄), 1개는 틀렸다(정답은 머리글 없음, `TH`는 첫 행과 첫 열).
- PDF [원문·실측]: Microsoft는 Word 표에 「머리글 행」 서식 옵션을 켜면 "Your table now has a header row. This means that, behind the scenes, Word and any assistive technologies can communicate intelligently about the table."라고 안내한다 [8]. 이 옵션이 `tblLook` 첫 행이고 [5], 우리 DOCX 표 23개 중 21개에 켜져 있다. Word PDF의 `TH`가 내용과 상관없이 첫 행과 첫 열에 붙는 까닭으로 본다[판단].
- PDF 도구 [실측·B]: OpenDataLoader 2.2.1에는 구조 트리를 쓰는 옵션 `use_struct_tree`(기본 꺼짐)가 있고, 설명은 "Use PDF structure tree (tagged PDF) for reading order and semantic structure"다 [25]. 1.2.0판(2025-11-14)에서 생겼다 [24]. 서버는 이 옵션 없이 부른다(`ai-server/main.py`의 `_load_documents`). Word 태그 PDF 하나에 켜고 돌려 보니 쪽마다 끊긴 표 조각 4개가 구조 트리대로 표 하나(19행)로 묶였지만, 칸 JSON에는 머리글 표시가 없었다(모든 칸이 `table cell`).
- PDF 도구 [B·실측]: 2.5.0판 릴리스 노트에 "fix: preserve table header (TH) semantics in JSON output"가 있고 [24], 2.5.22 JSON 칸에는 `is_header`와 `pdfua_tag`가 있다. 그러나 표 정답 문서의 표 158개 모두 첫 행에만 `is_header`가 붙었고, 머리글 경로 일치율은 0.648로 머리글을 1줄로 둔 값(0.654)과 같다. 2.5.12판의 "Mark first row as Header in tables from TableBorderProcessor" [24]와 맞는 결과다. 태그 없는 PDF에서는 작성자 표시가 아니라 도구의 첫 행 규칙이다[판단].
- HWP 5.0 [원문]: 한컴 공식 문서 5.0 rev 1.3의 표 76(표 속성의 속성) 2번 비트가 「제목 줄 자동 반복 여부」다 [2]. 칸 속성(표 80)과 문단 리스트 헤더(표 65)에는 제목 칸 항목이 없다 [2]. 우리가 센 제목 칸 비트(칸 속성 18번 비트)는 공개 문서가 아니라 커뮤니티 파서 hwplib의 해석이고, M1 조사에서 이 비트로 표 15개를 셌다(`docs/rag/m1/HWP-HTML-표변환-조사-20261002.md` 7.2절).
- HWP·HWPX [원문]: 한컴 HWPML 3.0 문서는 `TABLE`의 `RepeatHeader`를 「제목행을 반복할지 여부」(기본 true), `CELL`의 `Header`를 「제목 셀인지 여부」(기본 false)로 정의한다(표 102, 표 113) [3]. 반복은 기본으로 켜지고, 어느 행이 머리인지는 칸의 제목 셀 표시가 정한다는 뜻이다[판단]. HWPX(OWPML)의 국가표준 원문은 열지 못했고, 우리 HWPX 파일에서 같은 이름의 속성(`repeatHeader`, `header`)을 확인했다.
- DOCX [원문]: `w:tblHeader`는 "This element specifies that the current table row shall be repeated at the top of each new page on which part of this table is displayed."이고, 표 맨 위부터 이어진 여러 행에 붙여 여러 줄 머리글을 만들 수 있다 [4]. `w:tblLook`의 `firstRow`는 "Specifies that the first row conditional formatting shall be applied to the table."로 서식 적용 여부다 [5].
- PPTX [원문]: `a:tblPr`은 표 전체의 시각 속성이고, `firstRow`·`bandRow`를 켠 예에 대해 "The table style defines the formatting applied with the two formatting options enabled."라고 적는다 [6]. 머리글의 뜻이 아니라 표 스타일의 선택지다.
- XLSX [원문]: 표 개체의 `headerRowCount`는 "An integer representing the number of header rows showing at the top of the table."다 [7]. 우리 XLSX 7개에는 표 개체가 없어 쓸 데가 없다[실측].
- HTML [실측]: 서비스 색인 HTML 표의 79.6%가 `th`나 `thead`를 쓴다. 보관 문서(게시판 글) 표 1,030개 중에는 22개(2.1%)뿐이다. 학교 홈페이지 관리 화면이 만드는 표와 게시판 편집기가 만드는 표가 다르다[판단]. `th` 앞 행 수가 왼쪽 위 칸 규칙과 다른 표는 152개 중 1개였고, 그 표는 `th`가 맞았다(머리글 2줄). 전체 폭 한 칸 `th`(표 제목)는 7개로, 지금 `TableGrid` 규칙 2가 제목 줄로 뺀다.

### 질문 3. 머리글 판별 과제의 근거

**정답 데이터와 그 머리글의 출처** [원문]

- PubTabNet(ECCV 2020, IBM): 표는 6,000개 넘는 학술지의 출판사가 조판한 것이고, 칸을 머리와 본문으로 나눈 것이 장점이라고 적는다 [13]. 머리 칸은 출판사 XML의 `thead` 아래 칸이다. "table header cells are defined as th nodes in some tables, but as td nodes in others."라서 `thead` 아래 `td`로 맞췄다 [13].
- PubTables-1M(CVPR 2022, Microsoft): 같은 출판사 XML을 쓰지만 "the column headers for tables in the PMCOA corpus are not always" 맞아서 규칙(알고리즘 1)으로 머리글 칸을 더 추론했다 [12]. 행 머리글은 구역 행(projected row header)만 추론하고 "Inference of the full row header is considered outside the scope of this work."라고 적는다 [12].
- FinTabNet·ICDAR-2013(ICDAR 2023, Microsoft): "neither dataset explicitly annotates which cells belong to the row and column headers."라서 칸 구조 규칙으로 머리글을 추론했고, 두 열짜리 표는 "remove tables with only two columns as the column header of these is structurally ambiguous"로 뺐다 [14]. 머리글 정답이 없는 큰 자료는 규칙으로 정답을 만든다.
- [판단] 머리글을 출력하는 표 구조 모델은 출판사 표시와 규칙에서 만든 정답을 배운다. 모델이 규칙과 독립된 「확실한 정답」을 주는 것이 아니다. 영어 과학·금융 표에서 만든 규칙이 우리 표에서 0.722였다는 앞선 실측 [구조 부록 B]과도 같은 방향이다.

**규칙과 학습 방식의 비교** [원문]

| 자료 | 소속·게재처 | 자료 | 결과 | 우리에게 |
|---|---|---|---|---|
| Fang 외 [21] | 베이징대·펜실베이니아주립대, AAAI 2012 | 과학 논문 PDF 표 281개(CiteSeerX 표본 두 묶음) | 머리 행을 완전히 맞힌 표: 기준선 0.402, 규칙 0.609, 랜덤 포레스트 0.920(표 5) | 규칙이 학습보다 크게 낮았다. 2012년 자료라 숫자는 옮기지 않는다 |
| TabularNet [20] | Microsoft Research Asia 외, KDD 2021 | 스프레드시트 두 묶음 | 위 머리 영역 F1: SVM 0.850, CART 0.874, TabularNet 0.933 / 왼쪽 머리 0.860, 0.881, 0.912(표 2) | 서식 특징을 쓰는 학습 방식. 규칙 기준선은 없다 |

- [원문] 머리글 판별 정확도를 규칙과 최신 표 구조 모델로 같은 자료에서 견준 심사 논문은 찾지 못했다(검색: ACL Anthology, CVF, AAAI, VLDB, 웹 검색).

**여러 신호를 견주고 다르면 미루는 방식** [원문]

- 표 머리글에서 「파일 표시, 규칙, 모델이 다르면 판단을 미룬다」를 구현하거나 잰 심사 논문과 공개 구현은 찾지 못했다.
- 가장 가까운 것은 Snorkel(PVLDB 2017, 스탠퍼드대)이다. 여러 약한 규칙(labeling function)이 "either outputs a label or abstains"하고, 생성 모델이 규칙끼리의 일치와 정확도를 배워 합친다 [22]. Tab2Know는 이 틀을 표의 열 종류를 정하는 데 썼다 [23]. 머리글 판별에 쓴 예는 아니다.
- [판단] 설계 초안의 「규칙들이 서로 다른 줄 수를 내는 표는 줄을 만들지 않는다」가 이미 이 생각이다. 세 신호를 더해도 구조는 같다.

**반대 근거** [원문]

- 모델이 틀리는 표: 언어 모델은 "The greatest errors occur when processing tables with hierarchical headers and merged cells, where even large models lose accuracy."였다 [19]. 표 구조 모델도 합친 칸이 있는 표에서 TEDS가 모두 떨어졌다 [PDF 34].
- 규칙이 깨지는 표: 두 열짜리 표는 머리글이 구조로 정해지지 않는다 [14]. 우리 규칙도 머리글이 없는 양식 표를 1줄로 본다(질문 4).
- 작성자 표시가 틀리는 경우: 서식 옵션이 머리글 행으로 쓰이는 사례 [5·8]와 우리 PDF `TH` 11개 오표시(질문 1). 데이터셋 자체에서도 출판사 XML의 머리글이 늘 맞지 않았다 [12·13].

**(다) 데스크탑에서 잰 후보** [실측]

- 무엇을: 표 정답 85개가 든 PDF 40개 문서(묶음 66개, 96쪽)를 도구마다 돌려 앞선 도구 비교와 같은 지표로 쟀다(`table_metrics.evaluate`). 도구가 준 머리글 줄 수로 만든 머리글 경로, 같은 격자에 구조 규칙의 줄 수를 넣은 경로, 숫자 칸 완전 일치, 세로 병합 채움, 그리고 규칙과 도구의 머리글 줄 수가 같은 표와 다른 표다.
- 고른 후보: MinerU 4.2.2(앞선 비교에서 재지 못한 도구), 그리고 질문 2에서 머리글을 출력하고 12GB에 들고 라이선스가 맞는 Table Transformer v1.1(MIT, CVPR 2022 [12·27])과 Granite-Docling-258M(Apache-2.0, ICCV 2025 계보 [11·16]). PP-StructureV3는 머리글 정확도 근거가 없고 설치가 커서 이번에 재지 않았다.
- 조건: 문서를 넣는 실행은 모두 네트워크를 끈 컨테이너에서 했다. 모델은 제작사 공식 배포처(Hugging Face의 microsoft, ibm-granite 저장소)에서 문서 없이 미리 받았다(합 약 0.8GB). Table Transformer는 칸 글을 PDF 글자 층에서 칸 영역으로 꺼냈고, MinerU와 Granite-Docling은 쪽 그림을 모델이 읽은 글이다.
- MinerU를 재지 못했던 원인: vLLM의 확률 표본 추출기(FlashInfer)가 실행 중에 CUDA 코드를 컴파일하려다 CUDA 컴파일러가 없어 멈췄다. vLLM 설정 `VLLM_USE_FLASHINFER_SAMPLER=0`으로 PyTorch 추출기를 쓰게 하자 [28] 66개 묶음이 모두 돌았다. 새로 받은 것은 없다.

## 5. 반대 근거와 한계

- [실측] 이 조사의 숫자는 표 정답 85개(PDF 40개 문서)에 기댄다. 85개 모두 사람 확인 결과가 아직 없고, 28개는 확인을 기다린다. 머리글 없는 표 판정(질문 4)은 정답이 바뀌면 그대로 흔들린다.
- [실측] 표본 판단(HTML `th` 16개, `thead` 5개, PDF `TH` 37개, HWP 제목 칸 5개)은 한 사람이 화면으로 본 판단이다. 이중 라벨링을 하지 않았다.
- [실측] 서비스 색인 PDF의 표 수 533은 OpenDataLoader 2.2.1이 찾은 표다. 표를 놓치거나 쪼갠 경우가 섞여 있다(앞선 조사의 쪽 넘김 실측 [구조 부록 B]).
- [원문] 머리글 판별 정확도를 잰 심사 근거는 2012년 PDF 표 [21], 2021년 스프레드시트 [20], 2025년 워크숍의 영어 과학 표 [19]뿐이다. 한국어 행정 문서 표, 합친 칸이 많은 표로 잰 근거는 찾지 못했다.
- [원문] 머리글을 내는 문서 VLM(Granite-Docling)은 한국어를 지원 언어로 적지 않았다 [11]. 표 구조 모델은 그림만 보므로 언어 영향이 작을 수 있지만[판단], 잰 근거는 없다.
- [판단] 「HTML `th`는 믿을 만하다」는 학교 홈페이지 관리 화면이 만든 표에서만 확인했다. 학교 담당자가 편집기로 올린 표나 다른 기관 HTML에서 같은지는 모른다.
- [실측] 데스크탑 측정의 한계: 도구마다 기본 설정 하나로 한 번씩만 돌렸다. Table Transformer는 공식 추론 코드의 후처리(행·열 정리, 합친 칸, 머리글 행)를 줄여 다시 짰고 문턱값(표 0.7, 구조 0.5)을 고르지 않았다. 정답 표와 맞춰진 표가 54개뿐이라 표 찾기에서 진 몫이 경로 값에 섞여 있다. Granite-Docling은 Docling 2.150.0의 기본 VLM 설정(transformers 실행)으로만 돌렸다.
- 찾았지만 없음: 표 머리글에서 파일 표시·규칙·모델을 견주고 다르면 미루는 방식의 심사 근거와 공개 구현, Docling·TATR·SLANet의 머리글 분류 정확도를 따로 낸 심사 근거, 태그 PDF의 `TH` 오표시 비율을 잰 심사 논문(검색: ACL Anthology, CVF, AAAI, VLDB, ACM, 웹 검색).

## 6. 선택지와 권고

| 관점 | A. 지금 설계의 규칙만 | B. 뜻 표시가 있으면 먼저, 없으면 규칙 | C. 모델을 더해 규칙과 견주고 다르면 줄 안 만듦 | D. 모델로 바꿈 |
|---|---|---|---|---|
| 서비스 | 머리글 있는 표의 줄 수는 모두 맞음(72/72). 머리글 없는 양식 표 6개는 1줄로 봄 | A와 같고, HTML `th` 2줄 표처럼 규칙이 놓치는 표를 표시로 맞힘(1개 실측). 서비스 HTML 표 152개가 해당 | 줄을 만드는 표가 83%로 줄고 정답률은 92.0% → 96.8%. 버리는 13개 중 9개는 맞던 표 | 머리글 경로 0.95 → 0.70(Docling), 0.69(Table Transformer), 0.08(Granite-Docling). 그림을 읽는 도구는 숫자 칸도 0.13~0.77 |
| 비즈니스 | 새 도구 없음 | 새 도구 없음. 로더에서 `thead`와 HWP 제목 칸을 읽는 코드뿐 | 색인할 때 Docling 실행(CPU 초당 1.2쪽 [PDF 6]), 이미지 의존성 추가 | C와 같고 PDF 경로 전체가 바뀜 |
| 유지보수 | 머리 판단 한 곳(`table_grid.py`) | 한 곳에 「표시 우선」 분기 하나. 꾸밈 표시 목록(반복, `tblLook`, `firstRow`, 2.5의 `is_header`)을 쓰지 않는다고 적어 둠 | 신호 둘의 판 관리, 엇갈림 기록 | 모델 판이 바뀔 때마다 다시 잼 |
| 확장 | 새 형식은 칸 주소와 병합 수만 | 새 형식은 뜻 표시가 있으면 그 표시를 함께 넘김(Word의 `tblHeader`, XLSX 표 개체) | 신호를 더 붙일 수 있음 | 모델이 지원하는 언어·형식에 묶임 |

- 권고: B. 「뜻이 분명한 파일 표시(HTML `th`·`thead`, HWP·HWPX 제목 칸, DOCX `tblHeader`, XLSX 표 개체 머리 행)가 있으면 그 앞쪽 연속 행을 머리글로 쓰고, 없으면 설계의 구조 규칙을 쓴다. 규칙들이 엇갈리면 줄을 만들지 않는다(설계 그대로).」
- 이유
  - [실측] 뜻 표시는 있을 때 맞았다. HTML은 표본 21개 중 21개, HWP 제목 칸은 13개 중 12개가 0행에만 붙었고 눈으로 본 5개는 모두 실제 머리글이었다. 규칙과 다를 때도 표시가 맞았다(HTML 1개).
  - [실측·원문] 이름만 머리글인 서식 표시는 거의 모든 표에 켜져 있어 구분력이 없다 [3·5·6]. 이것들은 쓰지 않는다고 못박아야 같은 실수를 되풀이하지 않는다.
  - [원문·실측] 머리글을 내는 모델의 정답도 출판사 표시와 규칙에서 왔고 [12·13·14], 우리 표에서 잰 모델 셋 모두 규칙보다 낮았다(질문 4). 규칙과 다를 때 모델이 맞힌 표는 Docling의 머리글 없는 표 4개뿐이다. 모델이 「확실한 답」을 주지 않는다.
  - [판단] B는 지금 코드가 HTML에 하는 일(`th` 앞쪽 행)을 형식 공통으로 넓히는 것이라, 설계의 「머리 판단 한 곳」 원칙과 맞는다.
- PDF 태그의 `TH`: 쓰지 않는다. 서비스 색인 PDF에는 없고(0/533), 있는 곳(Word, PowerPoint PDF)에서는 첫 행과 첫 열에 서식대로 붙어 37개 중 11개가 틀렸다[실측]. 태그 PDF가 늘면 다시 본다.
- 버린 선택지와 이유: C는 Docling으로 하면 맞던 표 9개를 버리고 틀린 표 4개를 막고, Table Transformer로 하면 4개를 버려 1개를 막는다. 모델 실행 비용도 든다. D는 우리 표에서 규칙보다 낮고 머리글 정확도 근거가 없다. 언어 모델로 머리글을 정하는 것은 7~8B에서 F1 6~30%라 뺐다 [19].
- 남는 약점: 머리글 없는 양식 표를 규칙이 1줄로 보는 것. OpenDataLoader 표와 맞춘 머리글 없는 표 9개 중 6개는 설계의 「줄을 만들어도 되는 표」 조건이 걸렀고 3개가 남는다[실측]. 표 수가 적어 대책을 정하지 않고, 사람 확인 뒤 다시 센다.

## 7. 확신도와 다음 확인

- 확신도: 형식별 개수와 꾸밈 표시 판정은 높음(전수 셈과 표준 원문). 「뜻 표시가 맞다」는 중간(HTML·HWP 표본 26개, 한 사람 판단). 규칙 대 모델 비교는 중간(모델 셋, 표 54~76개, 사람 확인 전 정답, Table Transformer 후처리는 공식 추론 코드를 줄여 다시 짠 것).
- 다음 확인(맥북, 데스크탑 없이)
  1. 표정답확인 화면의 28표 사람 확인이 끝나면 질문 4의 표를 다시 낸다(`agree_rule_docling.py`).
  2. HTML 로더에 `thead` 행을 머리로 보는 분기를 넣었을 때 바뀌는 표 수를 센다(지금 셈으로 19개).
  3. HWP 제목 칸 표 13개가 지금 규칙 3과 같은 줄 수를 내는지 센다.
- 다음 확인(데스크탑): 이번에 재지 않은 PP-StructureV3는 머리글 정확도 근거가 생기거나 한국어 표 결과가 공개되면 잰다. Granite-Docling은 한국어를 지원하는 판이 나오면 다시 잰다.
- 다시 볼 조건: 학교가 태그 PDF를 많이 올릴 때, HWPX나 XLSX 표 개체를 쓰는 문서가 들어올 때, 머리글 판별을 한국어 표로 잰 심사 논문이 나올 때, OpenDataLoader가 태그 PDF의 `TH`를 JSON에 옮길 때.
