# 작은 모델 RAG의 여러 행 표 질문 처리 공개 기술 조사

## 요약

- [판단] 첫째로 고칠 곳은 넓히기 조건이다. 지금 실험 코드는 근거 8개 가운데 표 블록이면 질문과 상관없이 모두 넓힌다. 공개 구현은 넓히기에 조건을 단다. LlamaIndex와 Haystack은 같은 부모의 조각이 절반 넘게 검색됐을 때만 부모로 바꾼다 [21·25]. ATR은 하위 질문에서 뽑은 연산 종류와 개체 유무로 경로를 고르고, 개체 없는 집계만 SQL로 보낸다 [33]. 이 조건이 효과를 낸다는 심사 논문은 없다. 우리 기록으로 오프라인에서 먼저 잴 수 있다.
- [원문] 근거를 늘리면 거절이 준다는 결과가 심사 논문에 있다. Claude 3.5 Sonnet은 근거 없이 84.1%를 거절했지만 근거를 주자 52%로 줄었다 [4]. 우리 c13에서 답없음 거절이 24에서 18로 준 것과 같은 방향이다. 그래서 "답을 못 하면 표를 넓힌다"(Self-Route [3])는 우리에게 맞지 않는다. 답없음 질문이 모두 넓히기로 간다.
- [원문] 계산을 서버가 하는 공개 구현은 모델이 고르는 것의 폭으로 나뉜다. ① 칸과 연산 4종만 고르는 TAPAS [10·26·27] ② 정해진 연산 5종을 차례로 고르는 Chain-of-Table [31] ③ SQL이나 파이썬을 쓰게 하는 LlamaIndex·LangChain·TableRAG [18·19·23·24·30·32]. ③은 실행 안전 장치가 약하고, 판다스 엔진은 2026-04 저장소에서 지워졌다 [18]. 작은 모델은 형식을 묶으면 추론이 떨어지지만 분류형 답은 버텼다(LLaMA3-8B·Gemma-2-9B 포함) [5]. 그래서 "연산·열은 목록에서 고르고 계산은 서버"가 작은 모델에 맞는 쪽이다. 이 조합을 7~8B로 잰 심사 논문은 찾지 못했다.
- [원문] 표 전용 공개 모델은 한국어를 지원하지 않거나 중국어 중심이다(TableGPT2·TableGPT-R1 카드) [35]. 7B로 GPT-4.1 수준이라는 Table-R1도 영어 표 과제로 쟀다 [7]. 한국어 표 질의응답 데이터는 LG AI Research의 KorWikiTQ 하나를 확인했다. 그 데이터에서도 최댓값·최솟값 질문(Level5)은 EM 67.8로, 한 칸 질문(Level1) 89.6보다 크게 낮았다 [9].
- [판단] 상황별 권고(6장): 작은 표는 조건부 넓히기, 큰 표의 여러 행 질문은 서버 계산, 한 칸 질문은 지금처럼 조각과 같은 표 조각 합치기. 표 ID를 색인 메타에 넣는 일(Unstructured 방식 [34])은 어느 경우에도 쓰이는 공통 기반이다.

## 1. 배경과 조사 질문

- 왜 조사하나: 표 문항 오답 35개 가운데 여러 행 모으기·최댓값·조건 거르기 실패가 10개다(근거와 서버 줄이 모두 정상). 필요한 행이 든 청크가 검색에서 빠진 것이 7개, 정답 문서가 순위 밖인 것이 2개다 [분석 2절]. 같은 표 조각 합치기(c04)는 표 문항 +3(p 0.25)이었다. 예산 16,000자를 둔 표 전체 넓히기(c13)는 표 문항이 같은 24개였지만 표와 무관한 답없음 질문 6개에서 거절을 잃었다(24 → 18) [실험 1절]. '관련 행 먼저 옮겨 쓰기'(c11)와 '행마다 확인하기'(c12)는 움직이지 않았다.
- 정하려는 것: 위 오답을 고칠 방법 후보와 상황별 권고. 결정과 설계는 이 조사를 맡긴 설계 세션이 한다.
- 맡은 범위: 여러 행을 봐야 하는 질문, 표 전체 주기, 표 검색. 표 구조·머리글 경로와 상대 시간·과잉 거절은 다른 두 조사가 맡는다.
- 조사 질문:
  1. 계산을 모델이 아니라 서버가 하는 공개 구현은 어떻게 동작하고, 작은 모델·한국어·지저분한 머리글·실행 안전에서 무엇이 걸리나?
  2. 12GB에서 생성 모델과 함께 또는 번갈아 올릴 표 전용 공개 모델은 무엇이 있고, 근거와 한계는?
  3. 표 전체를 주되 무관한 질문에 번지지 않게 하는 공개 구현과 근거는?
  4. 표가 조각나 필요한 행이 검색에서 빠지는 문제를 다루는 공개 구현과 근거는?
  5. 한 칸 질문과 여러 행 질문을 가르는 공개 구현과, 틀렸을 때 손해를 줄이는 설계는?

## 3. 질문별 결과

### 질문 1. 계산을 서버가 하는 공개 구현

모델이 고르는 폭이 좁을수록 서버가 맡는 몫이 크다. 공개 구현을 그 폭으로 늘어놓으면 이렇다.

| 모델이 고르는 것 | 구현 | 서버(코드)가 하는 일 | 실패할 때 |
|---|---|---|---|
| 칸 + 연산 4종(NONE·COUNT·SUM·AVERAGE) | TAPAS 모델, Haystack 1.x `TableReader` [10·26], transformers 표 질의 파이프라인 [27] | Haystack `_aggregate_answers`: COUNT는 칸 수, SUM·AVERAGE는 칸에서 숫자와 단위를 읽어 모두 숫자이고 단위가 같을 때만 계산 | 계산 못 하면 `"SUM > a, b"` 글을 그대로 돌려준다. transformers는 계산하지 않고 늘 이 글을 준다 |
| 연산 5종(열 더하기·행 고르기·열 고르기·묶기·정렬)을 정해진 순서로 | Chain-of-Table 공식 코드 [31] | 고른 행·열을 판다스로 자르고, 묶기의 셈은 코드가 한다(`group_column_contents.count(v)`) | 모델 답에서 허용된 연산을 못 찾으면 그대로 끝낸다(`<END>`) |
| 하위 질문의 연산 종류(count·aggregate·sort·arithmetic·compare)와 개체 | ATR `HeuristicRouter` [1·33] | 개체가 있으면 값 묶기 뒤 제약 SQL(HYBRID), 개체 없이 집계면 SQL | 검증에서 떨어지면 다음 경로로 올라간다 |
| SQL 문 | LlamaIndex `NLSQLRetriever` [19], LangChain `create_sql_query_chain` [23], Huawei TableRAG [2·32] | DB에서 실행 | LlamaIndex는 오류 글을 결과로 돌려준다(재시도 없음) |
| 파이썬·판다스 코드 | LlamaIndex `PandasQueryEngine` [18], LangChain 판다스 에이전트 [24], Google TableRAG [30] | `eval`·`exec` | 오류 글을 답으로 돌려준다 |

- [원문] 실행 안전 장치는 SQL·코드 쪽이 약하다.
  - LlamaIndex `SQLDatabase.run_sql`은 받은 SQL을 `engine.begin()` 안에서 그대로 실행한다. SELECT만 허용하는 검사가 없고, 파서 주석은 "# assume that it's a valid SQL query"다 [19].
  - LangChain은 보안 안내에 "limit permissions to read and scope to the tables that are needed"라고 적어 DB 권한으로 막으라고 한다 [23].
  - 판다스 경로는 더 약하다. LlamaIndex는 가져오기·밑줄 속성·위험 입출력을 AST로 막고 30초 제한을 두지만 [18], 이 패키지를 2026-04-02에 지원 중단하고 이튿날 저장소에서 지웠다(README "This package is deprecated and no longer maintained.") [18]. LangChain 판다스 에이전트는 `allow_dangerous_code=True`를 직접 켜야 돌고, 켜지 않으면 "requires a specially sandboxed environment to be safely used"라는 오류를 낸다 [24]. Google TableRAG는 `python_repl_ast`로 격리나 시간 제한 없이 `exec`한다 [30].
- [원문] 한국어 열 이름에서 바로 걸리는 구현이 있다. Huawei TableRAG는 표를 MySQL에 넣을 때 열 이름을 `re.sub(r'[^a-zA-Z0-9_]', '_', ...)`로 바꾼다. 그래서 한글 열 이름은 모두 `_`가 되고, 중복 처리 뒤 `_`, `__1`처럼 뜻 없는 이름이 된다 [32]. 값도 `pd.to_numeric`으로 열 전체가 숫자로 바뀔 때만 숫자로 다룬다. `160명`, `41.6:1`처럼 단위가 붙은 칸은 글로 남는다 [32]. 글로 남은 열에 MAX를 쓰면 숫자가 아니라 글자 순서로 비교한다.
- [원문] 지저분한 머리글에서의 동작:
  - LlamaIndex Markdown 파서는 행마다 칸 수가 다르면 데이터프레임을 만들지 않고 원문을 그대로 둔다(`perfect_table=False`) [20].
  - Huawei TableRAG는 빈 첫 열 이름을 `No`로, 겹친 이름에는 `_1`, `_2`를 붙인다 [32]. 우리 오답에서 9개 열이 모두 `정밀안전진단 결과`가 된 표라면 `정밀안전진단 결과_1`~`_8`이 된다. 열은 갈리지만 뜻은 잃는다 [판단].
  - Haystack `TableReader`는 입력이 길면 행을 지워 맞춘다("the table will be truncated by removing rows until the input size fits the model", 기본 256토큰) [26]. 여러 행 질문에서 정답 행이 조용히 빠질 수 있다 [판단].
- [원문] 작은 모델에 맞는 쪽은 "고르기만 모델"이다. 형식을 묶은 출력에서 추론 과제는 성능이 떨어졌고("we observe a significant decline in LLMs’ reasoning abilities under format restrictions"), 묶음이 셀수록 더 떨어졌다. 분류 과제에서는 JSON 모드가 비슷하거나 더 나았다. 저자들은 그 이유를 "constraining possible answers resulted in reducing errors in answer selection"으로 봤다. 실험 모델에 LLaMA3-8B-Instruct와 Gemma-2-9B-Instruct가 있다 [5]. 같은 논문에서 GPT-3.5는 JSON 모드에서 100% 답 키를 이유 키보다 먼저 써서 풀이 없이 답했다. 키 순서가 결과를 바꾼다 [5].
- [원문] 우리 환경에서 형식을 묶는 길은 이미 있다. Ollama는 `format`에 JSON 스키마를 받는다 [28]. v0.40.16 코드는 스키마를 llama-server의 `json_schema`로 넘기고, llama-server가 이를 문법(GBNF)으로 바꿔 생성 단계에서 토큰을 묶는다 [28·29]. 모델의 도구 호출 지원과 무관하게 샘플러에서 걸린다 [판단, A.X 4.0 Light로 확인 안 함]. llama.cpp 문서의 한계: 지원하지 않는 스키마 기능은 "skipped silently", `number`의 최솟값·최댓값은 쓸 수 없고 `integer`만 된다, `if/then/else`·`not`은 안 된다 [29]. `enum`은 된다(`json-schema-to-grammar.cpp`의 enum 처리) [29]. 그래서 열 이름을 질문마다 그 표의 실제 열 이름 `enum`으로 넣을 수 있다 [판단].
- [원문] 7~10B 근거: 7B에서 Text-to-SQL은 F1 37.42로 표 전체(42.59)보다 낮았다 [처리 3]. 작은 모델은 코드를 짜서 푸는 방식에서 크게 나빴다 [처리 9]. Arctic-Text2SQL-R1 7B는 정리된 DB 벤치마크에서 "our 7B model outperforms prior 70B-class systems"였다 [12]. 우리처럼 PDF에서 뽑은 지저분한 표가 아니다. Huawei TableRAG(가장 작은 모델 72B) [2], ATR(가장 작은 모델 70B) [1], Weaver(GPT-4o-mini 이상) [14]는 7~10B 근거가 없다.

### 질문 2. 표 전용 공개 모델

### 질문 3. 표 전체를 주되 무관한 질문에 번지지 않게

먼저 우리 c13이 넓힌 조건이다. `_expand_tables_within_budget`는 근거 8개를 순위대로 돌며, 앞뒤 청크가 같은 표 머리이면 모두 넓히고 예산(16,000자)만 본다. 질문 종류나 그 표의 순위는 보지 않는다(`feat/#259-table-experiment`의 `ai-server/main.py`).

공개 구현이 넓힐지 정하는 방식:

| 정하는 방식 | 구현 | 효과 근거 |
|---|---|---|
| 같은 부모의 자식이 절반 넘게 검색됐을 때만 | LlamaIndex `AutoMergingRetriever`(`simple_ratio_thresh` 0.5) [21], Haystack `AutoMergingRetriever`(`threshold` 0.5, 0과 1 사이만 허용) [25] | 근거 없음(구현 사례만) |
| 표 조각이 맞으면 언제나(표가 1만 자 이하일 때) | AWS Bedrock 기본 동작 [처리 23] | 근거 없음(제품 기본값) |
| 모델에게 앞·뒤 문맥이 더 필요한지 묻기(PREVIOUS·NEXT·NONE) | LlamaIndex `AutoPrevNextNodePostprocessor` [21] | 근거 없음 |
| 질문의 연산이 집계이고 표 전체 보기 표시가 없을 때만 SQL | ATR `HeuristicRouter` Rule 3 [33] | ATR 전체 효과는 EMNLP 2026 [1], 이 규칙만 떼어 잰 결과 없음 |
| 모델이 "답할 수 없음"이라 하면 전체 문맥으로 | Self-Route [3] | Gemini-1.5-Pro는 82%가 첫 단계에서 끝났고 비용을 65% 줄였다(긴 글 과제, 표 아님) [3] |

- [원문] Self-Route는 "LLMs are well-calibrated in predicting whether a query is answerable given provided context"를 전제로 한다 [3]. 반대 근거가 있다. 근거를 늘리면 모델이 덜 거절한다("the introduction of additional context paradoxically reduces the model’s ability to abstain") [4]. 수치는 Claude 3.5 Sonnet 84.1% → 52%, Gemini 1.5 Pro 100% → 18.6%다 [4]. 작은 모델(Llama 3.1, Mistral 3, Gemma 2)은 문맥이 충분해도 지어내거나 거절하는 일이 잦았다 [4].
- [판단] 우리 답없음 질문은 첫 단계에서 "답할 수 없음"이 나오는 것이 맞는 동작이다. Self-Route를 따르면 이 질문이 모두 넓히기로 간다. c13에서 거절을 잃은 6문항이 바로 그 경로다. 넓히기 조건은 "모델이 답을 못 했다"가 아니라 질문과 검색 결과로 정해야 한다.
- [원문] 넓힌 뒤 거절을 지키는 장치: Sufficient Context(ICLR 2025)는 문맥이 충분한지 따로 판정하는 모델(FLAMe 24B)의 신호와 모델의 자신감을 합쳐 답할지 정한다. 답한 것 중 맞은 비율이 2~10% 올랐다(Gemini, GPT, Gemma). 가장 작은 생성 모델은 Gemma 27B다 [4].
- [원문] 넓힌 표를 줄이는 방식:
  - 질문에 맞는 열·행만 남기기: H-STAR [처리 6], TabSQLify(SQL로 하위 표를 만들어 줌, NAACL 2024, gpt-3.5로 WikiTQ 64.7%) [16], Google TableRAG(열 이름과 칸 값 검색) [30].
  - 반대 근거: 7B에서는 부분만 준 쪽이 표 전체보다 낮았다(20.54 대 42.59) [처리 3]. CABINET(ICLR 2024)은 "Such a question-conditioned hard decomposition of table is sub-optimal as the subsequent QA model cannot correct the error made during decomposition if relevant information is not selected"라고 적고, 지우지 않고 관련 부분에 무게를 주는 방식을 냈다 [11]. 무게 주기는 모델 내부를 바꾸는 학습형이라 Ollama 서빙에는 바로 못 쓴다 [판단].
- [판단] 넓힌 표를 줄일 때는 "조건에 맞는 행만 남기기"를 서버가 확정적으로 할 수 있을 때(열 이름과 값이 깨끗하고 조건이 비교식일 때)만 쓰고, 그렇지 않으면 줄이지 않는 편이 맞다. 줄이다 정답 행을 빼면 모델이 되돌릴 수 없다 [11].

### 질문 4. 표가 조각나 필요한 행이 검색에서 빠지는 문제

- [원문] 표 하나에 ID를 붙여 조각을 묶는 구현: Unstructured는 표를 나눌 때 `table_id = str(uuid.uuid4())`를 그 표의 모든 조각에 같게 넣고, `chunk_index`와 둘째 조각부터 `is_continuation=True`를 단다. `repeat_table_headers` 기본값은 참이고, HTML에서 머리 행으로 표시된 행이 이어지는 만큼을 머리로 세어 여러 줄 머리글도 되풀이한다 [34]. 우리 실험 코드는 표 ID 칸이 없어 "같은 문서 + 이어지는 청크 번호 + 같은 표 머리"로 같은 표를 추정한다(`_table_neighbor_pieces` 주석). 머리가 다르게 잘린 조각이나 중간에 글이 낀 조각은 놓친다 [판단].
- [원문] 표 요약을 검색 키로, 표 전체를 한 노드로: LlamaIndex 요소 파서는 표마다 모델에게 요약·제목·열 설명을 구조화 출력(`TableOutput`)으로 받는다. 이를 검색용 `IndexNode`로 색인하고, 같은 ID의 `TextNode`에 요약과 표 전체 마크다운을 둔다. 표를 쪼개지 않는다. 구조화 출력이 검증에 실패하면 요약 글만 받고 열 설명은 비운다 [20]. Google Vertex AI Search의 표 주석도 같은 방향이다 [처리 28].
- [원문] 행은 보조 색인으로: LlamaIndex `NLSQLRetriever`는 표마다 행 검색기(`rows_retrievers`)와 열 값 검색기(`cols_retrievers`)를 따로 두고, 질문에 맞는 행과 값을 SQL 프롬프트에 "Here are some relevant example rows"로 붙인다 [19]. ATR은 조각 색인, 열 색인, 칸·행 색인, 관계형 표를 따로 두고, 조각이 맞으면 조각에서 표로 가는 연결(chunk-to-table mapping)로 표 스키마를 되살린다 [1·33].
- [원문] 이웃 조각 창: Haystack `SentenceWindowRetriever`는 `source_id`·`split_id` 메타로 앞뒤 `window_size`(기본 3)개를 가져온다 [25]. LlamaIndex `PrevNextNodePostprocessor`는 기본 다음 조각 1개다 [21]. 표 경계를 모르는 창이라 표 밖 글까지 가져온다 [판단].
- [원문] 값 묶기(value linking): ATR은 질문 속 표현이 저장된 값과 달라 SQL이 행을 놓치는 일을 "soft-retrieval / hard-execution gap"이라 부르고, 칸 색인의 실제 값으로 먼저 묶는다 [1]. 값을 바꿔 쓰는 단계와 부분 일치 단계를 끄자 HybridQA F1이 2.3점 떨어졌고, 저자들은 이것이 값 묶기 전체 효과의 약 85%라고 적었다(Gemini 2.5 Flash) [1]. Google TableRAG도 범주형 열의 (열 이름, 칸 값) 쌍을 빈도순으로 색인한다 [30].
- [판단] 정답 문서가 순위 밖인 2문항(합친 칸 때문에 계열 이름과 학과 이름이 한 청크 글에 함께 없음)은 표 요약 키나 행 보조 색인으로 잡힐 수 있다. 합친 칸 값을 행마다 채우는 일은 「표 구조와 머리글 경로」 조사 몫이라 여기서는 다루지 않았다.
- [판단] 효과의 근거: 위 방식이 답 정확도를 얼마나 바꾸는지 잰 2024~2026 심사 논문은 찾지 못했다. 모두 구현 사례다.

### 질문 5. 한 칸 질문과 여러 행 질문 가르기

| 방식 | 구현·근거 | 확인한 것 |
|---|---|---|
| 작은 분류 모델 | Adaptive-RAG(NAACL 2024) [6] | T5-Large(770M) 분류기로 검색 안 함·한 번·여러 번을 고른다. 분류 정확도는 54.52%뿐이었지만 QA F1은 46.94로 비교 방법보다 나았다. 여러 번을 한 번으로 31%, 검색 안 함을 한 번으로 47% 잘못 갈랐다 [6] |
| 큰 모델 판정을 작은 분류기로 옮기기 | ATR `LearnedRouter` [1·33] | DistilBERT(66M)가 LLM 판정의 98.6%를 따라 했고 하위 질문마다 약 1ms [1] |
| 생성 모델에게 고르게 하기 | LlamaIndex `RouterQueryEngine`·`LLMSingleSelector` [22], Haystack `LLMMessagesRouter` [25], ATR `LLMRouter` [33] | LlamaIndex는 번호 목록에서 고르게 하고 JSON이 깨지면 YAML로 다시 읽는다. Haystack은 어느 정규식에도 안 맞으면 `unmatched`로 따로 내보낸다. ATR은 파싱에 실패하면 RETRIEVE로 간다 |
| 규칙 | ATR `HeuristicRouter` [33] | 질문 원문이 아니라 분해기가 낸 연산 칸(`expected_operator`)으로 가른다. 한 칸 조회를 값싼 경로로 바로 보내는 규칙은 dev에서 손해라 기본으로 꺼 뒀다(코드 주석) |

- [원문] 틀렸을 때의 손해를 줄이는 장치가 분류 정확도보다 중요했다. ATR에서 실패하면 다음 경로로 올라가는 장치(escalation)를 빼자 F1이 54.02에서 18.32로 떨어졌다(−35.70). 경로 판정을 없애고 HYBRID 하나로 보내면 −8.26이었다 [1].
- [판단] Adaptive-RAG에서 분류가 절반 가까이 틀려도 전체가 나아진 것은, 틀린 쪽의 손해가 작게 짜여 있기 때문으로 본다(복잡한 쪽으로 잘못 보내면 시간만 더 든다). 우리도 여러 행 경로가 틀렸을 때 한 칸 질문에 줄 손해(답없음 거절 감소, 긴 근거)를 작게 만드는 설계가 먼저다.

### 4.5 작은 모델·한국어 근거가 있는 후보

- 7~10B 근거가 있는 것: 1·18의 방향(분류형 구조화 출력, LLaMA3-8B·Gemma-2-9B [5]), 3(7B Text-to-SQL [처리 3], 7B SQL 전용 모델 [12]), 4·5(작은 모델에 불리하다는 반대 근거 [처리 9]), 13(7B에서 부분 < 전체라는 반대 근거 [처리 3]), 표 전용 모델 Table-R1·TableLLM·TableLlama [7·8·13].

## 6. 반대 근거와 한계

- [원문] 근거를 늘리면 거절이 준다 [4]. 표 전체 주기, 넓히기, 표 요약 노드처럼 근거를 늘리는 후보(8~10·15·16)는 모두 이 위험을 진다. 우리 c13이 실제로 겪었다 [실험].
- [원문] 형식을 묶으면 추론이 떨어진다 [5]. 후보 1·18에서 모델에게 풀이를 시키지 않고 "고르기"만 시키는 이유다. 고르기에 풀이가 필요한 질문(조건이 두 개 넘는 경우 등)은 이 이점이 줄 수 있다 [판단].
- [원문] 작은 모델의 코드·SQL 반대 근거: 7B에서 Text-to-SQL은 표 전체보다 낮았고 [처리 3], 코드 방식은 크게 나빴다 [처리 9]. 7B SQL 전용 모델의 좋은 결과 [12]는 정리된 DB 벤치마크에서 잰 것이다.
- [원문] 줄이기의 반대 근거: 지운 행은 되돌릴 수 없다 [11]. 7B에서 부분만 준 쪽이 낮았다 [처리 3].
- [원문] 분류가 자주 틀린다: T5-Large 분류기 정확도가 54.52%였다 [6].
- [판단] 평가 설정이 우리와 다르다.
  - 서버 계산·경로 나누기 논문(ATR, Huawei TableRAG, Weaver, H-STAR)은 모두 70B 이상이나 상용 모델로 쟀다. 7~8B에서 같은 이득이 난다는 근거가 없다.
  - 표 데이터는 위키 표(WTQ, HybridQA), 금융 표(TAT-QA)다. PDF에서 뽑아 머리글이 깨진 학교 표가 아니다. ST-Raptor만 반구조 표를 다루지만 GPU 160GB 설정이다 [17].
  - 한국어 근거는 2022년 BERT 모델 하나다 [9].
- [판단] "널리 쓰인다"의 한계: 넓히기 비율 기준(0.5), 표 ID 메타, 표 요약 노드는 프레임워크 기본값일 뿐 답 정확도를 잰 결과가 공개돼 있지 않다.
- [판단] 우리 데이터의 한계: 여러 행 실패는 10문항이다. 처치 하나의 효과가 ±3문항이면 짝 비교로 가르기 어렵다 [실험 2-1]. 연산 고르기 정답률처럼 생성 없이 잴 수 있는 중간 지표를 먼저 둔다.
- 찾았지만 근거로 쓰지 못한 것: 게재처를 확인하지 못한 TAPEX·StructLM·TableGPT2 기술 보고서, 개인·커뮤니티 저장소(부록 A).
- 찾았지만 없음: 7~8B 생성 모델로 "연산 목록 고르기 + 서버 계산"을 잰 심사 논문, 넓히기 조건(비율·순위·질문 유형)의 효과를 잰 심사 논문, 2024~2026 한국어 표 RAG 심사 논문. 검색한 곳: ACL Anthology 검색 결과, GitHub 주제 검색, OpenAlex.

- 권고 [판단]:
  1. 가(조건부 넓히기)를 먼저 한다. c13 실행 기록으로 오프라인에서 먼저 센다: 거절을 잃은 6문항이 조건에 걸러지는지, 마·가1 17문항은 여전히 넓혀지는지. 결과가 좋으면 데스크탑에서 c13 조건부 판으로 다시 잰다.
  2. 표 ID 메타(후보 14)를 색인 단계에 넣는다. 머리글 경로를 고치는 작업과 같은 색인 재생성에 실을 수 있다.
  3. 나(서버 계산)는 머리글 결함을 고친 뒤 좁게 시험한다. 연산 목록은 조회·최댓값·최솟값·세기·합계·목록·거르기로 두고, 열 이름은 그 표의 실제 열 이름 `enum`으로 묶는다. 생성 없이 연산·열 고르기 정답률을 먼저 잰다.
- 이유:
  - [원문] 넓히기의 부작용은 근거를 늘리면 거절이 준다는 일반 현상이다 [4]. 공개 구현은 넓히기에 조건을 단다 [21·25·33].
  - [원문] 작은 모델에서 형식을 묶은 출력은 고르기 과제에서 버텼고 추론 과제에서 떨어졌다 [5]. 계산을 코드가 맡으면 모델은 고르기만 한다.
  - [원문] 실패하면 다른 경로로 가는 장치를 빼자 큰 손해가 났다 [1]. 서버 계산은 실패를 코드가 알아챌 수 있다(열을 못 찾음, 결과가 빔).
  - [실측, 앞선 기록] 프롬프트 지시(c11·c12)는 여러 행 오답을 움직이지 않았다 [실험].
- 버린 선택지와 이유:
  - 판다스 코드 실행(후보 4): 작은 모델 반대 근거 [처리 9], LlamaIndex 판 지원 중단 [18], 실행 격리 부담.
  - 답 못 하면 넓히기(후보 11): 답없음 질문이 모두 넓혀진다 [3·4].
  - 표 전용 모델(라): 한국어 지원이 없거나 중국어 중심이다 [35]. 12GB에서 두 번째 7B 모델의 배치도 실측이 필요하다.
  - Chain-of-Table·Weaver(후보 5·14번 논문): 질문당 호출이 여러 번이고 근거가 큰 모델뿐이다.
  - 넓힌 표 줄이기(후보 13): 7B 반대 근거 [처리 3]와 되돌릴 수 없는 손실 [11]. 큰 표에서 서버 계산이 실패할 때의 보조로만.

## 8. 확신도와 다음 확인

- 확신도: 중간. "넓히기에 조건을 단다"는 공개 구현이 같은 방향이고 거절 감소의 원리가 심사 논문에 있다 [4]. 조건의 효과와 서버 계산의 효과는 7~8B·한국어로 잰 근거가 없어 우리 측정이 결정한다.
- 다음 확인:
  1. c13 실행 기록으로 후보 8·9의 조건이 거절을 잃은 6문항과 여러 행 17문항을 어떻게 가르는지 센다(데스크탑 없이).
  2. 표 질문 묶음 47문항에 "한 칸/여러 행"과 연산 라벨을 단다. 후보 18의 판정 정확도와 후보 1의 열 고르기 정답률을 A.X 4.0 Light로 잰다(생성 없이, 데스크탑).
  3. Ollama에서 A.X 4.0 Light가 한글 `enum` 스키마를 지키는지, 스키마를 쓸 때 응답 시간이 얼마나 느는지 잰다.
  4. 표 ID 메타를 넣은 색인에서 c04가 모으는 조각이 지금 추정 방식과 얼마나 다른지 색인만으로 센다.
- 다시 볼 조건: 7~10B로 서버 계산이나 넓히기 조건을 잰 심사 논문이 나오면, 한국어 LLM 표 질의응답 심사 논문이 나오면, 4,000자를 넘는 표 문항이 10개 넘게 생기면, 운영 서빙을 클라우드로 옮겨 VRAM 제약이 바뀌면(ADR-0030).
