# 다단 머리글과 합친 칸이 있는 표의 직렬화 방법 조사

## 요약

- [실측] 우리 PDF 표 74개에서 머리 줄 수 규칙 하나만 바꿔도 머리글 경로 일치율이 크게 오른다. 지금 서버가 보는 마크다운은 0.381이다. 같은 OpenDataLoader JSON 칸에 「왼쪽 위 칸이 아래로 k줄 병합이면 머리 k줄」 규칙(`TableGrid` 규칙 3)을 쓰면 0.966, 머리 줄 수를 1로 두면 0.654다. Docling은 0.702였다(부록 B).
- [원문] 공개 구현 대부분은 같은 순서로 일한다. 칸마다 머리글 표시를 받아 앞쪽 연속 행을 머리 블록으로 잡는다. 열 이름은 위에서 아래로 칸 글을 잇는다. 합친 칸의 값은 덮인 칸마다 되풀이한다. Docling, RAGFlow, Unstructured, pandas, Textractor가 이렇다 [1·4·5·8·19]. 머리글 표시는 표 구조 모델의 라벨이나 HTML `th`에서 오고, 잇는 글자는 구현마다 다르다(` - `, `.`, ` | `, 빈 글자).
- [원문] 줄 모양에 대한 심사 근거는 하나가 가장 직접적이다. 계층 머리글을 열마다 한 이름으로 편 표가 HTML 계층 머리글보다 나았다(HiTab, Qwen2-72B, EM 73.78 대 67.89) [35]. 칸마다 한 줄과 행마다 한 줄을 견준 심사 근거, 7B급 모델과 한국어 표 근거는 찾지 못했다.
- [판단] 권고: 머리글 판단을 마크다운이 아니라 격자(`TableGrid`)에서 한 번만 한다. PDF도 JSON 칸으로 격자를 채워 HWP, HTML과 같은 규칙을 쓴다. 빈칸과 '-'는 지우지 않고 자리표시로 남긴다. 머리 줄을 가리지 못한 표는 줄을 만들지 않는다. 행 이름은 낱말 목록 대신 구조로 고른다(3장 질문 4, 6장).
- [실측·판단] 과제의 전제 하나를 고친다. HWP와 HWPX는 머리글 구조를 아는 형식이 아니다. 칸의 「제목 칸」 표시가 있지만 수집 HWP 표 2,315개 중 15개만 썼고, HWPX 6개 파일 칸 446개는 모두 꺼져 있었다. HWP도 PDF JSON처럼 병합 정보만 아는 표로 다뤄야 한다.

## 1. 배경과 조사 질문

- 왜 조사하나: 2026-11-14 표 질문 오답 35개 중 5개는 서버의 「표 검색 정보」 줄 결함이 직접 원인이었고, 결함 줄이 24문항의 프롬프트에 있었다(`docs/rag/m2/표-질문-오답-분석-20261114.md`, 실험 브랜치). 결함은 네 모양이다. 2단 머리글의 아래 칸 이름을 버림, '-'와 빈칸을 지워 값 위치가 밀림, 머리글 행을 데이터 행으로 읽음, 합친 칸 글을 되풀이함.
- 정하려는 것: 이 결함을 고치는 설계 세션이 고를 후보와 근거. 한 표나 한 문서가 아니라 PDF, HWP, HWPX, HTML, DOCX에 함께 통하는 방법이어야 한다.
- 지금 서버가 하는 일(`ai-server/main.py`, 커밋 83a13c3 기준)
  - `_parse_markdown_table`: 구분선 앞 줄을 머리 줄로 본다. 마크다운은 머리 줄을 보통 한 줄만 가진다.
  - `_is_probable_subheader_row`: 머리 줄에 빈 칸이 있을 때만, 본문 첫 줄이 숫자 없는 짧은 칸 둘 이상이면 머리 보강 줄로 본다.
  - `_compose_column_labels`: 머리 줄들의 칸을 공백으로 잇는다.
  - `_build_row_summary_fact`: 빈칸과 '-'(`_is_empty_table_cell`)는 건너뛴다.
  - `_select_row_subject`: 열 이름에 '모집단위, 학과, 항목, 요소, 구분, 전형, 프로젝트 유형'이 든 열을 행 이름으로 고른다.
  - 꺼져 있는 두 번째 길(`OPENDATALOADER_JSON_TABLE_FACTS_ENABLED`, `ai-server/opendataloader_contract_adapter.py`): JSON 칸의 병합을 채운 뒤 `_table_header_row_count`로 머리 줄 수를 정하고 열 경로를 ` > `로 잇는다.
  - HWP, HWPX, HTML, DOCX 로더는 `format_loaders/table_grid.py`의 `render_table`로 여러 머리 줄을 한 줄로 합친 마크다운을 낸다(규칙 3). PDF는 이 길을 타지 않는다.
- 조사 질문:
  1. 공개 RAG와 문서 파이프라인은 표를 모델에 줄 글로 바꿀 때 다단 머리글, 합친 칸, 빈칸을 어떻게 처리하나
  2. 머리글 행의 수와 계층을 판별하는 공개 기술은 무엇인가(구조 규칙, 학습 모델, 스프레드시트와 CSV)
  3. PDF에서 칸 구조를 얻는 길(JSON 병합 정보 + 규칙, 구조 모델 + PDF 글자, 도구 교체) 중 무엇이 나은가
  4. 낱말 목록 없이 행 이름이 되는 열을 고르는 방법은 무엇인가
  5. 다단 머리글 표에서 줄 모양(행마다 한 줄, 칸마다 한 줄, HTML, 펴진 머리글)의 심사 근거는 무엇인가

- [원문] 머리 줄을 가리는 근거는 셋으로 나뉜다. 모델이 칸마다 붙인 라벨(Docling, RAGFlow PDF, Unstructured PDF, Textract, Azure), HTML `th`와 `thead`(pandas, Unstructured, RAGFlow HTML), 그리고 첫 줄 고정(Marker, LlamaIndex, LangChain, Kotaemon). 글자 규칙만으로 머리 줄을 정하는 구현은 RAGFlow의 「숫자 칸 빼고 세기」 보조 규칙 하나였다 [4].
- [원문] 합친 칸 처리는 둘로 갈린다. 덮인 칸마다 값을 되풀이하는 쪽(pandas, Docling 격자, RAGFlow 본문, HiTab의 TaPas 입력 [31])과 첫 칸에만 두는 쪽(Marker, Textractor 기본)이다. RAGFlow만 「본문 병합은 되풀이, 머리 병합은 머리 블록 안에서만」으로 나눠 적었다 [4].
- [원문] 빈칸이나 '-'를 지우는 구현은 찾지 못했다. 빈 값을 `열 = `이나 `열: `로 남기거나(Docling 트리플렛, LangChain) 자리표시 글을 넣게 한다(Textractor) [1·8·15]. 우리 서버만 빈칸을 건너뛰어 값 위치가 밀린다.
- [판단] 우리 결함 ③(머리 행을 데이터로 읽음)은 Textractor 기본값과 Marker가 같은 모양으로 갖고 있다. 둘째 머리 줄이 첫 데이터 행이 된다.

### 질문 2. 머리 줄의 수와 계층을 판별하는 공개 기술

**구조 규칙**

- [원문] PubTables-1M(CVPR 2022, Microsoft)의 정규화 알고리즘은 병합 범위만으로 머리 블록을 넓힌다. 첫 행이 빈 칸으로 시작하면 첫 행을 머리에 넣고, 머리 블록의 모든 열에 그 열 하나만 덮는 온전한 칸이 생길 때까지 다음 행을 더한다("while every column in the column header does not have at least one complete cell that only spans that column"). 같은 알고리즘이 구역 행(머리 아래에서 첫 열 한 칸만 찬 행)과 행 머리 열(머리 아래 첫 열에 병합 칸이나 빈칸이 있으면)도 정한다 [26]. 이 규칙은 머리글이 나무 구조이고 본문 열마다 고유한 잎 머리 칸이 있다는 가정에 기댄다. 논문은 이 가정이 맞는 표가 Wang의 연구에서 97%였다고 적었다 [26].
- [원문] WHATWG HTML 표준은 `th`의 범위가 지정되지 않으면 그 칸이 걸친 행들에 데이터 칸이 없을 때 열 머리글로 본다. 데이터 칸의 머리글은 같은 행 왼쪽과 같은 열 위쪽으로 훑어 모은다 [23]. 열 경로와 행 경로를 함께 만드는 표준 알고리즘이다.
- [원문] CSV 도구는 값의 종류로 첫 줄이 머리인지 정한다. Python `csv.Sniffer.has_header`는 둘째 줄부터 숫자가 오거나 글 길이가 다르면 머리로 보고, 문서가 이 방법을 "a rough heuristic"이라고 적는다 [21]. DuckDB는 첫 줄의 값 종류가 나머지 줄과 다르면 머리로 보고, 모든 열이 글이면 가리지 못한다고 적는다 [22].
- [실측] 우리 코드의 두 규칙. `TableGrid` 규칙 3은 왼쪽 위 칸의 세로 병합 수를 머리 줄 수로 본다. JSON 어댑터의 `_table_header_row_count`는 숫자 값이 없고 첫 칸이 비었거나 앞 줄과 같은 줄을 최대 3줄까지 머리로 더한다. 우리 PDF 표 74개에서 둘은 머리 줄 수를 71개와 70개 맞혔고, PubTables-1M 규칙은 56개였다(부록 B).
- [실측] PubTables-1M 규칙이 우리 표에서 머리를 지나치게 늘린 까닭은 맨 윗줄의 두 열짜리 병합 칸이다. 행 이름 두 열 위에 걸친 「구분」 칸이나, 값과 단위 두 열 위에 걸친 칸 아래에는 그 열 하나만 덮는 머리 칸이 없어 본문 행까지 머리로 끌어들인다. 영어 과학 논문 표에서 만든 가정이 우리 표에 그대로 맞지 않는다.

**칸의 머리글 표시(작성자가 넣은 구조)**

- [원문] Azure 문서 분석은 칸 종류를 `columnHeader`, `rowHeader`, `stubHead`, `description`, `content`로 준다 [10]. Textract는 `COLUMN_HEADER`, `TABLE_TITLE`, `TABLE_FOOTER`, `TABLE_SECTION_TITLE`, `TABLE_SUMMARY`를 준다 [24].
- [실측] HWP와 HWPX에도 칸의 제목 칸 표시가 있지만 학교 문서는 거의 쓰지 않는다. HWPX 6개 파일의 칸 446개에서 `hp:tc`의 `header` 속성은 모두 `"0"`이었다. 우리 HWPX 로더 주석에는 수집 HWP 표 2,315개 중 15개만 이 표시를 썼다는 실측이 있다(`format_loaders/hwpx.py` 머리 설명). 그래서 HWP 경로는 이미 이 표시 대신 규칙 3을 쓴다.

### 질문 4. 행 이름이 되는 열을 고르는 방법

- [원문] 가장 오래된 공개 규칙은 「왼쪽부터 보며 숫자나 날짜가 아닌 첫 열」이다. Google의 웹 표 연구에서 이 규칙이 주제 열을 83% 맞혔고, 고유 값 비율, 숫자 비율, 글자 수, 열 위치 같은 특징 25개로 학습한 SVM이 94%였다(PVLDB 2011) [30]. 영어 웹 표, 2011년 자료라 숫자는 옮기지 않는다.
- [원문] 구조로 행 머리 열을 정하는 규칙도 있다. PubTables-1M은 머리 아래 첫 열에 병합 칸이나 빈칸이 있으면 그 열을 행 머리로 넣는다 [26]. WHATWG는 `th`의 범위가 행이면 행 머리로 보고 데이터 칸에서 왼쪽으로 훑어 모은다 [23]. Docling 모델은 `rhed`, Azure는 `rowHeader`를 칸에 붙인다 [3·10].
- [원문] 구역 행(한 칸만 찬 행)은 여러 구현이 따로 다룬다. PubTables-1M의 「projected row header」 [26], Pytheas의 구역 머리 줄(첫 열에서만) [29], 우리 JSON 어댑터의 `_is_table_group_row`가 같은 개념이다.
- [원문] 공개 RAG 구현은 대부분 행 이름을 따로 고르지 않는다. 고르는 곳은 Docling 트리플렛(늘 첫 열)과 우리 JSON 어댑터(첫 칸)뿐이었다 [1].
- [원문] 모델이 행 머리를 열 머리보다 덜 본다는 관찰이 있다. GPT-3.5는 같은 형식에서 열 머리에 더 주목했고 답이 행 머리 계층에 기대는 문항에서 점수가 떨어졌다(EMNLP 2023) [32]. 행 이름을 줄 앞에 분명히 적는 쪽의 근거로 쓴다. 2023년 모델이다.
- [판단] 낱말 목록 없이 고르는 순서 제안: (1) 행 머리 표시(`th scope=row`, `rhed`)가 있으면 그 열들 (2) 없으면 머리 아래에서 세로 병합이 있는 왼쪽 열들과 숫자나 날짜가 아닌 첫 열을 왼쪽부터 이어 행 경로로 (3) 구역 행은 경로 맨 앞에. 한 표에만 맞는 낱말이 없어 다른 형식과 문서에도 통한다. 잰 적은 없다(7장).

- [원문] 「계층 머리를 열마다 한 이름으로 편 단층 표」가 「계층을 그대로 둔 HTML」보다 나았다는 심사 근거는 SMART 하나다 [35]. SMART는 LLM으로 이름을 만들었고, 모든 열에 걸친 머리는 「The column is about …」 문장으로 바꿔 표 제목에 붙였다 [35]. 우리가 규칙으로 위→아래 칸을 이어 붙이면 같은 효과가 나는지는 근거가 없다.
- [원문] 반대 방향 근거도 있다. 평평한 표에서는 HTML이 가장 나았고 [33], RealHiTBench에서는 LaTeX가 나았다 [처리 2]. 어느 모양이 늘 낫다는 근거는 없다는 앞선 조사의 결론 [처리]과 같다.
- [원문] 행을 문장으로 바꾼 템플릿이 마크다운보다 낫다는 근거는 찾지 못했다. RAG에서는 마크다운이 의외로 잘했다 [34]. 우리 「표 검색 정보」 줄이 원본 표보다 먼저 쓰이게 한 프롬프트 지시는 근거가 약하다는 뜻이다 [판단].
- 칸마다 한 줄(`행 경로, 열 경로 = 값`)과 행마다 한 줄을 직접 견준 심사 논문은 찾지 못했다. 7B급 모델, 한국어 표로 줄 모양을 견준 심사 논문도 찾지 못했다.

## 5. 반대 근거와 한계

- [실측] 머리글 경로가 맞아져도 답이 크게 나아진다는 보장은 없다. 실험 단계 2에서 표 청크 후보 9개(JSON으로 합친 칸 채우기, 칸마다 머리글 줄, HTML 표 포함)는 색인을 다시 만들 때 생기는 잡음보다 큰 효과를 보이지 못했다(`docs/rag/m2/표-근거-실험-단계1-20261114.md`). 줄 결함이 직접 원인인 오답은 35개 중 5개다.
- [실측] 부록 B의 지표는 도구가 낸 격자의 머리 경로만 잰다. 서버가 실제로 만드는 줄은 재지 않았다. 표 정답 85개는 Claude가 초안을 만들고 사람이 일부(28표 화면)를 보는 중이라 정답 자체에 오류가 있을 수 있다.
- [실측] 공개 규칙이 우리 표에 그대로 맞지 않았다. PubTables-1M 규칙은 영어 과학 표의 정규화 가정 때문에 우리 표 16개에서 머리를 지나치게 늘렸다(부록 B).
- [원문] 위→아래로 잇는 방식은 정보를 잃는다. Docling 코드 주석은 마크다운 한 줄 머리로 펴는 일이 "unavoidable lossy flattening"이고, 같은 글의 서로 다른 층도 지운다고 적었다 [1]. 「수시1차 전체」를 묻는 질문처럼 상위 머리로 모아야 하는 경우에는 편 이름만으로는 묶음을 알기 어렵다[판단].
- [원문] SMART의 효과는 70B 모델과 영어 표에서 LLM이 지은 이름으로 잰 것이다 [35]. 7B급 모델에서 규칙으로 이은 이름이 같은 효과를 낸다는 근거는 없다. Zhao 외와 Table Meets LLM, Min 외는 2023년 모델이다 [32·33·34].
- [원문] 행 문장보다 원본 표(마크다운, HTML)가 나은 결과가 있다 [33·34]. 줄을 고쳐도 「줄을 원본 표보다 먼저 쓰라」는 지시는 따로 재야 한다.
- 찾았지만 없음: 다단 머리글 표에서 칸마다 한 줄과 행마다 한 줄을 견준 심사 논문, 한국어 표 직렬화 심사 논문(ACL Anthology와 웹 검색). Docling TableFormer와 SLANet의 머리 라벨 정확도를 따로 잰 심사 근거.

## 6. 선택지와 권고

세 상황을 나눠 본다. 과제가 「머리글 구조를 아는 표」로 둔 HWP는 실측상 병합 정보만 아는 표다(3장 질문 2).

| 관점 | 가. 머리 표시가 있는 표(HTML `th`, Docling 라벨) | 나. 병합 정보만 아는 표(PDF JSON, HWP, HWPX, `th` 없는 HTML) | 다. 구조를 모르는 표(마크다운만) |
|---|---|---|---|
| 서비스 | 표시된 앞쪽 연속 행을 머리로. 결함 ①③이 없어짐 | 규칙 3으로 PDF 머리글 경로 0.381 → 0.966(격자 기준 실측) | 결함이 남음. 줄을 못 만들 때는 원본 표만 |
| 비즈니스(학교 운영) | 학교 홈페이지 HTML 일부만 해당 | 학교 문서 대부분(PDF, HWP)이 여기 | 다른 도구가 낸 마크다운을 받을 때만 |
| 유지보수 | 표준 규칙(pandas, WHATWG)이라 설명이 쉬움 | 머리 판단이 `TableGrid` 한 곳에 모임. 지금은 마크다운 추정, JSON 어댑터, `TableGrid` 세 곳에 같은 개념이 있음 | 글자 규칙이라 표마다 예외가 생김 |
| 확장 | 표시가 없는 형식에는 못 씀 | 새 형식도 칸 주소와 병합 수만 주면 됨 | 늘릴수록 낱말 목록 같은 예외가 늘어남 |

- 권고(가): `th`나 모델 라벨이 있는 앞쪽 연속 행을 머리 블록으로 쓰고, 없으면 (나)로 넘긴다(지금 `TableGrid`가 HTML에 하는 일과 같다).
- 권고(나): PDF도 OpenDataLoader JSON 칸으로 `TableGrid`를 채워 HWP, HTML과 같은 `render_table` 규칙(규칙 2 표 제목, 규칙 3 머리 줄 수)을 쓴다. 그 위에서 서버 줄을 만들 때 아래를 함께 바꾼다.
  - 열 이름: 머리 블록의 위→아래 칸을 잇고 바로 앞과 같은 글은 뺀다(규칙 3이 이미 이렇게 함).
  - 합친 값: 본문 세로 병합 값은 덮인 칸마다 되풀이하고, 머리 병합은 머리 블록 안에서만 쓴다(RAGFlow의 나눔 [4]).
  - 빈칸과 '-': 지우지 않고 「(빈칸)」, 「-」 같은 자리표시로 남긴다(결함 ②).
  - 행 이름: 낱말 목록 대신 3장 질문 4의 구조 순서로 고른다.
  - 나뉜 표: 머리 블록 전체를 조각마다 되풀이한다.
  - 못 가린 표: 규칙 3과 숫자 없는 앞줄 규칙이 서로 다른 머리 줄 수를 내면 그 표는 줄을 만들지 않고 원본 표만 준다[판단]. 부록 B에서 두 규칙이 엇갈린 표는 4개였다.
- 권고(다): 지금 마크다운 추정 규칙은 다른 길이 없을 때만 쓰고, 머리를 확신하지 못하면 줄을 만들지 않는다(LlamaIndex, Textractor의 방식 [8·14]). 마크다운만 남는 경우를 줄이는 것(원본 형식에서 격자를 받는 것)이 우선이다.
- 줄 모양: 지금처럼 행마다 한 줄을 두되 열 이름을 머리 경로로 바꾸는 것을 먼저 잰다. 칸마다 한 줄(`행 경로, 열 경로 = 값`)은 그다음 후보다. 어느 쪽도 7B급 근거가 없어 표 질문 묶음으로 재야 한다.
- 버린 선택지와 이유: PubTables-1M 규칙 그대로 쓰기(우리 표에서 0.722, 부록 B). 구조 모델 더하기(우리 표에서 ①보다 낮고 모델이 늘어남). LLM으로 머리 이름 짓기(70B 근거만 있고 색인 때 표마다 호출, 이름을 지어낼 위험).

## 7. 확신도와 다음 확인

- 확신도: 머리 줄 규칙(나)은 높음. 우리 표 74개 실측과 공개 구현의 공통 방식이 같은 방향이다. 줄 모양과 행 이름 규칙은 낮음. 근거가 70B 모델, 2011년 웹 표뿐이고 우리 데이터로 재지 않았다.
- 다음 확인(오프라인, 데스크탑 없이 가능)
  1. PDF JSON → `TableGrid` → `render_table` → `_extract_table_facts`로 만든 줄을, 결함 줄이 있던 24문항의 표와 오답 5문항에서 지금 줄과 나란히 본다. 열 이름, 값 위치, 행 이름이 맞는지 센다.
  2. 행 이름 규칙(구조 순서)과 지금 낱말 목록을 표 정답의 첫 열 값과 견준다.
  3. 규칙 3이 놓친 3표의 모양을 보고 보완 규칙(맨 윗줄에 두 열 이상 병합 칸이 있고 아래 줄이 그 아래를 나누면 머리 2줄)이 다른 표를 망치지 않는지 부록 B로 잰다.
- 다음 확인(데스크탑): 표 질문 묶음으로 「열 이름 경로 + 빈칸 자리표시」 줄과 지금 줄을 같은 조건에서 견준다. 행마다 한 줄 대 칸마다 한 줄은 그다음.
- 다시 볼 조건: PDF 도구를 바꿀 때, 7B급 모델로 계층 표 직렬화를 잰 심사 논문이 나올 때, 한국어 표 평가 자료가 나올 때.
