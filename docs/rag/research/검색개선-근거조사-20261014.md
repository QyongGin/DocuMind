# 검색 개선 근거 조사 — 우리 실패 유형마다 무엇이 효과가 있었나 (M2 준비, 2026-10-14)

> 목적: M2 검색 개선에서 쓸 기법을 논문과 기업 기술 보고서 근거로 고른다. 우리 실패 원인(`docs/rag/m2/실패원인-분석-20261014.md`)에 맞춰, 기법마다 "어떤 조건에서 얼마나 좋아졌다는 근거가 있고, 우리에게 그대로 옮겨도 되는지"를 적는다.
> 모든 출처는 2026-10-14에 원문(논문 초록·본문, 기업 블로그, 모델 카드)을 직접 열어 수치와 실험 설정을 확인했다. 같은 날 서브에이전트가 쓴 초안은 확인되지 않는 인용(존재하지 않는 모델 크기, 출처 회사 혼동, 찾을 수 없는 벤치마크)이 있어 이 문서로 대체한다.
> 근거 표시: [원문] 출처 글자 확인 · [실측] 우리 데이터 · [판단] 우리 해석. 인용은 짧게만 옮긴다.

## 1. 결론 — 실패 유형 × 기법

| 우리 실패 유형(개발셋 실측) | 1순위 기법 | 외부 근거 | 우리에게 옮길 때 주의 | 확신도 |
|---|---|---|---|---|
| 검색이 찾은 정답 청크를 사람이 만든 규칙이 지움(우선 거르기 19 · 좁히기 12 · 상위 5개 16) | **규칙 대신 순위 융합(RRF) + 학습된 재순위(cross-encoder)** | Anthropic: 문맥 임베딩+BM25에 재순위를 더해 상위 20개 검색 실패율 5.7%→1.9%(−67%)[1] · Qwen3-Reranker·bge-reranker-v2-m3 공개(Apache 2.0)[3][4] | Anthropic 수치는 영어·코드 등 자체 데이터, Cohere 재순위. 한국어 학교 문서에서는 직접 재야 함 | 높음(방향) · 중간(크기) |
| 상위 5개 자르기 | **문맥 예산 안에서 k 늘리기(8~10)** | Databricks: 문서를 더 넣으면 재현율은 오르지만 생성 품질은 모델별 한계 뒤 떨어짐(예: 일부 모델 4k~16k)[7] · Lost in the Middle: 근거가 문맥 중간에 있으면 성능 하락[6] | 7~14B 모델은 긴 문맥에 약할 수 있음 → 모델별로 k를 실측 | 중간 |
| 표 사실이 행을 잃음(칸 단위 사실 줄의 51%) | **행 단위 직렬화 + 표 제목·머리글 경로 붙이기** | TARGET: 표 검색은 메타데이터(표 제목 등)에 민감, 밀집 임베딩이 BM25를 크게 앞섬[9] · NVIDIA: 사실형 질문은 256~512토큰 청크가 유리[8] | 행 직렬화는 청크 수·길이를 늘림 → 색인 크기·검색 시간 실측 | 높음 |
| 질문과 문서 표현이 다름(본 문항은 다른 말로 묻는다) | **청크에 문서 맥락 붙여 임베딩(Contextual Retrieval) 또는 늦은 청크 나누기(late chunking)** | Anthropic: 청크마다 50~100토큰 맥락을 붙여 임베딩만으로 실패율 −35%, BM25까지 −49%[1] · Jina late chunking: 추가 학습 없이 청크 임베딩에 전체 문맥 반영[10] | 맥락 생성에 LLM 호출 비용(Anthropic 기준 문서 토큰 100만 개당 1.02달러, 우리는 로컬 모델로 시간 비용) | 중간 |
| 한국어 임베딩 | **지금 Qwen3-Embedding-4B 유지, 한국어 특화 임베딩(KURE 등)과 개발셋 재현율로 비교** | KURE-v1(bge-m3 미세조정, MIT): 한국어 검색 벤치마크 평균 재현율@10 0.797 · bge-m3 0.792 · OpenAI text-embedding-3-large 0.729[5] · Qwen3 Embedding은 다국어 MTEB 상위[3] | 두 출처가 같은 벤치마크로 비교하지 않음 → 우리 개발셋으로 직접 비교 | 중간 |
| 근거가 문맥에 있는데 거절·틀림(문맥에 있을 때 정답 70~79%) | **충분한 문맥(sufficient context) 판단으로 답할지/거절할지 가르기, 그다음 학습(LoRA)** | Google(ICLR 2025): 문맥이 부족할 때 모델이 거절 대신 틀린 답을 내는 경우가 많고, 선택적 생성으로 '답한 것 중 정답 비율'이 2~10% 오름[2] | 우리 문제는 거꾸로 '있는데 거절'(과잉 거절)도 큼 → 판단 기준을 개발셋으로 조정 | 중간 |

## 2. 주제별 근거

### 2-1. 하이브리드 검색과 재순위

- [원문] Anthropic "Introducing Contextual Retrieval"(2024-09-19)[1]: 지표는 "1 minus recall@20", 상위 20개 청크 기준. 문맥 임베딩 단독 5.7%→3.7%(−35%), +문맥 BM25 2.9%(−49%), +재순위 1.9%(−67%). 재순위는 Cohere reranker, 첫 검색 150개에서 20개로.
- [원문] Qwen3 Embedding 기술 보고서(Zhang 외, 2025-06)[3]: 임베딩과 재순위 모두 0.6B·4B·8B, "publicly available under the Apache 2.0 license". 우리 임베딩(Qwen3-Embedding-4B)과 같은 계열 재순위가 있다는 점이 운영상 이점.
- [원문] bge-reranker-v2-m3 모델 카드[4]: bge-m3 기반, 0.6B, 다국어, Apache 2.0.
- [원문] RRF(Cormack·Clarke·Büttcher, SIGIR 2009)[11]: 여러 순위 목록을 점수 정규화 없이 1/(k+순위)로 합친다(k=60). 우리 실험 옵션(`retrieval_mode=rrf`)이 이 식을 쓴다.
- [실측·계산] 우리 개발셋: 같은 검색 결과를 RRF만 해도 정답 청크 포함(상위 5개) 72→99문항. 재순위는 그 위에 순서를 더 다듬는 단계로 둔다.

### 2-2. 몇 개를 넣을까 (k와 문맥 길이)

- [원문] Databricks "Long Context RAG Performance of LLMs"(2024-08-12)[7]: 검색 문서를 늘리면 재현율은 평균 0.47(2k)→0.95(128k)로 오르지만, "Longer context is not always optimal for RAG" — 여러 모델이 특정 길이 뒤 성능이 떨어짐(예: mixtral-instruct 약 4k, dbrx-instruct 약 8k, gpt-4-turbo 약 16k). 결론: 검색 개수는 생성 모델과 작업에 맞춰 정한다.
- [원문] Liu 외 "Lost in the Middle"(TACL)[6]: 관련 정보가 입력의 처음이나 끝에 있을 때 성능이 가장 좋고, 중간이면 크게 떨어진다.
- [판단] 우리 프롬프트는 상위 5개로 이미 최대 약 1만 토큰(13번 측정)이다. k를 8~10으로 늘리면 7~14B 모델의 한계 근처라, 상위 몇 개를 넣을지는 고른 모델로 개발셋에서 k=5·8·10을 짝 비교해 정한다.

### 2-3. 청크 나누기와 표

- [원문] NVIDIA "Finding the Best Chunking Strategy for Accurate AI Responses"(2025-06-18)[8]: 5개 데이터셋에서 토큰 128~2,048·페이지·섹션 단위를 비교. 페이지 단위가 평균 정확도 0.648로 가장 높고 편차가 가장 작음. 사실형 질문이 많은 데이터셋은 256~512토큰이, 분석형은 1,024토큰·페이지 단위가 유리.
- [원문] TARGET(Ji 외, 2025-05)[9]: 표 검색에서 "dense embedding-based retrievers far outperform a BM25 baseline", 표 제목 같은 메타데이터가 빠지면 성능이 흔들림.
- [실측·코드] 우리 색인: 표 칸마다 문장 하나(`{표 제목}: {행 이름} 행 정보는 {칸}={값}이다.`)를 만들고 행 이름이 첫 칸뿐이라, 병합 셀이 있는 표에서 값이 어느 행 것인지 사라짐(칸 단위 사실 줄의 51%). → 행 전체를 한 문장으로, 행 이름은 행을 유일하게 가리는 머리 칸 경로로.
- [판단] 우리 청크 크기(800자, 겹침 80자)는 한국어 기준 약 300~500토큰으로 NVIDIA의 사실형 구간과 맞는다. 바꿀 근거는 약하다 → 청크 크기보다 표 직렬화와 맥락 붙이기를 먼저.

### 2-4. 표현 차이 줄이기

- [원문] Anthropic[1]: 청크마다 "usually 50-100 tokens" 맥락을 앞에 붙여 임베딩·BM25 색인. 생성 비용 문서 토큰 100만 개당 1.02달러(프롬프트 캐싱 사용).
- [원문] Jina "Late Chunking"(Günther 외, 2024-09, 개정 2025-07)[10]: 전체 글을 먼저 임베딩한 뒤 풀링 직전에 청크로 나눠, 청크 임베딩에 주변 문맥이 반영됨. "works without additional training". 다만 긴 문맥 임베딩 모델이 필요.
- [판단] 우리 문서는 게시판·FAQ처럼 짧은 글이 많아(청크가 곧 문서) 맥락 붙이기의 이득은 긴 PDF·HWP(모집요강·규정)에 몰릴 것이다. 문서 길이별로 효과를 나눠 잰다.

### 2-5. 한국어 임베딩

- [원문] KURE-v1 모델 카드[5]: bge-m3를 한국어로 미세조정, MIT. 한국어 검색 벤치마크 평균에서 재현율@1 0.526(bge-m3 0.518, gte-Qwen2-7B-instruct 0.466, OpenAI 3-large 0.449), 재현율@10 0.797(0.792, 0.741, 0.729).
- [판단] Qwen3-Embedding은 이 표에 없다. 임베딩을 바꾸면 전체 재색인(데스크탑 수 시간)이 필요하므로, 개발셋 질문·정답 청크로 오프라인 재현율을 먼저 비교하고 의미 있게 좋을 때만 바꾼다.

### 2-6. 답할지 거절할지

- [원문] Joren 외 "Sufficient Context"(Google, arXiv 2411.06037, ICLR 2025)[2]: 큰 모델도 문맥이 부족할 때 "often output incorrect answers instead of abstaining", 선택적 생성으로 답한 것 중 정답 비율이 "2--10%" 오름(Gemini·GPT·Gemma).
- [실측] 우리 개발셋: 정답 청크가 문맥에 있을 때 정답 70~79%, 없을 때 2% → 거절이 맞는 경우(문맥에 없음)와 틀린 경우(문맥에 있음)를 가르는 판단이 과잉 거절을 줄이는 열쇠.

## 3. 버린 기법과 이유

| 기법 | 버린 이유 |
|---|---|
| 규칙을 더 정교하게 고치기(점수 문턱 조정) | 규칙이 문항 유형마다 늘어나 유지보수 비용이 크고, 특정 표·문구에 맞춘 조건문이 되기 쉽다(AGENTS.md 금지 규칙). 같은 결과를 학습된 재순위가 일반적으로 낸다. |
| 질의 재작성·HyDE부터 | 생성 모델 호출이 하나 더 늘어 응답 시간이 길어지고, 우리 실패의 큰 몫은 '찾았는데 지움'이라 검색 앞단을 바꿀 이유가 약하다. 재순위 뒤에도 검색 실패가 남으면 다시 본다. |
| 긴 문맥 모델에 문서를 통째로 넣기 | 색인 698개 문서를 넣을 수 없고, Databricks 결과처럼 7~14B 모델은 긴 문맥에서 성능이 떨어진다. |
| 그래프 RAG | 학교 안내 질문은 대부분 한 문서 안의 사실이라 이득이 작고 구축 비용이 크다. |
