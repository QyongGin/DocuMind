# 온프레미스 PDF 표 읽기 도구 후보 조사

## 요약

- 후보 27개를 모아 18개(조건부 2개 포함)를 실험 후보로, 9개를 뺄 것으로 나눴다. 실험에 꼭 넣을 것은 다섯이다: 지금 쓰는 OpenDataLoader 2.2.1(기준선), 같은 도구 최신판 2.5.22, 그 hybrid 모드, Docling, MinerU 4.2.2. 다음 순위로 PaddleOCR-VL-1.6, GLM-OCR, PP-StructureV3를 넣을 만하다.
- [원문] 심사를 통과한 비교 근거는 셋뿐이고 판이 오래됐다. OmniDocBench(CVPR 2025)는 MinerU 0.9.3과 Marker 1.2.3을 쟀다 [34]. READoc(ACL 2025 Findings)는 영어 문서만 쟀다 [35]. MinerU2.5 논문(ACL 2026 Industry)은 MinerU를 만든 팀이 쟀다 [11]. 최신 모델의 표 점수는 대부분 제작사 기술 보고서와 제작사 벤치마크다 [4·14·16].
- [원문] 같은 도구의 순위가 벤치마크마다 뒤집힌다. Docling은 OpenDataLoader 벤치마크에서 표 0.887로 MinerU(0.873)보다 높고 [4], READoc에서도 MinerU보다 높았다 [35]. 반면 Marker 벤치마크에서는 72.0으로 MinerU 2.5-Pro(92.1)보다 크게 낮다 [16]. 제작사마다 자기 도구를 1위로 둔다. 우리 PDF로 재야 하는 이유다.
- [원문] 한국어 PDF 표에 대한 심사 통과 근거는 찾지 못했다. OmniDocBench와 CC-OCR의 표 자료는 영어와 중국어뿐이다 [34·36]. CC-OCR의 한국어는 글자 읽기 과제에만 있다 [36].
- [원문] 라이선스에서 걸리는 것: HunyuanOCR은 라이선스가 한국에 적용되지 않는다 [26]. Marker, Surya, Chandra는 모델 가중치가 연구, 개인, 매출이나 투자 500만 달러(Chandra는 200만 달러) 미만 신생 기업에만 무료다 [16·17·18]. MinerU는 남에게 온라인 서비스를 하면 MinerU를 쓴다고 밝혀야 한다 [10].
- [원문·판단] 우리 구조에 붙이기 쉬운 순서: OpenDataLoader 계열은 지금 쓰는 JSON 그대로, Docling은 칸마다 행·열·병합 수와 머리글 표시가 있다 [7]. HTML 표(rowspan, colspan)를 내는 도구는 이미 있는 HTML 표 로더(`format_loaders/html_tables.py`의 `table_to_grid`)로 `TableGrid`를 채울 수 있다.
- 확신도 중간. 도구 기능은 코드와 공식 문서로 확인했지만, 우리 문서에서 누가 나은지는 근거가 없다. 재는 법은 6장.

## 1. 배경과 조사 질문

- 왜 조사하나: 개발셋 표 근거 45문항 중 실패 13개, 근거를 받고도 틀린 표 문항 14개 중 12개가 PDF다. 원인으로 본 네 가지(여러 줄 머리글의 둘째 줄, 세로로 합친 칸의 빈칸, 표 아래 범례·각주, 쪽을 넘긴 표) 가운데 셋은 PDF를 읽는 단계에서 생긴다(설계 문서 2-2, 4-2). 2026-11-13 진행 방식 결정에 따라 방법을 판단으로 정하지 않고 후보를 넓게 모아 데스크탑에서 같은 조건으로 잰다. 이 문서는 그 후보 중 「PDF를 읽는 도구」 부분이다.
- 정하려는 것: 실험에 넣을 도구와 판, 순위, 재는 법.
- 조사 질문:
  1. 로컬에서 돌릴 수 있는 PDF 읽기 도구와 모델은 무엇이 있나(넓게)
  2. 도구마다 표 기능(칸 병합 정보, 여러 줄 머리글, 쪽 넘김 표, 각주, 출력 형식, 읽기 순서, OCR, 한국어)과 우리 `TableGrid`에 받을 수 있는지
  3. 심사를 통과한 정확도 근거와 그 평가 설정, 한국어 근거
  4. 라이선스, 하드웨어, 속도, 유지 상태, 파이썬에서 붙이는 법
  5. 실험에 넣을 후보 순위와 재는 법

## 3. 질문별 결과

### 질문 1. 후보는 무엇이 있나

후보를 방식에 따라 넷으로 나눴다. 방식이 표 품질과 위험을 가른다.

| 방식 | 하는 일 | 후보 |
|---|---|---|
| 규칙 기반 | PDF 글자 층과 선을 읽어 표를 만든다. 모델 없음 | OpenDataLoader 로컬 모드 [1·3], Camelot, pdfplumber, PyMuPDF [39] |
| 파이프라인(레이아웃 모델 + 표 구조 모델) | 쪽 그림에서 표 영역과 칸 구조를 모델로 찾고, 칸 글자는 PDF 글자 층이나 OCR로 채운다 | Docling(TableFormer) [5·8·9], OpenDataLoader hybrid(뒤에서 Docling을 부름) [3], PP-StructureV3 [12], Marker [16], Unstructured hi_res [19] |
| 문서 전용 시각 언어 모델(VLM) | 쪽이나 영역 그림을 보고 표를 HTML, OTSL, 마크다운으로 직접 쓴다 | MinerU2.5-Pro(MinerU 4.2.2 standard 등급) [10·11], PaddleOCR-VL-1.6 [14·15], GLM-OCR [22], dots.mocr [23], Unlimited-OCR-2 [24], Nemotron 3.5 Parse [25], Granite-Docling-258M [20], Surya OCR 2.5 [17], Chandra OCR 2 [18], HunyuanOCR [26], DeepSeek-OCR-2 [27], LightOnOCR-3 [28], olmOCR-2 [29], Nanonets-OCR2 [30], MiniCPM-OCR [31], Dolphin-v2 [32], MonkeyOCRv2 [33] |
| 범용 VLM | 일반 모델에 표를 써 달라고 시킨다 | Qwen3-VL 등. 12GB에 맞는 크기는 문서 전용 모델보다 표 점수가 낮게 보고되어(4.2절 [14]) 후보에서 뺐다 |

- [원문] 파이프라인과 VLM의 차이 하나가 우리에게 크다. Docling은 표 구조만 모델로 찾고 칸 글자는 PDF 글자 층에서 가져온다: "TableFormer structure predictions are matched back to the PDF cells in post-processing" [8]. PaddleX(PP-StructureV3, PaddleOCR-VL의 실행 틀)는 PDF를 쪽 그림으로 바꿔 넣는다(`image_batch_sampler.py`가 `PDFReader`로 쪽마다 그림을 읽음) [13]. 그림을 읽는 모델은 금액이나 인원 같은 숫자를 잘못 읽을 수 있다. 우리 PDF는 대부분 글자 층이 있는 원본 PDF라 [판단] 이 차이를 지표로 따로 잰다(6장).
- 클라우드 전용(후보에서 뺌, 비교 기준 이름만): Azure Document Intelligence, AWS Textract, Google Document AI, Upstage Document Parse, LlamaParse, Mistral OCR, Reducto, Datalab API, Hancom Data Loader(OpenDataLoader README가 「Coming Soon」으로 소개) [1].

### 질문 2. 도구마다 표 기능

자세한 칸은 4.1 후보 카탈로그. 여기서는 설계 문서의 네 문제에 직접 닿는 것만 쓴다.

**칸 병합 정보와 여러 줄 머리글**

- [원문] OpenDataLoader JSON은 칸마다 `row span`, `column span`을 준다(지금 서버가 이미 읽음). hybrid 모드는 Docling이 낸 `row_span`, `col_span`을 같은 JSON 형식으로 옮긴다(`DoclingSchemaTransformer`) [3]. 2.5.0 릴리스 노트에 「표 머리글 처리 개선」, 「JSON에 표 머리글(TH) 의미 보존」, 「실제 행·열 병합 수 처리」가 있다 [2]. 2.2.1에서 2.5.22로 올리면 여러 줄 머리글 출력이 바뀔 수 있다는 뜻이지, 나아졌다는 측정은 아니다.
- [원문] Docling의 표 칸(`TableCell`)에는 `row_span`, `col_span`, 시작·끝 행·열 번호, `column_header`, `row_header` 표시가 있다 [7]. 머리글 줄을 추정할 필요 없이 받을 수 있는 유일한 후보다.
- [원문] Marker는 표를 HTML `<table>`로 내고, 제작사 벤치마크가 `colspan`, `rowspan` 관계를 시험 항목으로 둔다 [16]. MinerU, PaddleOCR-VL, Unlimited-OCR-2도 HTML이나 OTSL로 표를 쓴다 [5·24].
- [원문] OmniDocBench의 표 인식 비교에서 합친 칸이 있는 표는 모든 모델에서 점수가 떨어졌다. RapidTable 77.1 대 85.4, StructEqTable 64.5 대 81.0, Qwen2-VL-7B 60.8 대 76.5(합친 칸 있음 대 없음, TEDS) [34].

**쪽을 넘긴 표**

| 도구 | 쪽 넘김 표 처리 | 근거 |
|---|---|---|
| OpenDataLoader 2.2.1 | 합치지 않고 잇는다. 열 수, 표 너비, 첫 행 칸 너비가 같으면 앞뒤 표에 `previous table id`, `next table id`를 적는다(스키마 설명: "Linked table identifier (if broken across pages)"). hybrid 모드도 같은 후처리를 한다 | [3] |
| Docling 2.150.0 | 표준 파이프라인 코드에서 표를 합치는 단계를 찾지 못했다. Unlimited-OCR 2 프리셋 문서는 "A table or paragraph that continues on the next page stays split."라고 적는다 | [5] |
| MinerU 4.2.2 | 4.2 소개에 「쪽을 넘긴 표 합치기 개선」. 합치는 조건(열 수 등)은 DocVortex `can_merge_tables`(기존 조사 자료 23) | [10] |
| PP-StructureV3, PaddleOCR-VL-1.6 | 후처리에서 쪽을 넘긴 표를 합친다: "with additional support for cross-page table merging" | [14], 기존 조사 자료 25 |
| Unlimited-OCR-2 | 여러 쪽을 한 번에 넣어 쪽을 넘는 맥락을 본다: "All pages of a document are parsed in one request" | [24] |
| Marker | `--use_llm`을 켜면 LLM이 쪽을 넘긴 표를 합친다. 기본 LLM은 외부 API(Gemini)이고 Ollama로 바꿀 수 있다 | [16] |
| GLM-OCR | 제작사가 한계로 적음: 쪽을 넘는 배치에서 읽기 순서가 불완전할 수 있다 | [22] |

- [실측] 우리 서버 코드는 `previous table id`를 읽지 않는다(`ai-server`에서 검색). OpenDataLoader를 바꾸지 않아도 쪽 넘김 표를 이어 붙일 단서가 이미 JSON에 있다. 다만 기존 조사(부록 B)에서 캡션 연결 번호가 표 id와 맞지 않았으므로, 이 번호도 실제로 맞는지 재야 한다.

**각주·캡션 연결**: 다시 조사하지 않았다. Docling은 읽기 순서상 표 바로 뒤 각주만, MinerU는 세로 간격 안의 각주, PP-StructureV3는 줄 높이 두 배 안의 짧은 글 하나를 붙이고, OpenDataLoader 2.2.1에는 각주 분류가 없다([표 범례·각주 조사](표-범례-각주-처리-조사-20261113.md) 자료 18·23·25·27).

**OCR과 한국어**

- [원문] OpenDataLoader 로컬 모드는 OCR이 없고, hybrid 모드에서 EasyOCR(기본), RapidOCR, Tesseract를 고르며 `ko,en`처럼 한국어를 줄 수 있다. 제작사는 "Quality varies by engine, language, and document"라고 표본으로 비교하라고 한다 [1].
- [원문] PaddleOCR-VL은 한국어를 포함한 109개 언어, 1.5판은 111개 언어를 지원한다고 적는다 [12]. GLM-OCR은 모델 카드 언어 목록에 `ko`가 있다 [22]. Surya OCR 2.5는 91개 언어 자체 평가(글자, 레이아웃, 표 등을 합친 통과율)에서 한국어 77.9%를 적었다 [17]. Granite-Docling은 영어 외에 일본어, 아랍어, 중국어만 「experimental」이다 [20]. MinerU2.5-Pro 모델 카드 언어는 `zh`, `en`이다 [10].
- 원본 PDF의 글자 층을 쓰는 도구(OpenDataLoader, Docling 표준)는 OCR 언어와 상관없이 한국어 글자를 그대로 가져온다 [판단, 근거 [3·8]].

**우리 구조(`TableGrid`)에 받을 수 있나**: 4.1 표의 「우리 구조」 칸. OpenDataLoader 계열은 지금 어댑터 그대로, Docling은 칸 객체를 바로, HTML 표를 내는 도구는 `table_to_grid`로 받는다 [판단]. LaTeX 표(Nemotron), 마크다운만 내는 도구(olmOCR-2, DeepSeek-OCR-2)는 병합 정보가 빠지거나 변환기를 새로 써야 한다.

## 5. 반대 근거와 한계

- [원문] 벤치마크끼리 순위가 맞지 않는다(요약 3번째 줄). 제작사 벤치마크 둘은 각자 자기 도구를 1위로 두고 [4·16], 제3자 심사 자료인 READoc은 Marker > Docling > MinerU [35], MinerU와 같은 기관이 만든 OmniDocBench는 MinerU > Marker다 [34·11]. 벤치마크 숫자로 도구를 고르면 안 된다.
- [원문] 벤치마크 문서가 우리 문서와 다르다. OmniDocBench는 영어·중국어 9종 [34], READoc은 arXiv와 GitHub 영어 문서가 대부분 [35], OpenDataLoader 벤치마크는 200개 PDF의 출처를 밝히지 않는다 [4]. 우리 문서는 한국어 모집요강, 장학 안내, 학칙처럼 여러 줄 머리글과 세로 병합이 많은 행정 표다.
- [원문] 합친 칸은 학습 모델에도 어렵다. OmniDocBench에서 합친 칸이 있는 표의 TEDS가 6개 모델 모두 떨어졌다(가장 크게는 InternVL2-8B 78.4 → 58.7, 19.7점) [34]. 우리 문제의 중심이 이 표들이다.
- [원문] 그림을 읽는 모델은 PDF 글자 층을 쓰지 않는다 [13]. 정답이 숫자 하나인 문항에서 OCR이 숫자를 틀리면 표 구조가 맞아도 답이 틀린다. TEDS는 글자 차이를 편집 거리로 깎을 뿐이라 [37] 숫자 하나 틀린 것을 크게 벌주지 않는다 [판단].
- [원문] 쪽 넘김 표를 합치는 기능도 한계를 적는다. GLM-OCR은 쪽을 넘는 배치에서 읽기 순서가 불완전할 수 있다고 적고 [22], Docling은 쪽 넘김을 합치지 않는다 [5].
- [원문] 제작사 기술 보고서는 심사 전이다 [8·14·22]. AGENTS.md 기준상 제작사 공식 보고서로 쓰지만 제3자 검증이 아니다.
- 학습된 모델이 틀리는 사례를 심사 통과 자료에서 따로 찾았지만, 표 구조 오류를 사례로 보인 것은 OmniDocBench의 합친 칸 결과 [34] 말고는 찾지 못했다. VLM이 글자를 지어내는 현상을 다룬 글은 프리프린트뿐이었다(부록 A).

### 6.2 재는 법(제안)

- **표본**: 기존 조사가 만든 PDF 표본 61개(표 540개)를 다시 쓴다(부록 C의 로컬 산출물). 여기서 층을 나눠 뽑는다. ① 개발셋 실패 14문항의 근거 표 전부, ② 여러 줄 머리글 표, ③ 세로 병합이 3행 이상인 표, ④ 쪽을 넘긴 표(10개 이상), ⑤ 무작위 표. 합쳐 80~100개 표 [판단].
- **정답 붙이는 법**: 같은 문서의 HWP판이 있으면 HWP 로더의 `TableGrid`를 정답 초안으로 쓴다. HWP 표는 칸 병합 정보가 원본에 있어서다 [판단]. 짝이 없는 표는 쪽 그림과 글자 층을 보고 HTML 정답 초안을 쓰고, 사람은 실패 문항 표와 무작위 20개만 확인한다. HWP판과 PDF판이 같은 표인지, 그런 짝이 몇 개인지는 아직 세지 않았다.
- **지표**:
  1. 표 구조: TEDS-S(구조만), TEDS(구조+글자) [37], GriTS [38]. 다른 자료와 견줄 수 있게 쓴다.
  2. 머리글 경로 일치율: 데이터 칸마다 「열 머리글 경로(수시1차 > 일반고)」가 정답과 같은 비율. 설계 문서 (가) 문제를 직접 잰다. TEDS는 이 오류를 작은 감점으로만 본다.
  3. 세로 병합 채움 정확도: 세로로 합친 칸 아래 행이 정답 값을 갖는 비율. (나) 문제.
  4. 숫자 칸 완전 일치율: 숫자가 든 칸의 글자가 정답과 한 글자도 다르지 않은 비율. 그림을 읽는 모델의 오독을 따로 본다.
  5. 쪽 넘김 표 연결 정확도: 이어진 표 쌍을 맞게 이었는지(정밀도·재현율).
  6. 운영 지표: 쪽당 시간, 최대 VRAM, 실패한 문서 수.
- **끝단 확인**: 표 단위 지표로 남은 두세 개만 색인을 다시 만들어 개발셋 표 근거 45문항 정답률을 잰다. 색인을 바꾸면 검색 결과도 바뀌므로, 표 모양 실험(다른 조사)과 섞이지 않게 순서를 실험 설계에서 정한다.
- **판단 기준은 결과를 보기 전에** 실험 설계 문서에 적는다(예: 머리글 경로 일치율이 기준선보다 몇 점 올라야 채택하는지).

### 6.3 네 관점

| 관점 | OpenDataLoader 계열(판 올림, hybrid) | Docling | MinerU, PaddleOCR-VL 등 문서 VLM |
|---|---|---|---|
| 서비스 | 지금 출력과 같은 모양이라 회귀 위험이 작다 | 머리글 표시로 (가) 문제를 직접 줄일 수 있다 | 표 점수는 높게 보고되지만 숫자 오독 위험 |
| 비즈니스 | 추가 비용 없음, CPU 가능 | 추가 비용 없음, MIT | GPU 시간이 늘고 MinerU는 사용 표시 의무 |
| 유지보수 | 어댑터 그대로 | 칸 변환기 하나 추가 | 별도 서버(vLLM, SGLang, MinerU 서버) 운영 |
| 확장 | 한컴 상용 백엔드로 넘어갈 길이 있음 [1] | VLM 프리셋으로 모델 교체가 쉬움 [5] | 모델 교체가 잦아 판 고정이 필요 |

- 권고 [판단]: 6.1의 1순위 다섯으로 시작한다. 지금 형식을 유지하면서 나아질 수 있는 OpenDataLoader 2.5.22와 hybrid가 가장 싸고, Docling은 머리글 표시라는 다른 장점이 있고, MinerU는 VLM 쪽 대표다. 쪽 넘김 표는 도구를 바꾸기 전에 지금 JSON의 `previous table id`가 맞는지부터 잰다.
- 버린 선택지: 벤치마크 점수로 하나를 바로 고르기(순위가 자료마다 뒤집힘, 5장). 클라우드 서비스(학교 문서를 외부 API로 보내지 않는다는 원칙).

## 7. 확신도와 다음 확인

- 확신도: 중간. 도구 기능, 라이선스, 판은 코드와 원문으로 확인했다(높음). 정확도는 우리 문서와 다른 자료에서 왔고 서로 엇갈린다(낮음).
- 다음 확인:
  1. 실험 설계 때: OpenDataLoader JSON의 `previous table id`, `next table id`가 실제 표 id와 맞는지 표본 61개에서 센다.
  2. 실험 설계 때: HWP판과 PDF판이 모두 있는 문서 쌍이 몇 개인지 센다(정답 붙이는 법).
  3. 데스크탑 실행 때: MinerU standard, PaddleOCR-VL-1.6, GLM-OCR의 표 출력에 rowspan·colspan이 실제로 있는지, 최대 VRAM이 얼마인지.
  4. 운영 후보로 올리기 전: Docling TableFormer 가중치 라이선스, Marker·Surya 가중치를 교육기관 무료 서비스에 쓸 수 있는지(Datalab 문의).
- 다시 볼 조건: OmniDocBench 다음 판이나 한국어 문서 파싱 벤치마크가 심사를 통과해 실릴 때. OpenDataLoader가 각주 요소를 추가하거나 Hancom Data Loader 백엔드가 공개될 때.
