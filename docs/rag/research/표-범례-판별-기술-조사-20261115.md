# 표 범례·각주 줄을 가려내는 방법 조사

## 요약

- [실측·판단] 결론(2026-11-16 보강 4): 범례는 위치와 모델을 함께 써야 가려진다. 표 뒤 구간(표 바로 뒤부터 다음 표 전까지) 안에서 Gemma 4가 고른 줄을 붙이면, 같은 PDF 표 97개(진짜 있는 표 26개)에서 진짜 줄을 빠짐없이 붙인 표가 12개에서 24개로 늘고 무관한 줄을 붙인 표가 9개에서 5개로 준다. 결과를 본 뒤 만든 조합이라 새 표로 다시 재야 하고, 표 아래 조건 줄도 60개 표에 함께 붙으므로 붙이는 대상을 넓힐지 먼저 정해야 한다(6장 보강 4 권고).
- [실측] 보강 2까지의 결론: 지금 규칙(가)보다 확실히 나은 방법은 찾지 못했다. 가장 가까운 것은 지금 규칙이 고른 줄을 Gemma 4 12B가 줄마다 예/아니오로 확인하는 방식이다. 같은 PDF 표 97개(진짜 있는 표 26개)에서 찾은 표 20개를 그대로 두고 잘못 붙인 표를 14개에서 5개로 줄였다. 하지만 HWP 표 37개에서는 진짜 2개 표를 놓쳤고, 가가 붙이는 표 51개가 모두 판정 자료라 새 표로는 재지 못했다(질문 10).
- [실측] 시각 언어 모델 넷(Gemma 4, Qwen3-VL-4B, kanana-1.5-v-3b, A.X 4.0 VL Light)은 혼자 쓰면 진짜 19~26개를 찾지만 잘못 붙인 표가 74~91개다. 그 잘못의 대부분은 표 아래 조건 줄(딸린 글)이고, 표와 무관한 줄을 붙인 표는 Gemma 17개, Qwen 23개다. 지금 규칙은 잘못 14개 중 9개가 무관한 줄이다(질문 8).
- [원문·실측] 표와 주석 줄을 잇도록 학습한 작은 공개 모델은 찾지 못했다. 표 각주 라벨이 있는 배치 모델 PP-DocLayoutV2는 MinerU 안에서 이미 쟀고(찾음 17, 조건 줄을 더 붙인 표 43), 서비스의 재순위 모델은 어느 문턱값에서도 가보다 못했다. 문서 안 기호 쓰임새로 글머리표를 빼는 규칙은 잘못을 반으로 줄였지만 진짜 5개 표를 잃었다(질문 9, 10).
- [실측] 상한 확인으로 Claude Opus에게 같은 프롬프트를 글만 주자 진짜 26개를 모두 찾고 무관한 줄은 한 표에도 붙이지 않았다(잘못 15개는 모두 조건 줄이거나 애매). 과제는 풀 수 있는 정의이고, 작은 모델의 한계로 보인다. 큰 모델을 색인에 쓸지는 운영 클라우드 결정(ADR-0030)에 달려 이 조사에서 권하지 않는다.
- [실측] 보강 3: 목표를 「범례」가 아니라 「표에 딸린 글(조건·단서 포함)」로 바꾸면, Gemma 4가 고른 줄을 다시 「딸린 글인가」로 확인하는 방식이 PDF 97개에서 진짜 줄을 빠짐없이 붙인 표 22개(지금 규칙 12개), 무관한 줄을 붙인 표 7개(지금 규칙 9개)였다. 지금 규칙은 기호가 든 줄만 고를 수 있어 여러 줄 범례의 이어지는 줄을 놓친다(진짜 줄 66줄 중 24줄, 질문 8·10).
- [원문] 표 각주를 표에 이어 주는 제품(Azure 등)은 방법을 공개하지 않는다. 공개된 정의는 「각주 기호로 표시되고 표 격자 아래에 있다」로 지금 규칙의 단서와 같다 [13]. 범례만 따로 라벨로 단 공개 데이터셋은 찾지 못했다(질문 5, 6).
- [실측] 같은 판정 자료(표 156개, 진짜 범례·각주가 있는 표 35개)로 방법 여덟 가지를 쟀다. 지금 규칙(표 바로 뒤 주석 묶음에서 그 표 칸의 기호가 든 줄)이 29개를 찾고 23개 표에 잘못된 줄을 붙여, 찾은 수와 잘못 붙인 수의 균형이 가장 좋았다. 모든 방법을 같은 PDF 표 97개(진짜 26개)로 보면 지금 규칙 20개 찾음·14개 잘못, MinerU 17·49, Docling 7·16이다. A.X 4.0 Light는 1,111개 표 모두에 줄을 하나 이상 골라 거르는 구실을 못 했다(3장 질문 4, 부록 B).
- [원문·실측] 레이아웃 모델은 범례를 가리지 않는다. DocLayNet 라벨 지침은 표 아래 글을 표 격자 밖이라 Text로 단다고 적었고 [6], Docling은 우리 진짜 범례 줄 31개 중 16개를 목록 항목으로, 8개만 각주로 분류했다. 표 각주 라벨을 따로 두는 MinerU [8]는 표 아래 ※ 줄을 범례든 조건이든 함께 붙여, 묶음 전체를 붙이는 것과 비슷하게 움직였다. 표 각주만 따로 잰 공개 정확도는 찾지 못했다 [7].
- [실측] 작성자가 파일에 남긴 표시는 드물다. HWP 표 1,436개 중 칸 안 각주 개체가 든 표 7개, 아래쪽 캡션이 있는 표 18개(15개가 ※·* 주석)뿐이고 서비스 색인에는 0개다. HTML `caption` 110개는 화면 낭독용 표 설명이었고 `sup`은 0개였다.
- [실측] 기호가 겹치지 않는 주석 표본 30개에서 진짜는 0개였다(95% 위쪽 한계 약 12%). 서비스 색인 전수에서는 1개(행 이름의 등급 코드 풀이)였다. 지금 규칙의 빈틈은 작다.
- 권고 [판단]: 찾기 규칙은 지금 것(가)을 유지한다. 그 위에 파일 표시 하나만 더한다. HWP 표의 아래쪽 캡션은 로더가 표 앞에 두는데, 이것을 표 뒤로 옮겨 같은 규칙이 보게 한다. 레이아웃 모델, 언어 모델, 시각 언어 모델 단독, 재순위 모델, 글자 크기·간격 규칙, 글머리표 기호 빼기는 지금 숫자로는 들이지 않는다. Gemma 4 예/아니오 확인(과 교집합 거르개)은 다음 후보로 두고, 새 문서의 표를 다른 사람이 판정해 다시 잰 뒤 정한다. 확신도 중간.

## 1. 배경과 조사 질문

- 왜 조사하나: 설계 초안은 범례와 각주를 표 번호에 달아 그 표가 검색되면 함께 모델에 주기로 했다. 어느 줄이 그 표의 범례·각주인지 찾는 방법은 「표 바로 뒤 주석 묶음에서 칸 기호가 든 줄」이었고, 앞선 셈에서 걸린 표 51개 중 29개(57%)가 진짜였다. 이 방법이 단순하고 근거가 모자라며 한 문서에 맞춰졌다는 지적이 있어, 다른 방법을 넓게 찾고 같은 자료로 재 비교한다.
- 이미 답한 것(되풀이하지 않음): 공개 도구가 표와 각주를 잇는 규칙(Docling은 읽기 순서상 표 바로 뒤의 각주 블록만, MinerU는 같은 쪽 표 뒤, PP-StructureV3는 줄 높이 2배 안의 짧은 글), 상용 문서 AI의 표 각주 구조, OpenDataLoader 2.2.1의 캡션 연결 번호 문제는 [앞선 범례 조사](표-범례-각주-처리-조사-20261113.md)(아래 「앞 조사 N」) 질문 1·4·5에 있다.
- 조사 질문:
  1. 문서를 만든 사람이 파일에 남긴 각주·범례 표시가 형식마다 무엇이고, 우리 문서에 얼마나 쓰였나. 칸 표식과 이어진 표시인가 꾸밈인가
  2. 표 각주와 범례를 가려내는 모델·도구·논문에는 무엇이 있고, 근거가 얼마나 되나
  3. 반대 근거와 한계
  4. 같은 판정 자료로 잰 방법별 결과
- 보강 질문(2026-11-16): 지금 규칙의 근거가 약하다는 지적에 따라, 쪽을 읽고 표의 범례를 가려 주는 모델과 제품을 찾아 같은 판정 자료로 잰다. 범위를 줄이지 않는다. 다음 쪽 주석, 표와 떨어진 범례, 색 범례도 대상이다.
  5. 쪽을 읽고 표와 그 표의 범례·각주를 이어 주는 모델이나 제품이 있는가. 무엇을 받고 무엇을 돌려주는가
  6. 표 주석·범례 라벨이 있는 공개 데이터셋이 있는가(한국어 포함)
  7. 데스크탑(RTX 4070 Super 12GB)에서 색인할 때 돌릴 수 있는 후보는 무엇인가
  8. 우리 문서에서 지금 규칙보다 나은가
- 보강 2(2026-11-16 새벽): 「표의 내용과 범례를 견줘 판단하는 작은 전용 신경망 모델은 없는가, 다른 방법은 없는가」라는 질문에 따라 더 쟀다. 잘못 붙인 표가 표 아래 조건 줄을 붙인 것인지 표와 무관한 줄을 붙인 것인지도 나눠 셌다.
  9. 표의 내용과 후보 줄을 견줘 범례·각주인지 가리는 작은 전용 모델이 있는가
  10. 다른 방법(문서 안 기호 쓰임새 규칙, 규칙 후보를 모델이 예/아니오로 확인, 큰 모델 상한)은 지금 규칙보다 나은가

## 2. 범위와 방법

- 자료 기준: `AGENTS.md` §4와 이 폴더 README 머리말. 근거는 표준 문서, 도구·모델을 만든 회사·기관의 공식 문서와 기술 보고서, 게재처를 확인한 심사 논문(A 등급)만 쓴다. 공식 저장소의 코드는 그 도구가 하는 일의 1차 자료로 쓰고 README는 사례(B)로만 쓴다. 개인 저장소, 프리프린트, 검색 요약은 실마리로만 썼다.
- 기간: 2025~2026년 자료를 먼저 봤다. 2006~2022년 자료([5]·[9]·[10])는 「그런 현상이 있다」는 근거로만 쓰고 숫자를 지금 도구로 옮기지 않는다.
- 포함 / 제외: 파일 형식 7개의 표시, 레이아웃 모델의 표 각주 라벨과 그 정의, 표식과 주석 줄을 잇는 논문, 범례 연구. 머리글 판별과 표 구조 인식은 앞선 조사가 맡아 뺐다. 클라우드 문서 API는 학교 문서를 밖으로 보낼 수 없어 실행하지 않았다.
- 검색한 곳과 날짜: 2026-11-15. ISO 32000-1(Adobe 공개 사본), 한컴 공식 파일 형식 문서 2종, WHATWG HTML, CVF Open Access, ACL Anthology, ACM·Springer 서지(OpenAlex·Crossref), IBM DocLayNet 공식 저장소, 저자 소속 기관의 공개 PDF, GitHub 공식 저장소. 웹 검색으로 후보를 모은 뒤 원문을 직접 받았다.
- 고른 기준 / 뺀 기준: 논문은 `venue_check.py`로 게재처를 확인했다. 프리프린트만 있는 것(DocLayout-YOLO 등)은 뺐다(부록 A).
- 건수: 후보 목록 세 개에 이름이 오른 자료는 형식 표준 8종, 모델·도구·데이터셋 30여 항목, 논문 25항목이다(목록마다 단위가 달라 더하지 않는다). 원문을 받아 대조한 것은 참고 문헌 12건이다. 인용 문장 27개를 `quote_check.py`로 원문 글에서 대조했고 모두 「있음」이었다.
- 제작사·기관 체크리스트: Adobe(ISO 32000) 찾음 [1] · 한글과컴퓨터 찾음 [2·3] · WHATWG 찾음 [4] · IBM(Docling, DocLayNet) 찾음 [5·6·11] · 상하이 AI 연구소(MinerU, OmniDocBench) 찾음 [7·8·12] · Baidu(PaddleOCR-VL) 원문을 열었으나 표 각주 범주를 찾지 못함(부록 A) · Microsoft·AWS 앞 조사 [앞 조사 3·6] · ECMA-376(DOCX), ISO 32000-2 원문은 열지 않음(부록 A) · 한국어 행정 문서로 잰 심사 논문은 찾지 못함.
- 직접 잰 것: 형식별 작성자 표시 개수(수집 문서 전부), 표 156개의 줄 단위 판정, 방법 여덟 가지의 결과와 시간. 레이아웃 모델과 언어 모델은 데스크탑(RTX 4070 Super 12GB)에서 네트워크를 끈 컨테이너로 돌렸다(부록 B).
- 보강(질문 5~8)의 방법: 2026-11-15~16. 모델은 Hugging Face의 제작사 공식 저장소에서 라이선스, 동의 필요 여부, 파일 크기를 확인했고, 제품은 제작사 공식 문서만 읽었다. 클라우드 제품에는 우리 문서를 보내지 않았다. 측정 후보는 12GB에 들고, 라이선스가 맞고, 공식 배포처에서 동의 없이 받을 수 있는 시각 언어 모델 넷으로 골랐다(질문 7, 부록 A). 보강에서 새로 쓴 인용 16개를 `quote_check.py`로 원문 글과 대조했고 모두 「있음」이었다.
- 보강 2(질문 9·10)의 방법: 2026-11-16 새벽. 모델 카드와 공식 저장소(Hugging Face, GitHub)만 읽었고, 논문 셋은 `venue_check.py`로 게재처를 확인했다. 새 인용 9개를 원문과 대조해 모두 「있음」이었다. Hugging Face 모델 검색과 GitHub 저장소 검색으로 표-주석 연결 가중치를 셌다. 새 방법은 같은 판정 자료와 같은 지표로 쟀고, 잘못 붙인 표를 딸린 글과 무관으로 나눠 셌다(부록 B).

## 3. 질문별 결과

### 질문 1. 형식별 작성자 표시와 우리 문서의 개수

**결론** [실측] 표와 이어진 각주·주석을 작성자가 파일에 남긴 경우는 HWP에서만 보였다. 표 1,436개 중 칸 안 각주가 든 표 7개, 아래쪽 캡션이 있는 표 18개이고, 서비스 색인에는 0개다.

| 형식 | 표시(정의) | 칸 표식과 이어지나 | 수집 전체 | 서비스 색인 |
|---|---|---|---|---|
| HWP 5.0 | 각주·미주 컨트롤 `fn`, `en`(표 127) [2], 표 개체의 캡션 리스트(표 68·71)와 캡션 방향(표 73) [2] | 각주는 칸 안 자리에 번호가 붙음(이어짐). 캡션은 표 전체에 딸림 | 표 1,436개 중 칸 안 각주 든 표 7(각주 14개), 캡션 있는 표 22(아래 18, 그중 ※·* 주석 15) | 표 60개 중 0 |
| HWPX | `FOOTNOTE`, `ENDNOTE`(표 165), `CAPTION`(표 107, Side) [3] | 위와 같음 | 표 9개 중 0 | 해당 문서 없음 |
| PDF(태그) | `Note`, `Reference`, `Lbl`, `Caption`, `TFoot`(표 333·337·338) [1] | `Note`는 본문에서 참조되는 각주 | 태그 PDF 163개의 표 201개 중 표 안 `Note` 1, `Lbl` 2, 표 옆 `Caption` 0 | 태그 PDF 2개, 0 |
| HTML | `caption`(4.9.2), `tfoot`(4.9.7) [4], 칸 안 `sup` | `caption`은 표 제목, `tfoot`은 열 요약 | 표 1,222개 중 `caption` 110, `tfoot` 2, 칸 안 `sup` 0 | 표 191개 중 `caption` 110, `tfoot` 2 |
| DOCX | 각주 참조, 표 캡션(`tblCaption`), Caption 스타일 문단 | — | 표 17개 중 0 | 표 9개 중 0 |
| XLSX | 칸 메모 | 칸에 직접 붙음 | 파일 7개 중 메모 파일 2 | 해당 문서 없음 |
| PPTX | 표 각주 요소를 찾지 못함 | — | 세지 않음 | — |

- PDF [원문]: `Note`는 "An item of explanatory text, such as a footnote or an endnote, that is referred to from within the body of the document."이고 `Reference`로 참조될 수 있다 [1]. 다만 "Tagged PDF does not prescribe the placement of footnotes in the page content order."라서 쪽의 어디에 오는지는 정하지 않는다 [1]. `TFoot`은 "A group of rows that constitute the footer of a table."로 표 안의 행 묶음이다 [1].
- HWP [원문]: 각주·미주는 문단 리스트를 가진 컨트롤이고(표 127), 각주 번호를 위 첨자로 할지 정하는 속성이 있다("각주 내용 중 번호 코드의 모양을 위 첨자 형식으로 할지 여부", 표 134) [2]. 캡션은 개체 공통 속성 뒤에 "캡션 정보가 있으면 캡션 리스트 정보를 얻는다"(표 68)로 붙고, 방향은 left, right, top, bottom이다(표 73) [2].
- HWP [실측, 표본 전부]: 칸 안 각주가 든 7개 표의 각주 14개는 모두 칸 글에 번호로 걸린 풀이였다(「현재 재학 중인 캠퍼스 소재지 기준입니다」 등). 아래쪽 캡션 18개 중 15개는 ※·* 주석이었고, 그중 하나는 앞선 셈이 「표 바로 위」에서 찾은 진짜 각주(칸 「우대 지원*」의 풀이)였다.
- HWP 로더 [실측·판단]: 서버의 HWP 로더(`format_loaders/hwp5.py`의 `table`)는 캡션 방향과 상관없이 캡션 글을 표 앞에 둔다. 그래서 아래쪽 캡션의 주석이 「표 바로 위」로 보인다. 칸 안 각주 글은 그 칸의 글로 이미 들어가므로 따로 찾을 일이 없다.
- HTML [원문·실측]: `caption`은 "The caption element represents the title of the table that is its parent"로 표 제목이다 [4]. 우리 `caption` 110개 가운데 12개는 비었고, 나머지는 「구분별 졸업학점, 최소취득학점 안내」처럼 화면 낭독용 표 설명이었다(앞 40자 기준 76가지). `tfoot` 2개는 합계 행이었다.
- [판단] 파일 표시로 찾을 수 있는 것은 HWP 아래쪽 캡션뿐이다. 수가 적어 효과는 작지만, 글자 모양이 아니라 작성자가 고른 개체라 다른 HWP 문서에도 그대로 통한다.

### 질문 2. 표 각주와 범례를 가려내는 모델·도구·논문

**결론** [원문] 표 각주를 라벨로 따로 다는 모델과 데이터셋은 있다. 그러나 그 라벨만 따로 잰 정확도와 한국어 행정 문서로 잰 근거는 찾지 못했다. 범례(기호 뜻풀이)를 따로 다루는 연구는 찾지 못했다.

| 후보 | 표 각주 라벨 | 라벨 정의의 출처 | 따로 잰 정확도 | 한국어 근거 | 라이선스·12GB | 우리 표에서(부록 B) |
|---|---|---|---|---|---|---|
| Docling 2.150.0(레이아웃 모델 heron) | 없음. `footnote` 하나 [앞 조사 19] | 라벨 이름이 DocLayNet과 같다. DocLayNet의 각주는 쪽 아래의 작은 글 [6]. heron의 학습 자료는 확인하지 못함 | 없음 | 없음 | MIT, CPU로 돎 [앞 조사 18] | PDF 표 25개 중 7개 찾음, 16개 잘못 붙임 |
| MinerU 4.2.2(standard) | `table_footnote`(표 블록 안) [12] | 자체 태그 체계 [8] | 없음 | 없음 | 앞 조사 [앞 조사 22], 파싱 서버가 GPU 7.5GB를 잡음(실측) | PDF 표 26개 중 17개 찾음, 49개 잘못 붙임 |
| MinerU2.5(VLM) | `table_footnote` [8] | 자체 태그 체계, 기존 데이터셋 정의가 서로 다르다고 적음 [8] | 없음 | 없음 | 1.2B | MinerU 4.2.2 standard의 모델 폴더에 MinerU2.5-Pro 1.2B가 있음(실측) |
| OmniDocBench(평가셋) | Table Footnote [7] | 자체 주석 | 평가에서 캡션·각주를 뺌 [7] | 없음 | — | — |
| PP-StructureV3 | 없음. 좌표 규칙으로 각주를 만듦 [앞 조사 25] | — | 없음 | — | Apache-2.0 | 재지 않음(규칙은 마2와 같은 계열) |
| Azure·Textract(클라우드) | 표의 각주 목록, `TABLE_FOOTER` [앞 조사 3·6] | 공개 안 함 | 공개 안 함 | — | 학교 문서를 보낼 수 없음 | 재지 않음 |
| Wei 외 2006(CRF) | `TABLEFOOTNOTE` [9] | 칸이나 행을 참조하는 줄 | 정밀도 0.896, 재현율 0.687(FedStats) [9] | 없음 | 옛 방법 | — |
| TableSeer 2007 | Table Footnote [10] | 표 내용을 설명하는 표 아래 글 | 정밀도·재현율 82.77%(표 371개) [10] | 없음 | 옛 방법 | — |

- [원문] DocLayNet 라벨 지침은 각주를 "Typically small text at the bottom of a page, with a number or symbol that is referred to in the text above."로 정의한다 [6]. 표 아래 주석은 각주로 달지 않는다. 8.3.5절은 그림 아래 "notes, or source statement, or footnote-like text below"를 두 번째 캡션으로 달지 않는다고 하고, 표에도 같은 규칙을 적용해 "the text below the table has to become “Text”, as it is not inside the table grid."라고 적는다 [6]. 범례는 그림의 범례만 다루며 "Legends of a diagram belong to the Picture"다 [6].
- [원문] MinerU2.5는 레이아웃 태그 체계를 비교한 표 10에서 `table_footnote`를 따로 두고, PaddleOCR은 `common_footnote` 하나로 묶는다고 적었다 [8]. 이유로 "Existing datasets suffer from widespread inconsistencies in element definitions, granularity, and scope."를 든다 [8].
- [원문] OmniDocBench는 레이아웃 주석에 Table Footnote를 두지만, 끝에서 끝까지의 평가에서 캡션과 각주를 뺀다. 이유는 "Captions for figures, tables, and footnotes often have uncertain placements, thus complicating the reading order."다 [7]. 표 각주를 얼마나 맞게 찾는지는 이 벤치마크로 알 수 없다[판단].
- [원문] 표식과 주석을 잇는 방법을 다룬 심사 논문은 2006~2007년 것만 찾았다. Wei 외는 표의 줄을 CRF로 분류하며 `TABLEFOOTNOTE`를 "a reference to a cell or line in a table"로 정의했다 [9]. TableSeer는 표 각주를 "text that explains the information in the table and usually appears below the table body"로 정의했다 [10]. 둘 다 각주 줄을 찾을 뿐 어느 칸의 표식과 잇는지는 다루지 않았다[판단].
- [원문] 코드가 공개된 도구가 표와 각주를 잇는 규칙은 모두 위치(같은 쪽, 표 뒤, 가까움)이고 기호나 번호를 맞춰 보지 않는다 [앞 조사 18·23·25].
- 찾았지만 없음: 범례(기호 뜻풀이)를 따로 분류하거나 칸의 기호와 잇는 심사 논문·공식 도구, 표 각주 라벨만 따로 잰 클래스별 정확도(2025~26), 한국어 행정·공공 문서로 잰 표 각주 근거. 검색한 곳은 2장과 같다.

**수집 전체에서 붙는 표** [실측]: 같은 파일 같은 표는 한 번 셌다. 가는 51개 표에 붙이고 51개 모두 판정했다(잘못 23). 나와 라는 1,098개 표에 붙인다. 판정하지 않은 944개는 빈틈 표본의 비율(30개 중 30개 잘못)로 보면 대부분 진짜 범례가 아닌 줄이다[계산]. 마2는 PDF 표 328개에 붙인다.

### 질문 5. 쪽을 읽고 표와 범례·각주를 잇는 모델과 제품(보강)

**결론** [원문] 표 각주를 표에 이어 주는 제품은 있지만 방법은 공개하지 않는다. 공개된 정의는 「각주 기호로 표시되고 표 격자 아래에 있다」로, 지금 규칙이 쓰는 단서(표 바로 뒤, 칸 기호)와 같다. 범례만 따로 가려 주는 제품이나 모델은 찾지 못했다.

| 제품·모델 | 받는 것 | 돌려주는 것 | 표와 주석 잇기 | 우리가 쓸 수 있나 |
|---|---|---|---|---|
| Azure Content Understanding [13] | 문서 | 표의 각주 목록, 문단 역할 footnote | 정의만 공개(아래) | 클라우드라 학교 문서를 보낼 수 없음 |
| Azure Document Intelligence, AWS Textract | 문서 | 표의 각주 목록, TABLE_FOOTER [앞 조사 3·6] | 방법 비공개 | 같음 |
| Upstage Document Parse | 문서 | 확인 못 함 | 확인 못 함 | 공식 문서가 스크립트로 그려져 받은 글에 범주 목록이 없었다(열지 못함, 부록 A) |
| Claude, OpenAI, Gemini의 PDF 입력 [14·15·16] | PDF | 쪽 그림과 추출한 글을 함께 모델에 줌 | 표 주석을 다루는 문장은 찾지 못함 | 우리 「그림 + 번호」 입력이 같은 방식 |
| 문서 파서 MinerU [8·12], Docling [11] | PDF | 표 블록 안의 표 각주 / 표 항목의 각주 참조 | 레이아웃 모델의 분류 + 표 뒤 위치 [앞 조사 18·23] | 데스크탑에서 돎(질문 4에서 잼) |
| 범용 시각 언어 모델(Gemma 4, Qwen3-VL, kanana, A.X 4.0 VL Light) | 쪽 그림 + 지시 | 지시한 형식의 답 | 정해진 출력이 없다. 우리가 지시와 출력 형식을 정해야 한다 | 데스크탑에서 돎(질문 8에서 잼) |

- [원문] Azure Content Understanding은 표 각주를 이렇게 정의한다. "Table footnotes annotate content inside the table and are often marked with footnote symbols." "They're often found underneath the table grid." [13] 표 객체에는 "A table can also have a set of footnotes."로 각주 목록이 붙는다 [13].
- [원문] Claude의 PDF 입력은 "The system converts each page of the document into an image."이고 "The text from each page is extracted and provided alongside each page’s image." [14] OpenAI도 "the API extracts both text and page images and sends both to the model."이라고 적었다 [15]. Gemini는 PDF를 "rendered as page images"로 다룬다 [16]. 쪽 그림과 추출한 글을 함께 주는 것이 큰 모델 회사들의 문서 입력 방식이다.
- [판단] 범용 시각 언어 모델은 표 각주용 출력이 따로 없어, 「후보 줄 번호를 고르게 하는」 출력 계약을 우리가 정했다. 모델이 글을 새로 쓰면 지어낸 뜻풀이가 근거로 들어갈 수 있어서다(질문 8에서 실제로 나왔다).

### 질문 9. 표와 줄을 견주는 작은 전용 모델(보강 2)

**4. 딸린 글인지 묻기(경계, 보강 3)** [실측]: 큰 모델도 「범례만」 묻는 질문에 표 아래 조건 줄을 함께 골랐고, 공개 정의(Azure, M6Doc, OmniDocBench)의 단위도 「표 주석」이다. 그래서 「범례인가」 대신 「이 표에 딸린 글인가, 다음 내용인가」를 묻는 두 방식을 쟀다. 딸린 글은 붙여도 되는 것으로 보고, 지표는 ① 진짜 줄을 빠짐없이 붙인 표, ② 진짜를 하나라도 붙인 표, ③ 무관한 줄을 붙인 표, ④ 딸린 글을 붙인 표(참고)다. 질문은 재기 전에 고정했고, 문구 시험은 가나대학 합성 쪽으로만 했다(부록 B).

## 5. 반대 근거와 한계

- [원문] 레이아웃 모델의 각주 정의가 우리 표 주석과 다르다. DocLayNet은 쪽 아래 각주만 Footnote로, 표 아래 주석은 Text로 단다 [6]. 데이터셋마다 정의가 다르다는 지적도 있다 [8].
- [원문] 각주는 찾기 어려운 라벨이다. DocLayNet의 2022년 모델은 Footnote를 Text·Table보다 낮게 찾았다 [5]. TableSeer는 짧은 표 각주를 표의 행으로 오인했고 [10], Wei 외의 표 각주 재현율은 0.687이었다 [9]. 모두 옛 모델이라 지금 숫자로 옮기지 않는다.
- [원문] 표 각주를 다는 최신 평가셋도 그 부분을 채점하지 않는다 [7]. 표 각주 찾기를 공개 수치로 비교할 길이 없다.
- [실측] 우리 판정 자료는 「칸 기호가 겹친 표」(A)에서 시작해 가에 유리하다. 빈틈 표본 30개와 서비스 색인 전수로 이 치우침을 어림했지만, 빈틈 표본은 수집 전체 1,041개 중 30개라 위쪽 한계가 12% 안팎으로 넓다.
- [실측] 판정은 Claude가 한 번 했고 사람이 확인하지 않았다. 줄 단위 판정에서 애매했던 것(칸 낱말을 표식 없이 풀어 쓴 줄 1개, 다른 ※ 줄의 *에 딸린 줄 4개 등)은 판정 기록에 메모로 남겼다.
- [실측·판단] 라의 결과는 한 프롬프트, 양자화(Q4_K_M)한 학습 전 A.X 4.0 Light, JSON 스키마 출력 한 조건이다. 빈 답이 한 번도 없었던 것은 프롬프트의 예시(`{"lines": [2]}`)나 스키마 출력이 고르게 만든 탓일 수도 있다. 프롬프트를 판정 자료에 맞춰 고치지 않기로 했으므로 다른 조건은 재지 않았다.
- [실측] 다는 PDF 쪽을 한 쪽씩 잘라 돌렸다. 표가 쪽을 넘기는 경우 앞 쪽 조각의 각주 연결은 보지 못했다. 우리 표 97개 중 도구의 표와 칸 글로 짝지어지지 않은 표가 Docling 5개, MinerU 2개다.
- [판단] 근거를 늘리면 답이 나빠질 수 있다는 앞 조사의 반대 근거 [앞 조사 15·16]와 우리 두 번의 기록은 여기에도 그대로다. 나(묶음 전체)는 서비스 색인 표 82개 중 80개에 범례가 아닌 줄을 붙인다.
- [실측·판단] 시각 언어 모델(보강)은 한 프롬프트, temperature 0, 3~12B 크기에서만 쟀다. A.X 4.0 VL Light는 4비트로 올렸고 Gemma 4는 QAT 4비트판이다. 더 큰 모델, 다른 프롬프트, 표마다 따로 묻는 방식은 결과가 다를 수 있다. 프롬프트를 판정 자료에 맞춰 고치지 않았다.
- [실측] Gemma 거르개는 결과를 본 뒤 만든 조합이고, 넷 가운데 가장 좋은 모델을 골랐다. 같은 조합에서 Qwen3-VL-4B는 잘못 14개→8개, kanana는 12개, A.X 4.0 VL Light는 13개였다. 모델에 따라 효과가 크게 달라, 새 표에서는 덜 좋을 수 있다[판단].
- [실측] 묶음 밖 줄은 모델이 고른 줄만 판정했다(줄 단위 진짜 66줄은 하한이고 모델의 줄 재현율이 유리하게 잡힌다). 어느 모델도 고르지 않은 묶음 밖 진짜는 정답에 없어, 「찾은 표」의 분모(진짜 있는 표 26개)가 작게 잡혔을 수 있다. 기호도 주석 모양도 없는 본문 줄(kanana 566줄, 다른 모델 302줄)은 눈으로 보지 않고 진짜 아님으로 넣었다.
- [실측] Word·HWP 문서는 쪽 그림을 만들지 못해(데스크탑에 LibreOffice가 없고, HWP 변환 도구는 확인하지 못함) HWP 표 37개는 글만 넣었다. DOCX와 HTML 표는 모델로 재지 않았다. 판정한 HTML 표 22개 가운데 지금 규칙이 줄을 고른 표가 1개라 거르개를 확인할 자료가 되지 않았다.
- [실측] kanana와 A.X 4.0 VL Light는 시간 때문에 한 번씩만 돌려 두 번 같은 답인지 재지 않았다. 서비스 색인 PDF 49개는 판정 97개와 겹치는 표다.
- [실측] 보강 2의 나눔 판정(딸린 글, 무관, 애매)은 Claude가 한 번, 모델 답을 본 뒤에 했다. 다른 표의 주석과 그 표의 제목처럼 경계가 판단에 기대는 줄이 있어 애매 55줄은 따로 셌다.
- [실측] 판정을 한 번 고쳤다. 교원 초빙 연구실적 배점 표(pdf:2006)는 열 「※세부기준」의 칸이 번호(1~14)이고 다음 쪽 번호 줄이 그 풀이인데, 처음 판정에서 진짜 아님으로 봤다. 같은 모양(표식이 붙은 머리 칸 + 번호뿐인 열)을 판정 자료 전체에서 찾았고 이 표 하나뿐이었다. 고친 판정으로 질문 4와 질문 8을 다시 셌다.
- [판단] 바1·바2와 Gemma 거르개는 가의 오답을 본 뒤 만든 방법이다. 가가 붙이는 표 51개가 모두 판정 자료라, 우리 문서 안에서는 새 표로 검증할 수 없다.
- [실측] 재순위 모델과 예/아니오 확인은 질의 모양 하나, 프롬프트 하나로만 쟀다. 큰 모델 상한 확인은 글만 줬다(쪽 그림 없음). 그래서 색으로만 뜻을 나타내는 범례는 큰 모델도 볼 수 없었다.
- 찾았지만 없음: 한국어 행정 문서에서 표 각주 분류를 잰 심사 논문, 범례를 따로 다룬 연구, 표와 주석 줄을 잇도록 학습한 공개 가중치.

- 이유:
  - [실측] 같은 PDF 표에서 가보다 진짜를 더 찾은 방법은 나뿐이고, 나는 잘못 붙인 표가 6배다. 레이아웃 모델 둘은 가보다 적게 찾았고(7, 17), MinerU는 잘못이 3배 넘었다(49).

  - [실측] 빈틈(기호가 겹치지 않는 진짜)은 표본 30개 중 0개, 서비스 색인에서 1개였다. 지금 규칙을 바꿀 만큼 크지 않다.

| 비즈니스 | 색인 시간이 거의 들지 않는다 | 가가 고른 줄만 묻는다. 수집 전체 82줄 × 0.8초 ≈ 1분, 글만이라 HWP·DOCX도 같은 방식 | 가가 줄을 고른 표만 쪽 그림으로 돌린다. 51개 × 2.3초 ≈ 2분, GPU 9.1GB | 모든 표를 돌린다. 1,111개 × 2~3초 ≈ 40~55분 |
| 유지보수 | 규칙 하나 | 질문 하나와 모델 하나. 모델 판이 바뀌면 다시 잰다. 가의 줄을 빼기만 한다 | 같고, 그림 입력이 필요하다 | 같고, 출력을 번호로 묶지 않으면 지어낸 글이 들어갈 위험이 있다 |
| 확장 | 코드 범례(「A = 30점」)를 못 잡는다 | 같다 | 같다 | 코드 범례 5개 표를 찾았다 |

- 권고 [판단](보강): 모델 단독은 들이지 않는다. Gemma 4 예/아니오 확인은 질문을 측정 전에 고정했고 찾은 표를 줄이지 않아 다음 후보로 둔다. 교집합 거르개는 결과를 본 뒤 만든 것이라 같은 자리의 비교 후보로만 둔다. 두 방식 모두 새로 모으는 문서에서 가가 줄을 고른 표를 다른 사람이 판정해 다시 잰 뒤 정한다. 재순위 모델, 글머리표 기호 빼기, 작은 전용 배치 모델은 들이지 않는다.
- 보강 3 결과(사실만, 권고 문장은 결과를 보고 따로 정한다): 딸린 글을 붙여도 되는 목표로 보면 「Gemma 4가 고른 줄 → Gemma 4 딸린 글 확인」(질문 10의 4)이 PDF 97개에서 빠짐없이 붙인 표 22(지금 규칙 12), 무관한 줄을 붙인 표 7(지금 규칙 9)이고, 표 아래 조건 줄을 붙인 표는 늘었다. 「끝 줄 묻기」는 Gemma가 끊는 곳을 늦게 잡아 무관이 많았고, Claude Opus는 빠짐없이 25, 무관 7이었다.
**보강 4 권고** [판단]: 앞의 권고(Gemma 4 예/아니오 확인을 다음 후보로 둠)를 바꾼다. 다음 후보는 「표 뒤 구간 안에서 Gemma 4가 고른 줄을 붙이는」 방식이다.

- 이유 [실측]: 위치는 「어디까지가 후보인가」를, 모델은 「그 안에서 어느 줄이 이 표에 딸린 글인가」를 맡는다. 규칙만 쓰면 빠짐없이 붙인 표가 26개 중 12개이고, 모델만 쓰면 무관한 줄을 붙인 표가 97개 중 17개인데, 둘을 합치면 24개와 5개다(질문 10의 5).
- 먼저 정할 것: 붙이는 대상을 「범례·각주」에서 「표에 딸린 글(조건·단서 포함)」로 넓힐지. 이 방식은 표 아래 조건 줄을 60개 표에 함께 붙인다. 사용자 결정이다.
- 정한 뒤 확인할 것: ① 판정에 쓰지 않은 표를 새로 뽑아 무관한 줄을 붙인 표 비율을 다른 판정자가 다시 잰다. ② 답이 나아지는지는 표 오답 수정 설계의 단계 0(근거를 고정하고 프롬프트만 바꿔 다시 생성)에서 붙인 것과 안 붙인 것을 견준다. 그때까지 지금 규칙을 유지한다.
- 작은 전용 모델을 직접 학습하는 길(큰 모델의 판정을 정답 삼아 작은 분류 모델을 학습)은 지금 권하지 않는다. 공개 모델이 없어 새로 만들어야 하고, 진짜 범례가 있는 표가 판정 자료 26개에 거의 다 들어 있어 학습용과 평가용으로 나누기 어렵고, 유지할 모델이 하나 늘어난다. 다시 볼 조건: 위 방식이 새 표 검증에서 무너질 때, 운영 서버에 Gemma 4를 색인용으로 올릴 수 없을 때.
- 버린 선택지와 이유: 나는 범례가 아닌 조건 줄이 대부분이다. 마2는 잘못이 가의 세 배다. 견줌(글자 모양)은 잘못이 0개지만 각주를 못 찾고(5/34), 글자 모양에 기대지 않는다는 원칙과 어긋난다. 클라우드 API는 학교 문서를 보낼 수 없다.

## 7. 확신도와 다음 확인

- 확신도: 중간 — 방법 여덟 가지를 같은 표 156개로 쟀고 원문 12건을 대조했다. 보강에서 시각 언어 모델 넷을 PDF 표 109개, HWP 표 37개로 더 쟀고 원문 11건을 더 대조했다. 다만 판정이 Claude 한 번이고 사람 확인이 없으며, 진짜가 있는 표 34개 가운데 24개가 PDF 보관 문서라 서비스 색인의 진짜는 5개뿐이다. 「작은 모델 단독은 못하다」는 넷 모두 같은 방향이라 확신도가 높다. 「Gemma 4 확인이 잘못을 줄인다」는 판정 자료 안의 결과뿐이라 중간 아래이고, 교집합 거르개는 사후 조합이라 낮다. 보강 2에서 원문 6건(모델 카드와 공식 저장소)을 더 대조했다.
- 다음 확인:
  1. HWP 로더가 캡션 방향을 읽어 아래쪽 캡션을 표 뒤에 두게 고친 뒤, 가가 그 18개 표에서 무엇을 붙이는지 본다(맥북, 로더 수정 작업 때).
  2. 판정 156개 가운데 진짜 35개와 가가 잘못 붙인 23개를 다른 사람이 한 번 더 판정한다.
  3. 코드 범례(「A = 30점」, 「(고) : 고위험」, 「1등급 - 안전한 상태」)를 잡는 방법이 필요해지면, 칸 값 전체가 짧은 코드인 표만 대상으로 따로 잰다. 시각 언어 모델 넷은 이 5개 표를 모두 찾았지만 조건 줄도 함께 붙였다(질문 8).
  4. Gemma 4 예/아니오 확인과 교집합 거르개: 새로 모으는 문서에서 가가 줄을 고른 표를 다른 사람이 판정하고, 같은 질문·프롬프트와 같은 Gemma 4 12B(QAT)로 다시 잰다(데스크탑, 줄당 약 0.8초). 무관한 줄을 붙인 표가 가보다 확실히 줄고 놓치는 진짜가 1개 안팎이면 들일지 정한다. HWP에서 놓친 「* 차상위계층 확인서류」 같은 서식 각주를 따로 본다.
  5. HWP·DOCX 문서를 쪽 그림으로 바꿀 도구(LibreOffice, 공식 HWP 변환기)를 데스크탑에 들일 때, HWP 표 37개를 그림과 함께 다시 잰다.
- 다시 볼 조건: 표 각주 라벨만 따로 잰 레이아웃 모델의 공개 수치가 나올 때, 서비스 색인에 HWP·DOCX 문서가 늘 때, 범례 관련 질문이 평가셋이나 사용 기록에 생길 때.
