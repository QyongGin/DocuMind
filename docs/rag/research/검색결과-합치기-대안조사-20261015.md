# 검색 결과 합치기 대안 조사 — 실무 제품·논문과 개발셋 오프라인 비교 (M2, 2026-10-15)

> ADR-0032(검색 순서를 사람이 만든 규칙 대신 순위 융합으로) 확정 전에, 표 사실·BM25·벡터 세 검색기의 결과를 하나로 줄 세우는 실무 대안을 찾아 지금 운영 중인 규칙과 실험한 순위 융합(RRF)을 기준으로 비교한다(2026-10-15 사용자 요청: "현직·실무에서 쓰이는 알고리즘이 있는지, 더 나은 선택지는 없는지").
> 관련: ADR-0032, `docs/rag/m2/검색개선-설계-20261014.md` §3(1·3단계), `docs/rag/research/검색개선-근거조사-20261014.md`(순위 융합·재순위 1차 근거)

## 1. 결론

- **합치기는 순위 융합으로 둔다.** 실무 검색 제품 다섯 곳이 모두 제공하고 상수는 대개 k=60이다. 우리 개발셋에서 규칙보다 의미 있게 낫고(정답 청크 상위 5개 포함 72 → 101/121, p<0.0001), 다른 합치기 방식(보르다 합산·가중 순위 융합·번갈아 끼우기·벡터만)은 순위 융합과 같은 수준이다. [원문·실측]
- **순서를 다듬는 일은 학습된 재순위 모델이 맡는다.** 순위 융합 뒤에 재순위(bge-reranker-v2-m3)를 붙인 경우만 의미 있게 앞섰다(101 → 114, p=0.002). Azure AI Search는 합친 뒤 의미 재순위를 붙이는 구조를 문서에 적고, Intercom Fin은 LLM 라벨로 학습한 cross-encoder로 상용 재순위를 이겼다(지연 P50 약 150ms 유지). [원문·실측]
- **점수 결합(볼록 결합·분포 기반 결합)은 근거가 있지만 아직 못 쟀다.** Bruch 외(ACM TOIS)는 두 검색기에서 볼록 결합이 순위 융합보다 낫다고 보고했다. 평가 기록에 검색기별 점수가 없어 M2 3단계에서 점수를 기록한 뒤 재순위와 함께 비교한다. [원문·판단]

## 2. 실무 제품 (공식 문서, 2026-10-15 확인)

| 제품 | 제공하는 합치기 | 문서가 말하는 쓰임 |
|---|---|---|
| Azure AI Search | 순위 융합만(점수 1/(rank+k), "k to a small value, such as 60"), 벡터 질의별 가중치 | 순위 융합 뒤 의미 재순위(semantic ranker)를 따로 붙임 |
| Elasticsearch | RRF retriever(rank_constant 기본 60, 9.2부터 검색기별 weight) · linear retriever(정규화 minmax·l2_norm 후 가중합) | 둘 중 고름. 정규화 없음은 "may bias the result set towards lexical matches" |
| Qdrant | RRF(가중치 v1.17.0부터) · DBSF(평균±3표준편차를 끝점으로 정규화 후 합) | 평가셋이 없으면 기본 가중치 권장 |
| Milvus | RRFRanker(k 기본 60) · WeightedRanker(arctan으로 0~1 정규화 후 가중 평균) | 중요도가 불분명하면 RRF |
| Weaviate | relativeScoreFusion(점수 결합, v1.24부터 기본) · rankedFusion | 점수 결합이 기본 |

## 4. 개발셋 오프라인 비교 (실측)

- 방법: 실험 E1(EXAONE + 순위 융합, 2026-10-14) 실행 기록에 남은 검색기별 결과 순서(표 사실 5 · BM25 5 · 벡터 약 28)로 각 방식을 다시 합치고, AI 서버처럼 표 사실을 부모 원본 청크로 펼친 뒤, 정답 청크가 상위 k에 든 문항을 셌다(채점기와 같은 `_covers` 판정, 허용 근거 문서만). 스크립트 `Assets/eval/work/m2/fusion_offline.py`(로컬), 결과 `fusion_offline.json`.
- 레이아웃 분석으로 만든 표 사실은 기록에 부모 청크 id가 없어 같은 문서의 레이아웃 청크 중 글 낱말이 가장 많이 겹치는 것으로 추정했다. 이 추정으로 E1의 실제 펼친 순서를 끝까지 재현한 문항 161/177, 상위 10위까지 176/177.
- 개발셋 본 121문항, 정답 청크 상위 5개 포함(같은 문항 짝 비교, 순위 융합 기준):

| 방식 | 상위 5 | 순위 융합만 / 상대만 | 판정 |
|---|---|---|---|
| 사람이 만든 규칙(지금 운영, 베이스라인 최종 후보) | 72 | 34 / 5 | 순위 융합이 의미 있게 나음, p<0.0001 |
| BM25만 | 84 | — | — |
| **순위 융합 k=60(E1)** | **101** | 기준 | — |
| 번갈아 끼우기(표·BM25·벡터) | 104 | 3 / 6 | 같은 수준, p=0.51 |
| 가중 순위 융합(5겹 교차 검증으로 가중치 선택) | 106 | 1 / 6 | 같은 수준, p=0.125 |
| 보르다 합산 | 107 | 1 / 7 | 같은 수준, p=0.070 |
| 벡터만 | 109 | 4 / 12 | 같은 수준, p=0.077 |
| **순위 융합 → bge-reranker-v2-m3(R1)** | **114** | 2 / 15 | 재순위가 의미 있게 나음, p=0.002 |

- 순위 융합 상수: k=10·30·100·1000은 모두 101, k=1만 105. BM25·표 사실 목록이 5개뿐이라 상수의 영향이 작다.
- 벡터만(109)이 순위 융합(101)보다 방향상 높고, BM25만 84 · 표 사실만 13이다. 약한 두 목록을 같은 무게로 섞으면 벡터의 좋은 결과가 밀린다. 개발셋에서 고른 가중치도 벡터 쪽이 컸지만(교차 검증 선택 예: 표 1 · BM25 0.5 · 벡터 3), 남은 문항에 적용하면 같은 수준이었다.
- 상위 3개: 순위 융합 85 → 재순위 105, 상위 10개: 115 → 119. 근거를 적게 넣을수록 재순위의 이득이 크다.

## 5. 대안 판단

| 방법 | 판단 | 이유 |
|---|---|---|
| 순위 융합(RRF, k=60) | 채택 — 후보 합치기 | 실무 기본 도구, 설정이 거의 없음, 규칙보다 의미 있게 나음 |
| 학습된 재순위(cross-encoder) | 채택 후보 — M2 3단계 핵심 | 실무 구조, 우리 데이터에서 의미 있게 나음. GPU 메모리·지연을 3단계에서 실측 |
| 점수 결합(볼록 결합·DBSF) | 보류 — 3단계에서 비교 | 논문 근거 있음, 점수 기록이 없어 못 잼 |
| 가중 순위 융합 | 보류 | 같은 수준이고 개발셋에 맞춘 가중치가 될 위험. 재순위 뒤 다시 본다 |
| LLM 재순위 | 버림(직접 사용) | 답 생성 전 LLM 호출이 늘어 지연·비용이 큼. 대신 재순위 학습 라벨로(Fin 방식) 학습 단계에서 검토 |
| 순위 학습(LambdaMART 등) | 버림(지금) | 라벨이 개발셋뿐이라 과적합. 운영 기록이 쌓이면 다시 |
| 질문 유형별 분기(표 질문 → 표 검색) | 버림 | 분류가 사람이 만든 규칙으로 돌아가 지운 규칙과 같은 위험 |

## 6. 한계와 다음

- 검색 단계 측정(정답 청크가 상위 k에 들었나)이며 답 정확도가 아니다. 개발셋만 썼다(ADR-0018). 일부 순서는 추정이다(§4).
- 서버가 BM25·표 사실을 5개씩만 가져와 합치기 방식의 차이가 작게 나왔을 수 있다.
- 다음(M2 3단계): ① 평가 기록에 검색기별 점수와 표 사실의 부모 청크 id를 더한다(평가 요청에서만) ② 검색만 다시 돌려 볼록 결합·DBSF를 순위 융합과 비교 ③ 같은 후보에 재순위 모델 셋(bge-reranker-v2-m3, 한국어 학습판, Qwen3-Reranker-0.6B)과 후보 수·벡터 위주 후보를 비교 ④ 가장 나은 조합만 생성까지 돌려 정답률·오답률·응답 시간 짝 비교.
