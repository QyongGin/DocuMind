## 1. 첫 30문항으로 재는 것

설계에서 "첫 30문항에서 잰다"고 미뤄 둔 값이다. 첫 30문항은 이 값을 재는 시험 묶음이라, 나머지 220문항의 축소판이어야 한다.

| 잴 것 | 미뤄 둔 결정 | 쓰는 곳 |
|---|---|---|
| 문항당 휴먼 리뷰 시간, 고친 비율 | ④·⑥ | 2배 이상 걸리면 총 문항 수를 다시 정한다(⑥-9) |
| 이중 라벨링 불일치·헛걸음 비율(형식별) | ⑦·⑦-1·⑦-2 | 사람이 볼 문항 수 추정(약 100) 검증 |
| 긴 문서에서 근거를 못 찾는 비율 | ⑦-3 | '못 찾으면 위치 알려 주기'를 더할지 |
| 답 없는 문항 후보가 부재 확인으로 빠지는 비율 | ③ | 답 없는 문항 만드는 법 손질 |
| 답 유형이 애매한 문항 비율 | ① | 50문항쯤에서 10%를 넘으면 정의 손질 |

## 6. 색인 글을 맥북에서 재현해 진행 ✅ (2026-10-10 사용자 결정)

**맥락**: 정답·인용은 챗봇이 보는 색인 글로 써야 한다(§3). 설계(결정 ④-6)는 "색인 글은 데스크탑을 켤 때 한 번 내보낸다"였고, 데스크탑을 켤 수 없어 첫 30문항이 멈춰 있었다.

**결정**: 서비스 업로드 파이프라인(ai-server)의 임베딩 전 단계(파일 변환 → 청크 나누기 → 중복 정리 → 짧은 청크 합치기 → 겹침 → 색인 항목 만들기)를 맥북에서 돌려 색인 글을 재현하고, 내보내기(`export-index`)와 같은 방식으로 문서별 글을 만든다. 정답·인용 쓰기, 자동 검증(`--index-dir`), 부재 확인 ①, 이중 라벨링, 휴먼 리뷰를 이 글로 진행한다. **버전 고정 전에** 데스크탑을 켜서 실제 색인 글을 내보내 재현 글과 비교하고, 다른 문서가 있으면 그 문서 문항의 인용만 다시 맞춘다.

**근거**
- [코드] 색인 글은 임베딩 전 단계에서 정해지고, GPU는 임베딩에만 쓴다. 내보내기는 `documents` 컬렉션의 원문 청크(표 사실은 부모 청크 글)를 청크 순서대로 잇는다.
- [실측] 색인할 때의 코드(develop `84f4fa4` + #139 브랜치)와 지금 develop(`15e776c`)의 변환·청크 코드가 같다(바뀐 것은 검색 캐시 무효화뿐). 맥북의 OpenDataLoader도 같은 판(2.2.1).
- [실측] 700문서 재현 집계가 색인 보고서(`서비스-전체-색인-및-측정-20261004.md`)와 정확히 같다: 원문 청크 3,206 · 표 사실 45,878 · 출처 블록 3,654 · 청크 0 문서 2개. 맥북 99초(PDF 93초).
