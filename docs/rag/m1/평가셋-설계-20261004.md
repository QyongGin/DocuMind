- 학교 FAQ 85개 중 84개는 제목이 질문 문장이 아니라 **낱말 나열**(예: "○○·○○ 방법·기간")이고, 본문은 짧은 답 문단이다. 입시 FAQ 11개만 질문 문장이다.

- 따라서 "FAQ 문장 그대로 묻는 문항"은 학교 FAQ에서는 "FAQ 제목 낱말을 그대로 쓴 질문"으로 읽어야 한다. 쉬운 문항의 정확한 정의는 ⑥에서 정한다.

### 2.5 외부 근거 — CRAG (Meta, 2024) [원문: arXiv 2406.04744v2 HTML 본문]

- 질문 유형 8개를 한 문항에 하나씩 매긴다(Simple, Simple w. condition, Set, Comparison, Aggregation, Multi-hop, Post-processing heavy, False Premise). 분야·변화 속도(Real-time·Fast-changing·Slow-changing·Static)·인기도는 유형과 따로 나눠 집계한다(Table 2·3·4).
- 답을 perfect·acceptable·missing·incorrect로 나누고 1·0.5·0·−1점을 준다. 원문: "we penalize hallucinated answers and prefer missing answers to incorrect ones". 정확·환각·모름 비율을 따로 보고한다(§4.1).
- 자동 채점은 두 단계다. 정답과 정확히 같으면 맞음, 아니면 LLM 둘이 판정한다(자기 선호를 피하려고 두 모델). 사람 판정 대비 F1 94.7%(ChatGPT)·98.9%(Llama 3)(§4.2).
- 데이터를 validation 30%·public test 30%·private 40%로 나누고, 최종 평가는 private으로 한다(§4.2 Test data split).

### 2.6 대기업 사례 조사 [원문: `docs/rag/research/대기업-RAG-구현-평가-사례조사-20261004.md`]

- 해외 7곳·국내 4곳의 핵심 주장을 원문 글자로 대조했다(초안 오기 13곳을 고침, 보고서 §5).
- 평가 질문은 실제 질문 + 전문가 손질이 기본이다(Microsoft "Choose real content over synthetic content.", Uber 전문가가 고른 100여 개 질문을 배포 관문으로 씀).
- 틀린 답을 모름보다 무겁게 친다(CRAG −1/0). Google 연구에서 큰 모델은 근거가 모자라도 틀린 답을 내고, 작은 모델은 근거가 있어도 거절·환각이 잦다.
- 판정 모델도 틀린다. 공개된 사람 대비 수치는 CRAG F1 94.7%·98.9%, Google 93%, 올거나이즈 오차 약 8%다.
- LinkedIn은 평가의 첫 장벽이 '판정 지침 만들기'였고, 평가자 점수의 일관성이 핵심이라고 썼다 → ④.
- 테스트셋(비공개) 몫은 공개 벤치마크(CRAG 30/30/40)만 두고, 회사들은 운영 피드백으로 평가한다. 우리는 시범 운영이 없어 운영 피드백이 없다 → ⑤.
- 공개 문항 수: Uber 100여 개(문서 40여 개), 올거나이즈 300개(분야 5개 × 60), Google 판정기 검증 115개. "AWS 150~300개 권장"은 원문에서 찾지 못했다 → ⑥.

- [원문] CRAG(arXiv 2406.04744v2) Table 2·3·4: 유형은 문항마다 하나, 변화 속도·분야는 따로 집계 — 같은 두 층 구조다.
- [실측] 학교 FAQ 85개 중 25개는 제목에 '방법·신청·절차', 입시 FAQ 11개 중 5개는 '할 수 있나요·가능한가요'류(낱말 일치, 대략) → 절차·예/아니오를 모양으로 따로 둔다.

**네 관점**
- 서비스: 실제로 많이 묻는 모양(절차·예/아니오)이 따로 잡혀 점수가 사용자가 겪는 품질을 반영한다.
- 비즈니스: '모르면 모른다고 한 비율', '표 값 정답률', '올해 값으로 답한 비율'을 따로 보여 줄 수 있다. 학교가 가장 걱정할 틀린 전형료·지난해 값 문제에 직접 답하는 숫자다.
- 유지보수: 담당자가 학기마다 문항을 바꿀 때 모양 하나를 고르고 태그만 붙이면 된다. 한 칸 고르기처럼 사람마다 갈리지 않는다.
- 확장: 새 원인(예: 후보 선택 단계 탈락)이나 M6 내부 문서는 태그만 더하면 되고 채점 규칙은 그대로다. M2 학습 데이터 원본 레코드도 같은 칸을 써서 평가와 분포를 맞출 수 있다.

**확신도**: 중간~높음. **확인 시점**: 초안을 50문항쯤 만들었을 때 모양이 애매한 문항 비율을 센다. 10%를 넘으면 모양 정의를 고친다.

### ② 정답 적는 법과 채점 방식 — 핵심 사실 + 규칙 기반 채점, 못 정한 것만 사람 ✅ (2026-10-04 사용자 결정, D안)

**결정**

1. **정답 칸**: 정답 문장(사람이 읽는 1~2문장) + 필수 사실(모양별, 사실마다 허용 표기 여러 개) + 금지 값(지난해 값·옆 칸 값처럼 틀리기 쉬운 값, 있을 때만).
2. **판정 결과**: 맞음 · 일부 · 모름 · 틀림. 규칙이 못 정하면 '애매'로 두고 사람이 넷 중 하나로 판정한다. 답이 비었거나 중간에 멈추면 '빈 답'으로 따로 센다(시스템 고장).
3. **모양별 규칙**

| 모양 | 정답 칸 | 맞음 | 일부 | 틀림 |
|---|---|---|---|---|
| 값 | 값 1개 + 허용 표기 | 값이 있고 금지 값이 없음 | — | 금지 값이 있음 |
| 목록 | 항목 n개 | 전부 | 일부(틀린 항목 없음) | 금지 항목이 있음 |
| 절차 | 필수 단계 n개 | 전부 | 일부 | 금지 단계가 있음 |
| 예/아니오 | 가부 + 핵심 조건 | 가부와 조건 | 가부만 | 가부가 반대 |
| 설명 | 핵심 낱말 2~3개 | 전부 | 일부 | 금지 낱말이 있음 |
| 거절 | ③에서 정함 | 모른다고 하고 값을 지어내지 않음 | — | 값을 지어내거나 근거 밖 지식으로 답함 |

   - 모양과 상관없이: 답이 거절 문구면 '모름'(답이 있는 문항이면 과잉 거절). 필수 사실도 금지 값도 거절 문구도 없으면 '애매'. 거절 문구와 다른 내용이 함께 있으면 '애매'.
4. **지어낸 숫자 감시**: 답 속 금액·날짜·인원·학점 같은 숫자가 모델이 받은 근거(프롬프트)에 없으면 '지어낸 숫자'로 표시하고 '애매'로 보낸다. 계산이 필요한 '비교·계산' 문항은 사람이 본다.
5. **사람 판정 재사용**: 문항과 정규화한 답 글자가 같으면 저장한 판정을 다시 쓴다(temperature 0이라 같은 조건이면 같은 답).
6. **근거**: 대장 ID + 인용 글(색인 원문 그대로). 같은 사실이 다른 서비스 색인 문서에도 있으면 '허용 근거'로 함께 적는다. 청크 번호는 적지 않는다(M2에서 청크가 바뀌어도 평가셋 파일 유지). 채점기는 검색 기록 단계(검색 상위 → 표 우선 → 최종 후보 → 프롬프트)와 답의 출처에서 "허용 근거 문서의 후보에 필수 사실이 있나"를 보고 실패 위치를 붙인다: 통과 / 검색 실패 / 후보 선택 탈락 / 생성 실패 / 외운 답 의심(검색은 실패했는데 맞음). 근거 청크가 2,048토큰을 넘으면 '임베딩 잘림', 답이 출력 상한(512토큰)에서 끊기면 '답 잘림'을 더한다.
7. **지표**: 정답률 = 맞음 ÷ 답이 있는 문항(일부 비율은 따로) · 환각률 = 틀림 ÷ 전체 문항(답 없는 문항에서 지어낸 답 포함, 지어낸 숫자 수는 따로) · 과잉 거절률 = 모름 ÷ 답이 있는 문항 · 출처 정확도 = 화면 출처에 허용 근거 문서가 든 문항 비율 + 출처 중 허용 근거 문서 비율. 하나로 합친 점수(예: CRAG의 1·0.5·0·−1)는 12번 베이스라인에서 '의미 있는 차이'와 함께 정한다.
8. **판정 모델**(다른 AI가 채점)은 지금 쓰지 않는다. 사람 판정이 쌓이면(예: 300건) 사람과의 일치율을 재서 M2 반복 측정의 보조로 쓸지 정한다.

**버린 대안**
- A. 낱말 포함(예전 방식): 합성 예에서 맞는 답 '3만 원'을 틀림, 틀린 답 '30,000원 또는 25,000원'을 맞음으로 판정하고, 모름과 틀림을 가르지 못한다.
- B. 판정 모델이 전부: 같은 답에 판정이 바뀔 수 있고 판정 모델도 따로 검증해야 한다. 데스크탑 12GB에 후보 모델과 임베딩이 이미 약 10.9GB, 외부 서비스면 학교 문서와 답이 밖으로 나간다.
- C. 사람이 전부: 후보 5개 × 수백 문항 × 여러 번은 할 수 없다.

**근거**
- [실측·코드] 예전 채점기: '1992년'·'65학점' 가짜 실패(decisionLog 2026-06-29), 정답 낱말이 없으면 판정 안 함(None), 거절은 문구 3개로만 판정(`ai-server/evaluate_rag.py:21`).

**네 관점**
- 서비스: 가장 해로운 틀린 숫자(전형료·날짜·인원)를 금지 값과 지어낸 숫자 감시로 따로 잡고, 목록 일부만 답한 경우를 '일부'로 나눠 사용자가 느끼는 품질과 맞춘다.

- 유지보수: 담당자는 문항마다 정답 값·허용 표기·금지 값만 적으면 되고, 채점 이유를 규칙으로 설명할 수 있다. 판정 모델 버전에 따라 점수가 흔들리지 않는다.

**한계**: 숫자가 아닌 지어낸 말(예: 없는 절차 단계를 덧붙임)은 규칙이 못 잡는다 → 12번 베이스라인 때 '맞음' 판정 중 무작위 30개를 사람이 다시 봐서 놓친 비율을 잰다.

**확신도**: 중간. **확인 시점**: 12번 베이스라인에서 '애매' 비율을 잰다. 30%를 넘으면 규칙을 보강하거나 판정 모델을 시험한다.

### ③ 답 없는 문항 만드는 법 — 가까운 빈칸·잘못된 전제 주력 + 두 겹 부재 확인 ✅ (2026-10-04 사용자 결정, C안)

**결정**

1. **종류 넷**: 가까운 빈칸(관련 문서는 있지만 물은 값이 없음 — 연도 바꾸기, 문서에 없는 칸 묻기, 다른 기관) · 잘못된 전제(없는 학과·전형·제도를 있는 것처럼) · 자료 없는 학교 질문 · 학교와 무관(소수). 가까운 빈칸과 잘못된 전제가 주력이다. 종류별 비율과 전체에서의 비율은 ⑥에서 정한다.
2. **만들기**: 가까운 빈칸·잘못된 전제는 평가 문서의 실제 내용을 비틀어 만들고, 그 문서를 '가까운 문서'(대장 ID)로 적는다. 답 있는 문항과 같은 주제·말투로 써서 겉모양으로 구별되지 않게 한다.
3. **두 겹 부재 확인**: ① 챗봇이 볼 수 있는 글 전체(서비스 색인 700개 문서의 색인 글)에서 핵심 낱말을 검색해 걸린 문서를 사람이 본다. 답이 있으면 답 없는 문항에서 뺀다. 답이 학습 몫 문서에 있으면 답 있는 평가 문항으로도 바꾸지 않는다(평가 근거는 평가 몫에서만). ② 데스크탑을 켤 때 검색 기록으로 상위 후보를 확인한다. 평가셋 파일에 '부재 확인 기록'(검색 낱말·걸린 문서 수·확인 날짜·색인 백업 이름)을 남긴다.
4. **다시 확인**: 서비스 색인에 문서가 늘거나 바뀌면 같은 검색을 다시 돌려, 새로 걸린 문항만 리뷰 대상으로 표시한다(학기 측정에 포함).
5. **채점(② 거절 규칙 보충)**: 모른다고 하거나 전제가 틀렸다고 밝히고 값을 지어내지 않으면 맞음. 문서에 있는 가까운 정보를 '지난해 값'처럼 밝혀 덧붙이는 것도 맞음, 그 값을 물은 값처럼 말하면 틀림(규칙이 못 가르면 '애매' → 사람). **문서 밖 일반 지식으로 답하면 맞는 말이어도 틀림**(서비스 방침: 학교 안내는 출처 있는 답만, 사용자 확인).

**버린 대안**
- A. 학교와 무관한 질문 위주: 만들기·확인은 쉽지만 검색이 아무것도 못 가져와 거절하기도 쉽다. 변별력이 없다.
- B. 확인 없이 '없을 것 같은' 질문을 씀: 실제로 답이 어딘가 있으면 맞게 답한 챗봇을 환각으로 벌준다. 서비스 색인 700개를 기억으로 판단할 수 없다.

**근거**
- [원문] SQuAD 2.0(arXiv 1806.03822 초록): 답 없는 질문 5만여 개를 "written adversarially by crowdworkers to look similar to answerable ones", 기존 자동 생성 답 없는 질문은 "easy to identify". SQuAD 1.1에서 F1 86%인 모델이 2.0에서 66%.
- [원문] CRAG: False Premise를 유형 하나로 따로 둔다(4,409문항 중 525개, 12%, Table 4). "The non-perfect coverage … allows us to test whether the RAG solutions admit 'I don't know' when the retrieval results do not contain the necessary information."
- [실측] 예전 평가셋 답 없는 문항 30문항 중 1개(3%) — '올해 합격 등급컷'(지난해 입시결과만 있는 가까운 빈칸). 후보 모델 시험에서 이 질문에 EXAONE은 거절 + 일반 안내, Gemma 4 E4B는 문맥 4,096에서 1토큰 멈춤(8,192에서는 거절) → 모델마다 반응이 달라 변별력이 있다.
- [실측] 서비스 색인 700개 중 474개가 학습 몫 → 평가 문서만 보고는 '없음'을 판단할 수 없다.

**네 관점**
- 서비스: 관련 근거가 잔뜩 나오는데 물은 값만 없을 때 비슷한 숫자를 갖다 붙이는 실제 위험을 재서, '틀린 답을 자신 있게 함'(B3)이 줄었는지 확인할 수 있다.
- 비즈니스: "문서에 없는 것을 물으면 지어내지 않는다"를 숫자로 보여 주고, 확인 기록으로 "그 질문은 정말 문서에 없었나?"라는 반문에 답한다.
- 유지보수: 문서가 늘면 같은 검색이 다시 돌아, 답이 생긴 답 없는 문항을 담당자가 놓치지 않는다.
- 확장: M2 학습 데이터의 거절 예시도 학습 몫 문서에서 같은 종류·같은 확인으로 만든다. M3 권한이 생기면 '볼 수 없는 문서' 종류를 더한다.

### ④ 리뷰 방법과 저장 — 자동 검증 → 리뷰 화면 → 평가셋 파일 한 파일 + 지문 고정 ✅ (2026-10-04 사용자 결정, C안)

**결정**

1. **저장**: `Assets/eval/`(git 제외)에 평가셋 파일(JSONL, 문항 한 줄) 하나를 둔다. M2 학습 데이터 파일도 같은 형식에 '학습/평가' 칸으로 구분한다. 학교 글이 든 파일은 공개 저장소·외부 서비스에 올리지 않는다. 검사·화면·채점 코드는 저장소에 두고, 테스트는 합성 데이터만 쓴다.
2. **자동 검증(사람이 보기 전)**: 인용이 색인 원문에 글자 그대로 있나 · 필수 사실이 인용 안에 있나 · 근거 문서가 평가 몫이고 서비스 색인에 있으며 `[평가질문제외]`가 아닌가 · 모양·태그 값이 목록 안에 있나 · 같은 질문이 겹치지 않나 · 답 없는 문항에 부재 확인 기록이 있나. 고친 문항은 다시 검사한다.
3. **리뷰 화면**: 맥북 브라우저로 여는 HTML 파일 하나(서버·인터넷 없음). 근거 원문을 앞뒤 글과 함께 보여 주고 인용에 색을 칠한다. 문항마다 승인·고침·버림과 이유를 남기고, 결과는 리뷰 기록 파일로 저장해 스크립트가 평가셋 파일에 합친다.
4. **지침**: 판정 예시가 든 리뷰 지침(1~2쪽)을 먼저 쓰고 첫 30문항으로 다듬는다. 첫 30문항에서 문항당 리뷰 시간과 고친 비율을 재서 ⑥ 문항 수에 쓴다.
5. **고정**: 리뷰가 끝나면 버전 이름과 SHA-256 지문을 남긴다(용도 고정 때 `split_frozen_20261002.txt`와 같은 방식). 고치면 새 버전과 바뀐 문항 기록을 남긴다. 베이스라인 기록에는 평가셋 버전과 색인 백업 이름을 함께 적는다.
6. **색인 글**: 근거 원문 표시와 부재 확인에 쓸 색인 글은 데스크탑을 켤 때 한 번 내보낸다. 그 전에는 맥북의 원본 파일에서 뽑은 글로 초안을 쓴다.

**버린 대안**
- A. 엑셀 왕복(대장 리뷰 방식): 엑셀이 일부 값을 날짜로 바꾸고 끌 수 없다(Microsoft 도움말 원문 "2/2 changes to 2-Dec … Unfortunately there is no way to turn this off."). 허용 표기·근거가 여러 개라 한 칸에 뭉치고, 근거를 보려면 원본 파일을 따로 열어야 한다.
- B. 편집기에서 평가셋 파일을 직접 고치기: 형식 실수가 잦고 근거를 보며 고치기 어렵다.

**근거**
- [원문] LinkedIn(2024-04-25): 평가의 첫 장벽은 "developing guidelines", "Ensuring these details were consistent was key for the uniformity of our annotator scores."
- [원문] Microsoft RAG preparation phase(2025-10-10): 시험 질문에 근거의 "page and the actual text"를 함께 기록하고, 그래야 "evaluate every stage of the RAG solution".
- [원문] 우아한형제들(2026-03-10): "먼저 소수의 쿼리로 직접 품질을 확인한 뒤 자동화 평가를 도입하는 순서가 현실적입니다."
- [실측] 용도 고정(#124)에서 SHA-256 지문으로 나눔을 고정한 방식이 이미 있다.

**네 관점**
- 서비스: 리뷰의 질이 평가셋의 질이다. 근거 원문을 옆에 두면 정답이 근거와 다른 문항이 걸러진다.
- 비즈니스: "모든 문항을 사람이 근거 원문과 대조했고 기록이 남았다"를 학교에 보일 수 있다. 학교 문서는 공개 저장소·외부 서비스로 나가지 않는다.
- 유지보수: 같은 화면을 M2 학습 데이터 무작위 200개 리뷰, 학기 측정 문항 교체에 다시 쓴다. 학교 담당자도 엑셀 함정 없이 같은 절차로 리뷰한다. 지침이 있어 리뷰어가 바뀌어도 기준이 같다.
- 확장: 평가셋 파일을 채점기(11번)가 바로 읽고 학습 데이터 파일과 형식이 같다. 버전·지문으로 베이스라인과 묶여 다시 잴 수 있다.

**비용·위험**: 리뷰 화면과 검사 스크립트를 새로 만든다. 색인 글을 한 번 내보내야 한다(데스크탑).

**확신도**: 중간~높음. **확인 시점**: 첫 30문항에서 문항당 시간과 고친 비율을 잰다.

### ⑦ 리뷰 범위 — 사람은 휴먼 리뷰 대상만(약 100) ✅ (2026-10-05 사용자 결정, '전수 리뷰' 번복)

**번복 대상**: "평가 몫은 Claude 초안 → 사용자 전수 리뷰"(총괄계획 §7 2026-09-30, 설계 6단계 안건 4 '만드는 도구'·'휴먼 리뷰').

**왜 바꿨나**: 사용자: "내가 일일이 시험지가 정말 정답이 맞는지 확인하기에는 시간 비용이 너무 크다", "꼭 봐줘야 하는 문항만 남겨봐". 전수 리뷰는 약 9시간(문항당 2분 가정)이다. 대신 무엇이 사람 눈을 꼭 필요로 하는지 네 경우로 따졌다(원서비 예, 진짜 답 30,000원):

| | 챗봇이 맞게 답함 | 챗봇이 틀리게 답함 |
|---|---|---|
| 정답 맞음 | 맞음으로 나옴 — 정상 | 틀림으로 나옴 — 정상(챗봇 문제) |
| 정답 틀림 | 틀림으로 나옴 — 실패를 볼 때 정답 오류가 드러남 | **맞음으로 나옴 — 결과만 보고는 알 수 없음** |

정답만 틀린 경우는 결과에 드러나므로 나중에 잡을 수 있다. 정답과 챗봇이 **같이** 틀린 경우만 숨는다(같은 원문을 똑같이 잘못 읽을 때). 그래서 그 경우를 잡는 장치만 남긴다.

**결정**

1. **사람이 보는 문항(약 100, 추정)**: ① 이중 라벨링에서 정답과 다르게 읽은 문항(또는 규칙이 '애매'로 판정) ② 테스트셋 답 없는 문항 ③ 경고 문항(부재 확인에 걸림, 자동 검증 경고) ④ 표본 30 — 테스트셋의 자동 승인 문항에서 무작위로 뽑는다. 표본에서 2개 이상 틀리면 30개를 더 보고, 그래도 오류가 많으면 테스트셋 전수로 넓힌다.
2. **자동 승인**: 위에 들지 않은 문항(약 246)은 자동 검증과 이중 라벨링 통과로 승인하고 `review.status = 자동 승인`과 이유를 남긴다. 개발셋 자동 승인 문항은 M2에서 챗봇이 틀린 문항을 볼 때 정답도 함께 확인한다.
3. **이중 라벨링**: 비교 후보(EXAONE·A.X 4.0 Light·A.X 3.1 Light·Gemma 4 E4B·Qwen3-8B)가 **아닌** 모델이, 서비스 파이프라인과 **다른 방법으로 읽은 원본 글**(PDF는 다른 추출기, HTML은 본문 글, HWP는 olefile 글)로 질문에 답하고, 결정 ②의 규칙으로 정답과 비교한다. 후보 모델을 쓰면 그 모델과 정답이 같이 틀린 문항에서 그 모델이 점수를 얻는 쏠림이 생기고, 같은 추출 글을 쓰면 추출 오류가 정답·이중 라벨링·챗봇에 함께 들어간다. ~~모델은 2단계에서 시험해 정한다(후보: Kanana 1.5 등 Apache 2.0 한국어 모델).~~ → **담당은 다른 세션의 Claude, 정답을 보지 않고 질문과 다른 읽기 원본만 받아 푼다**(2026-10-05 사용자 결정, 아래 ⑦-1). 읽는 방법은 ⑦-2.
4. **자동 검증 추가**: 연도 시험 문항의 금지 값이 지난해 판(2026 모집요강) 원문에 실제로 있는지 확인한다.

### ⑦-1 이중 라벨링 담당 — 다른 세션의 Claude, 정답 안 보고 ✅ (2026-10-05 사용자 결정)

**결정**: 이중 라벨링은 정답을 쓴 세션과 **다른 Claude 세션**이 한다. 그 세션에는 **질문과 다른 방법으로 읽은 원본 글만** 담은 작업 단위를 주고, 정답(답·핵심 사실·인용)와 초안을 쓴 대화는 주지 않는다. 그 세션의 답을 결정 ②의 규칙 기반 채점(PR 1 코드)으로 정답과 비교해 다르면(또는 '애매'면) 사람이 본다. Claude Chat에 손으로 붙여 넣는 방식은 쓰지 않는다(약 350문항, 다시 하기 어려움). 평가셋 파일 `second_annotation.model`에 모델 이름과 '다른 세션'을, `second_annotation.reader`에 읽은 방법을 적는다.

**처음 추천과 바꾼 이유** (문제 중심 기록)
- 처음 추천은 Mi:dm 2.0 Base(KT, MIT, 11.5B)였다. 근거는 "정답을 쓴 Claude와 **다른 모델**이어야 같이 틀리지 않는다"와 제3자 지문 읽기 점수(W&B 호랑이 4 KorQuAD 85.2)였다.
- 사용자가 되물었다: "교차 모델은 너보다 사양이 낮은데, 네가 이해 못 한 걸 그 모델이 이해하고 오류를 잡아낸다고? 차라리 다른 세션의 클로드에 맡기는 게 낫지."
- 정답 오류를 종류별로 다시 따졌다(아래 표). 이중 라벨링이 실제로 잡는 것은 **잘못 읽힌 글**과 **옮겨 쓰다 낸 실수**이고, 둘 다 확인자가 더 똑똑할 필요 없이 **다른 입력으로 새로 풀기만** 하면 잡힌다. Claude가 규정을 잘못 이해한 경우는 성능이 낮은 모델도 거의 못 잡는다(우연히 다를 때만). 반면 성능이 낮은 모델은 표를 서툴게 읽어 **헛걸음**(정답이 맞는데 다르다고 나와 사람이 봄)을 늘려, 결정 ⑦의 목적(사용자 시간 줄이기)과 부딪친다. → '다른 모델'이라는 원칙을 너무 앞세운 추천이었다.

| 정답 오류 종류 (가나대학 예) | Mi:dm 2.0 Base (다른 읽기) | 다른 세션 Claude (다른 읽기, 정답 안 봄) |
|---|---|---|
| 글이 잘못 읽힘 (표 칸이 빠져 납부 마감 3월 7일 → 3월 5일) | 잡음, 헛걸음 많음(표 읽기 서툶) | 잡음, 헛걸음 적음 |
| 옮겨 쓰다 실수 (옆 줄 값을 씀) | 잡음, 헛걸음 많음 | 잡음(새로 풂) |
| 규정을 잘못 이해 (조건 하나 놓침) | 거의 못 잡음 | 못 잡음(같은 식으로 이해) → **테스트셋 표본 30이 맡음** |
| 데스크탑 | 켜야 함 | 안 켬 |

**정답을 보지 않는 이유**: 답을 보여 주고 "맞나요?"라고 물으면 그대로 따라가기 쉽다(답안지를 펴 놓고 숙제를 검사하는 것과 같다). 질문만 받아 스스로 풀어야 정답과 어긋난 곳이 드러난다.

**다른 읽기를 쓰는 이유**: 정답을 쓰는 Claude와 챗봇은 둘 다 서비스가 바꾼 글(색인 글)을 본다. 그 글에서 표 칸이 밀리면 둘이 같이 틀리고 채점은 '맞음'이 된다. 확인하는 쪽은 같은 원본을 다른 프로그램으로 바꾼 글을 봐야 이 오류가 드러난다.

**버린 대안**
- Mi:dm 2.0 Base(처음 추천): 위 표 — 잡는 오류는 같고 헛걸음이 많으며 데스크탑 12GB에 빠듯하다(계산 약 11.5GB, 실측 안 함). 비교 후보 보류 목록에 있어 나중에 후보가 되면 바꿔야 한다.
- Kanana 1.5 8B: 메모리 여유는 있으나 제3자 지문 읽기 근거가 없다. 헛걸음 문제는 같다.
- gpt-oss-20b: 12GB를 넘어 일부 CPU로 돌아 느리고 사고 모드 모델이다.
- 외부 유료 API(GPT·Gemini 등): 비용, 학교 문서가 새 외부 서비스로 간다, 인계 뒤 학교가 유료 계정이 필요하다.
- 같은 세션의 Claude가 자기 정답 확인: 초안을 쓴 대화가 남아 있어 그대로 따라간다.
- Claude Chat에 붙여 넣기: 350문항을 손으로 옮겨야 하고 다시 하기 어렵다.

**근거**
- [판단] 위 오류 종류별 표. 사용자 지적으로 다시 따짐.
- [실측] HTML 표 칸 밀림 385곳(#125) → '잘못 읽힌 글'은 실제로 있는 오류다.
- [원문] CRAG는 자동 판정에 판정 모델 둘을 썼다. 여기서는 확인자가 정답을 '판정'하지 않고 보지 않은 채 '새로 푼다'(판정할 때의 자기 선호 문제를 피함). 같은 모델이라 생기는 '같은 식의 이해'는 표본 30으로 잰다.
- [계산] 표본 30에서 오류 0개면 정답 오류율 95% 상한 약 10%(결정 ⑦과 같음).

**네 관점**
- 서비스: 헛걸음이 적어 사람이 볼 문항이 덜 늘어난다. 표를 잘 읽어 '잘못 읽힌 글'을 더 정확히 잡는다.
- 비즈니스: 새 장비·계정이 필요 없고 학교 문서가 새 외부 서비스로 가지 않는다(초안 단계에서 이미 Claude가 읽음). 학교에는 "같은 회사 모델이 확인했다"는 약점을 표본 30으로 잰 정답 오류율과 함께 밝힌다.
- 유지보수: 코드는 작업 단위 만들기·답 가져오기·비교(PR 1 규칙 기반 채점 그대로)만 하고 모델 호출 코드가 없다. 이중 라벨링에 데스크탑을 켜지 않는다(색인 글 내보내기에는 켠다). 인계 뒤 학기마다 새 문항을 만들 때도 정답 초안과 같은 도구라 따로 배울 것이 없다.
- 확장: 학기마다 새 문항도 같은 방식. M2 학습 몫 리뷰는 원래대로 AWS 오픈 모델(Claude 출력은 학습 몫에 쓰지 않음, 안건 4) — 결정 ⑦ 네 관점의 '같은 장치를 M2에 다시 씀'은 '같은 틀(다른 읽기 + 새로 풀기 + 규칙 비교)을 다시 씀'으로 고친다.

**한계·위험**: Claude가 규정을 잘못 이해한 문항은 정답과 이중 라벨링이 같이 틀려 자동 승인될 수 있다 → 테스트셋 표본 30이 유일한 장치다(0/30이면 약 10% 이하까지만 보장). 다른 세션이 작업 단위 밖의 파일(평가셋 파일)을 읽지 않도록 작업 단위만 따로 두고 지시한다.

**확신도**: 중간~높음(잡는 오류 종류는 분명, 헛걸음 비율은 실측 전). **확인 시점**: 첫 30문항에서 불일치 비율·헛걸음 비율·문항당 시간을 잰다.

### ⑦-2 이중 라벨링에 줄 원본 — 형식마다 원본에 가깝게 ✅ (2026-10-05 사용자 결정)

**결정**: 이중 라벨링 세션에 주는 원본은 서비스의 변환 코드(OpenDataLoader PDF, `ai-server/format_loaders/`)를 거치지 않은 것으로 한다.

| 형식 (평가 문서 수) | 주는 것 | 도구 | `second_annotation.reader` 예 |
|---|---|---|---|
| HTML (202, 표 있는 문서 30) | 수집기가 고른 본문 영역의 **원본 HTML**. 꾸밈(속성·스크립트·스타일)만 지우고 표의 `rowspan`·`colspan`은 남긴다 | BeautifulSoup(수집기에 이미 있음) | `원본 HTML(본문, 꾸밈 제거)` |
| PDF (12) | 해당 **쪽 그림** + 같은 쪽의 PDFium 글자 | pypdfium2(수집기에 이미 있음) + 그림 저장용 Pillow(추가) | `pypdfium2 쪽 그림+글자` |
| HWP (7, 표 있는 문서 5) | 수집기의 **글자 추출**(`tools/corpus/corpus/hwp.py`, 서비스 `hwp5.py`와 다른 코드, 표 줄 맞춤 없음) | olefile(수집기에 이미 있음) | `수집기 HWP 글자` |

**이유**: 서비스 변환에서 생긴 오류(예: #125 전 HTML 표 칸 밀림 385곳)를 잡으려면 확인하는 쪽이 그 변환을 거치지 않아야 한다. 표를 줄 맞춤 그대로 보여 줘야 헛걸음이 적다. HTML은 원본 자체가 글이라 변환 없이 줄 수 있고, PDF는 사람이 보는 쪽 화면이 가장 원본에 가깝다. HWP는 화면으로 바꾸려면 한글 변환 도구가 필요해 글자만 준다(7개뿐).

**버린 대안**
- 모든 형식 글자만(수집기 추출 재사용): 새 도구는 없지만 표의 열 이름과 값의 줄 맞춤이 사라져 표 문항 헛걸음이 많다.
- 모든 형식 그림(HTML은 브라우저 화면, HWP는 PDF로 변환): 헛걸음은 적지만 브라우저·한글 변환 도구를 새로 설치해야 하고, 저장한 HTML은 꾸밈 파일이 없어 화면이 원본과 다를 수 있다.
- 새 추출 프로그램(pdfplumber 등): 라이브러리가 늘고 그 프로그램만의 변환 오류가 새 헛걸음을 만든다. PyMuPDF는 AGPL이라 공개 저장소 코드에 넣지 않는다.

**근거**: [실측] 평가 문서 형식 분포(대장 `split='평가'`·`index_status='색인'`, `[평가질문제외]` 제외 221개: HTML 202·PDF 12·HWP 7). [실측] #125 HTML 칸 밀림 385→0. [판단] 위 비교.

**네 관점**
- 서비스: 표 칸 밀림을 원본으로 잡고, 표를 줄 맞춤 그대로 봐서 헛걸음이 적다.
- 비즈니스: 맥북에서 끝나고 데스크탑을 켜지 않는다.
- 유지보수: 수집기에 이미 있는 도구를 다시 쓰고(새 도구는 Pillow 하나), 문항마다 읽은 방법을 한 줄(`second_annotation.reader`)로 남긴다.
- 확장: HWP 표 문항에서 헛걸음이 많으면 그때 HWP를 그림으로 바꾸는 길을 더한다.

**한계·위험**: HWP 표 문항은 글자만 봐서 헛걸음이 날 수 있다(사람이 보게 될 뿐 숨는 오류는 아님). PDF 쪽 그림은 그림 위주 PDF(대장 `image_heavy`, 평가 PDF 중 1개)도 읽을 수 있어 오히려 낫다.

**확신도**: 높음. **확인 시점**: 첫 30문항에서 형식별 헛걸음 비율.

### ⑦-3 이중 라벨링에 줄 범위 — 문서 전체, 위치는 안 알려 줌 ✅ (2026-10-05 사용자 결정)

**결정**: 이중 라벨링 세션에는 근거 문서의 **전체**를 ⑦-2의 방법으로 읽은 파일로 주고, 정답이 인용한 위치(쪽·문단·인용 글)는 **알려 주지 않는다**. 이중 라벨링 세션이 파일 검색 도구로 스스로 찾아 읽는다. PDF는 모든 쪽의 그림과 글자를 쪽별 파일로 만든다. 답 없는 문항은 부재 확인 기록의 '가까운 문서'를 전체로 준다.

**이유**: 위치를 알려 주면 정답이 엉뚱한 곳을 본 경우(가나대학 예: 표의 "1학기 납부 마감 3월 7일"만 보고 아래 "※ 휴학생은 3월 14일까지"를 놓침) 확인하는 쪽도 같은 곳을 봐 같이 틀리고 자동 승인된다. 스스로 찾게 하면 단서·예외를 놓친 정답까지 잡는다.

**규모**: [실측] 평가 문서 221개 중 219개가 짧다(HTML 평균 640자·최대 12,171자, HWP 최대 10,145자, PDF 10개는 6,000자 이하). 긴 문서는 PDF 2개 — 2027 모집요강 22쪽(32,876자), 실습실 정밀안전진단 결과보고서 369쪽(175,947자).

**버린 대안**
- 인용한 쪽만 준다: 헛걸음은 적지만 엉뚱한 곳을 본 오류가 숨는다.
- 먼저 위치 없이 풀고, 못 찾으면 위치를 알려 줘 다시 푼다: 오류는 잡지만 단계가 둘이 되고 코드가 는다. 긴 문서가 늘면 그때 더한다.

**네 관점**
- 서비스: 단서·예외·다른 문단을 놓친 정답까지 잡는다.
- 비즈니스: 문서 대부분이 짧아 드는 시간·비용이 거의 같다.
- 유지보수: 작업 단위는 원본 파일을 읽은 그대로라 위치 계산 코드가 없다.
- 확장: 긴 문서가 늘어 못 찾는 헛걸음이 많아지면 '못 찾으면 위치 알려 주기'를 더한다.

**한계·위험**: 긴 PDF 2개는 확인하는 쪽이 못 찾아 '없음'으로 답할 수 있다(헛걸음, 사람이 봄). **확인 시점**: 첫 30문항에서 '못 찾음' 비율.

### ⑦-4 확인하는 Claude 띄우기 — 명령 하나로 따로 실행 ✅ (2026-10-05 사용자 결정)

**결정**: 이중 라벨링 명령이 맥북의 Claude Code를 비대화형(`claude -p`)으로 따로 실행한다. 실행 위치는 작업 단위 폴더(평가셋 파일·대장·저장소 밖), 허용 도구는 읽기 도구(Read·Grep·Glob)만, 지시문은 코드에 고정, 답은 표준 출력(JSON)으로 받아 명령이 저장한다. 모델 이름과 Claude Code 판(지금 2.1.205)을 `second_annotation.model`에 적는다. 사용자가 할 일은 없다 → **정정(2026-10-05 실측)**: 맥북의 Claude Code 명령(`~/.local/bin/claude`)이 로그인되어 있지 않아(`Not logged in · Please run /login`) 처음 한 번 사용자가 터미널에서 로그인해야 한다. 그 뒤로는 할 일이 없다. 실행 옵션: `--tools "Read Grep Glob"`(쓸 수 있는 도구 자체를 읽기로 제한), `--strict-mcp-config`(MCP 서버 안 띄움), `--no-session-persistence`, `--output-format json`.

**이유**: 이 대화와 완전히 다른 세션이고, 폴더 밖의 정답을 못 보게 설정으로 막을 수 있으며, 지시문이 고정돼 매번 같다. 인계 뒤에도 담당자가 같은 명령 하나로 돌린다.

**확인할 것 (PR 2)**: 작업 단위 폴더 밖에 둔 가나대학 가짜 정답을 정말 못 읽는지 직접 시험한다. 읽히면 막는 설정을 더한다. 저장소 안에 두면 상위 폴더의 CLAUDE.md가 함께 읽히므로 작업 단위는 저장소 밖 임시 폴더에서 돌리고, 기록용 사본만 `Assets/eval/`에 남긴다.

**버린 대안**
- 제가 이 대화 안에서 하위 에이전트로 띄우기: 정답을 못 보게 하는 것이 지시에만 기대고, 인계 뒤에는 대화 안에서 해야 한다.
- 사용자가 새 세션을 열어 지시문 붙여 넣기: 30문항 묶음마다(약 12번) 사용자 손이 간다.

**네 관점**
- 서비스: 다른 세션·정답 차단으로 이중 라벨링 결과를 믿을 수 있다.
- 비즈니스: 사용자 시간 0. 이 대화와 같은 Claude 계정 사용량을 쓴다.
