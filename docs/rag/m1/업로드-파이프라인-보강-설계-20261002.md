## 3. 결정 1 — 대장 정보를 어디에 두고 어떻게 넘기나 → **A 확정** (2026-10-02 사용자 결정)

| 안 | 내용 | 장점 | 약점 |
|---|---|---|---|
| A (추천) | 백엔드 `documents`에 칸 5개(대장 ID, 원래 주소, 게시일, 학년도, 주제) 추가(Flyway V4). 업로드 API에 선택 입력으로 받아 AI 서버에 넘기고, AI 서버는 같은 값을 청크마다 메타데이터로 넣는다 | 인계 뒤에는 대장 없이 화면으로 올려도 된다(빈칸 허용). 칸이라 형식 검사·정렬·DB-색인 대조(A5)에 바로 쓴다. 청크 메타데이터는 M2 학년도·주제 범위 좁히기에 쓴다 | 마이그레이션 1개, 칸이 늘면 다시 마이그레이션 |
| B | DB에 JSON 칸 하나 + 청크 메타데이터 | 칸을 늘릴 때 마이그레이션이 없다 | 형식 검사·조회가 어렵고 이름이 흩어진다 |
| C | 청크 메타데이터에만 | 백엔드 변경 없음 | 관리 화면·DB 대조에서 못 쓴다. 서비스 DB가 기준이 아니게 된다 |
| D | 서비스가 대장(SQLite)을 직접 읽음 | — | 서비스가 맥북 파일에 기대고, 인계 뒤 화면 업로드엔 대장이 없다 |

결정: A. 백엔드 `documents`에 대장 ID·원래 주소·게시일·학년도·주제 칸을 더하고(Flyway V4, 모두 빈칸 허용), 업로드 API의 선택 입력으로 받아 AI 서버에 넘긴다. AI 서버는 같은 값을 `_build_chunk_metadata`에서 청크 메타데이터로 넣어 source_blocks·retrieval_chunks·table_fact까지 잇는다. 이유: 인계 뒤에는 대장 없이 화면으로 올리므로 서비스 DB가 기준이어야 하고, 칸이면 형식 검사·관리 화면·DB-색인 대조(A5)에 바로 쓰며, 청크 메타데이터는 M2 범위 좁히기에 쓴다.

## 4. 결정 2 — 같은 파일을 무엇으로 판단하나 → **A 확정** (2026-10-02 사용자 결정)

[실측, 대장 `index_status='색인'` 704행, 스크립트 `Assets/corpus/review/prototypes/recheck_20261002/text_dups.py`]
- 파일 바이트(SHA-256)가 같은 행: **0**. 수집기가 같은 해시는 한 번만 색인으로 두고 나머지를 '내용 중복'으로 뺐다.
- 파일은 다르지만 글(한글·영숫자만 남김)이 완전히 같은 행: **8행(4쌍), 모두 PDF 첨부** — 같은 규정을 다시 내보내 두 게시판에 올린 경우.
- 같은 묶음 안에서 한쪽 글의 90% 이상이 다른 쪽에 들어 있는 쌍: **0**(531쌍 비교).

| 안 | 내용 | 장점 | 약점 |
|---|---|---|---|
| A (추천) | 백엔드가 받은 파일의 SHA-256을 계산해 칸에 두고, **살아 있는 문서**에 같은 값이 있으면 409(기존 문서 번호·이름)로 막는다. 글만 같은 4쌍은 #127 서비스 색인 때 대장에서 하나만 색인으로 둔다 | 업로드를 받기 전에 바로 판단, 단순·결정론적. 대량 업로드 스크립트는 409를 "이미 있음"으로 처리 | 다시 내보낸 같은 글은 못 막는다(지금 4쌍) |
| B | AI 서버가 글을 뽑은 뒤 정규화한 글의 해시로 막는다 | 다시 내보낸 같은 글도 막는다 | 해석이 끝나야 알 수 있어 비동기 처리 뒤에 실패로 바뀐다(흐름이 복잡). 짧은 빈 서식처럼 글이 같은 다른 문서를 잘못 막을 수 있다 |
| C | A + 글 해시를 메타데이터로 남기기만(막지 않음) | 나중 정리 도구에 쓸 수 있다 | 지금 쓸 곳이 없다 |

결정: A. 백엔드가 받은 파일의 SHA-256을 `documents` 칸에 두고, 살아 있는 문서에 같은 값이 있으면 409(기존 문서 번호·이름)로 막는다. 지운 문서와는 비교하지 않는다(다시 올릴 수 있음). 글만 같은 PDF 4쌍은 #127 서비스 색인 때 대장에서 하나만 '색인'으로 둔다. 이유: 받기 전에 바로 판단하고 단순하다. 글 기준은 해석 뒤에야 알 수 있어 흐름이 복잡해지고 빈 서식처럼 다른 문서를 잘못 막을 수 있는데, 막을 대상은 지금 4쌍뿐이다. 동시에 같은 파일을 두 번 올리는 경쟁은 관리자 전용·스크립트 순차 업로드라 받아들인다.

## 5. 결정 3 — 대량 업로드 스크립트 모양 → **A 확정** (2026-10-02 사용자 결정)

확인한 사실:
- [원문 설정] 백엔드 문서 처리 실행기는 스레드 1개·대기열 20칸(`DocumentProcessingAsyncConfig`, `document.processing.*` 기본값). 기다리지 않고 연달아 보내면 21번째쯤부터 거절된다 → 한 문서씩 끝날 때까지 기다려야 한다.
- [원문 설정] 접근 토큰 수명 24시간(`jwt.access-token-expiration`). 로그인 응답 본문에 `accessToken`, 갱신 토큰은 HttpOnly 쿠키.
- [실측, 대장] 서비스 색인 대상 704행(파일 704개), 데이터셋(학습 몫, 파일 있음, 글 형식, 개인정보 통과) 3,329행(파일 3,122개 — 같은 파일을 여러 글이 공유).
- 관리자 비밀번호는 사용자가 실행할 때 직접 입력한다(데스크탑은 Tailscale 주소라 Claude가 비밀번호를 넣지 않는다).

| 안 | 내용 | 장점 | 약점 |
|---|---|---|---|
| A (추천) | `tools/corpus`에 `upload` 명령: 대장에서 고르기(`--set service` 색인 704행 / `--set dataset` 학습 몫) → 로그인(비밀번호는 실행 때 입력, 저장 안 함) → 한 문서씩 올리고 진행률로 끝날 때까지 기다린 뒤 다음 → 대장 SQLite 새 표 `uploads`(대상 주소·대장 ID·문서 번호·상태·이유·시각)에 기록, 다시 실행하면 이어 올림 → 409는 "이미 있음"으로 기록 → 연속 5번 실패하면 멈춤 → 파일 이름은 대장 제목(+확장자), 주제는 같은 이름의 카테고리로 | 대장 코드·가상환경을 그대로 쓴다. 서비스·데이터셋 색인(M1 8·9번)이 같은 명령. 처리 대기열을 넘지 않는다 | 순차라 오래 걸린다(시간은 #127 표본에서 잰다) |
| B | 따로 도구(`tools/uploader`) | 수집기와 분리 | 대장 읽기·쓰기를 다시 짠다 |
| C | 백엔드에 묶음 업로드 API(압축 파일·목록) | 인계 뒤에도 화면에서 쓸 수 있다 | 서버 변경이 크고 지금은 필요 없다 |
| D | AI 서버에 직접 올리기 | 빠르다 | "이후 색인은 백엔드 경로로만"(A5) 위반, DB와 색인이 다시 어긋난다 |

결정: A. `tools/corpus`의 `upload` 명령. 실행(비밀번호 입력)은 사용자가 맥북에서 한다.

## 7. 결정 1 보완 — '주제'를 '카테고리'로 합치나 → **합침 확정** (2026-10-02 사용자 결정)

| 안 | 내용 | 서비스 | 비즈니스 | 유지보수 | 확장 |
|---|---|---|---|---|---|
| 합침 (추천) | DB에 '주제' 칸을 따로 두지 않는다. 대장의 주제 5개는 같은 이름의 카테고리로 만들어 넣고(업로드 명령이 없으면 만든다), AI 서버에는 카테고리 번호와 이름을 청크 메타데이터로 넘긴다 | 화면의 카테고리 거르기가 바로 주제 거르기가 된다 | 담당자에게 분류는 '카테고리' 하나 | 같은 뜻의 칸이 하나, 분류 목록은 코드가 아니라 DB(관리자가 늘릴 수 있음) | M2 범위 좁히기는 카테고리 번호로(이름을 바꿔도 안전). 카테고리 이름 바꾸기·삭제(M3)를 만들 때 청크 메타데이터도 함께 고친다 |
| 둘 다 둠 | '주제'(고정 5개)와 '카테고리'를 따로 둔다 | 같음 | 담당자가 둘을 헷갈린다 | 같은 뜻 두 칸 | 같음 |

결정: 합침. `documents`에 주제 칸을 두지 않고 기존 `category_id`를 쓴다. 업로드 명령은 대장 주제와 같은 이름의 카테고리를 찾고 없으면 만든다. AI 서버에는 카테고리 번호·이름을 청크 메타데이터(`category_id`, `category`)로 넘긴다. 결정 1의 DB 칸은 대장 ID·원래 주소·게시일·학년도 4개(+ 결정 2의 파일 지문)가 된다. 카테고리 이름 바꾸기·삭제를 만들 때(M3) 청크 메타데이터도 고치는 일을 함께 한다.
