# 짝 비교 명령과 틀림 종류 집계 (M1 13번 준비, 이슈 #130) — 2026-10-13

> 13번 모델 비교 전에 필요한 채점 도구 두 가지를 더했다: 두 결과를 같은 문항끼리 비교해 '의미 있는 차이'인지 가리는 명령(ADR-0025), '틀림'을 문서 글로 잘못 답한 것과 지어낸 것으로 나눠 세는 집계(`베이스라인-측정-20261012.md` §3에서 하기로 함). 데스크탑·사람 시간 없이 맥북에서 했다.
> 관련: ADR-0025(짝 비교), ADR-0027(모델 선택 순서 — 거르기에 오답률 짝 비교), ADR-0018(테스트셋 봉인), `평가셋-v3-20261013.md`

## 1. 결론

- `evalset compare-runs --a <기준 결과> --b <비교 결과>`: 같은 평가셋 판으로 채점한 두 결과 폴더를 같은 문항끼리 짝 지어, 지표 6개마다 A만 예·B만 예인 문항 수, 정확 이항 검정(매크니마 검정)의 양측 p, 판정(의미 있는 차이 / 같은 수준)을 낸다. 기본은 개발셋만, 13번처럼 테스트셋도 넣을 때는 `--part all`이고 테스트셋은 합계만 나온다. [코드]
- 실행 채점이 '틀림'마다 종류를 붙이고 묶음마다 센다: 엉뚱한근거(질문과 다른 근거를 답으로 붙임) · 다른문서사실(문서를 잘못 읽거나 문서의 다른 사실로 답함) · 지어냄(근거 글에 없는 값). [코드]
- [실측] 베이스라인 v3의 틀림 25건(네 묶음 합계) = 엉뚱한근거 10 · 다른문서사실 15 · **지어냄 0**. 규칙이 바로 틀림으로 정한 답(답없음 문항에 값을 단정)도 값이 모두 근거 글에 있었다. 지금 챗봇의 틀린 답은 없는 사실을 만들어 낸 것이 아니라 근거를 잘못 고르거나 잘못 읽은 것이다 → M2의 후보 고르기·우선 경로 좁히기가 오답률에도 직접 듣는다.

## 2. 짝 비교 명령

**문제**: 한 실행의 지표는 신뢰구간과 함께 나오지만(Wilson), 두 실행이 '다른가'는 답하지 못한다. 13번은 모델 4개를 비교하고 M2는 고치기 전후를 비교하는데, ADR-0025가 정한 짝 비교를 손으로 계산하면 실수하기 쉽고 테스트셋 문항이 드러날 수 있다.

**동작** [코드] (`tools/corpus/corpus/evalset/compare.py`)

| 지표 | 문항 묶음 | 문항별 '예' | 좋은 방향 |
|---|---|---|---|
| 정답률 | 답 있는 문항 | 맞음 | 높을수록 |
| 오답률 | 전체 | 틀림 | 낮을수록 |
| 과잉 거절률 | 답 있는 문항 | 모름 | 낮을수록 |
| 출처 정확도 | 답 있는 문항 | 화면 출처에 허용 근거 문서 | 높을수록 |
| 답없음 거절 | 답 없는 문항 | 맞음 | 높을수록 |
| 안내 충실도 | 안내 사실이 있는 문항 | 충족 | 높을수록 |

- p = 2 × (결과가 갈린 b + c 문항이 반반으로 갈린다고 할 때 지금만큼 치우칠 확률), 1을 넘으면 1. p < 0.05면 의미 있는 차이이고, 요약 줄에 어느 쪽이 나은지(낮을수록 좋은 지표는 방향을 뒤집어) 붙인다.
- 막는 것: 두 결과의 채점 지문이 지금 평가셋 파일과 다르면 거부(다시 채점한 결과는 `scored_with`, 실행 폴더에서 채점한 결과는 실행 기록의 지문으로 확인) · 애매가 남아 있으면 거부 · 한쪽이라도 채점되지 않은 문항(미실행·실패·질문 바뀜)은 짝에서 빼고 수만 센다.
- 테스트셋: 기본(`--part dev`)에서는 읽지 않는다. `--part all`·`test`면 봉인 파일을 읽어 합계에만 넣는다. 결과가 갈린 문항 ID(`--out` JSON)는 개발셋 문항만 담는다 — M2에서 "고쳐서 새로 맞힌 문항 / 망가뜨린 문항"을 찾는 데 쓴다.

**버린 대안**
- 두 결과의 지표 파일만 읽어 비율 차이로 판단: 짝 정보(같은 문항에서 갈렸는지)가 없어 매크니마 검정을 할 수 없다.
- 결과 행을 평가셋에서 다시 채점해 비교: 판정 파일·채점 규칙이 바뀌면 비교 대상이 흔들린다. 이미 채점된 결과 파일을 그대로 짝 짓는다.
- 기본을 개발셋+테스트셋으로: M2에서 고칠 때마다 테스트셋 합계를 보게 된다(ADR-0018은 정해진 때에만).

**실제 결과로 확인** [실측]: 베이스라인 v3 결과끼리 비교하면 모든 지표가 A만 0 · B만 0 · p 1.0 · 같은 수준이고 비율은 `score-run` 지표와 같다(본 개발셋 정답률 43.8%, 53/121). v2로 채점한 실행 폴더와 v3 결과를 비교하면 "이 평가셋 파일로 채점한 결과가 아니다"로 거부한다.

## 3. 틀림 종류 집계

**문제**: 베이스라인 틀림 22건을 손으로 나눴을 때 16건이 문서에 있는 글로 잘못 답한 것이었다(베이스라인 보고서 §3). 오답률 하나로는 '근거를 잘못 고름'과 '지어냄'이 섞여, 13번에서 모델 탓인지 검색 탓인지 가리지 못한다.

**동작** [코드] (`metrics.wrong_kind`)
- 판정 파일에 종류 태그(엉뚱한근거·다른문서사실·지어냄)가 있으면 그것을 쓴다(판정할 때 붙이던 태그를 그대로 읽음).
- 태그가 없으면(규칙이 정한 틀림 — 금지 값, 답없음 문항에 값을 단정 — 또는 태그 없는 판정) 채점이 이미 계산하는 '근거 글에 없는 숫자'가 있으면 지어냄, 없으면 다른문서사실.
- 결과 행에 `wrong_kind`, 지표에 묶음마다 `wrong_kinds`, 요약에 "틀림 종류 엉뚱한근거 n · 다른문서사실 n · 지어냄 n".
- 종류 태그가 없던 틀림 판정 5건에 태그를 더했다(판정·이유는 그대로, `Assets/eval/work/wrong_kind_tags_20261013.py`).

**한계** [판단]: 태그가 없는 틀림은 숫자로만 가린다. 숫자 없이 문서에 없는 말을 지어낸 답은 '다른문서사실'로 세질 수 있다. 그런 답은 규칙이 '틀림'으로 정하지 못해 판정으로 가므로, 판정 때 '지어냄' 태그를 붙이면 된다(13번부터 판정 기록에 종류 태그를 함께 단다).

| 묶음 | 틀림 | 엉뚱한근거 | 다른문서사실 | 지어냄 |
|---|---|---|---|---|
| 본 개발셋 | 12 | 4 | 8 | 0 |
| 본 테스트셋 | 10 | 3 | 7 | 0 |
| 쉬운 개발셋 | 1 | 1 | 0 | 0 |
| 쉬운 테스트셋 | 2 | 2 | 0 | 0 |
