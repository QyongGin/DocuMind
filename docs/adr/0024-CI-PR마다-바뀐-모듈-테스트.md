# ADR-0024: CI — PR마다 바뀐 모듈의 테스트를 GitHub Actions로 돌리고, 통과해야 머지한다

- 상태: 채택
- 날짜: 2026-10-12
- 관련: 이슈 #146, 총괄계획 §3 D4(CI 없음), `docs/rag/m1/CI-도입-20261012.md`

## 맥락

- 저장소에 CI가 없어 테스트는 작성자의 맥북 가상환경에서만 돌았다. 지금까지 PR은 자동 검사 없이 머지됐다.
- 작성자 환경에서는 의존성 목록 누락, 커밋하지 않은 파일에 기대는 코드를 잡지 못한다. 인계 뒤 담당자가 혼자 고칠 때 안전망이 없다.
- M1 11번 채점기부터 코드가 다시 쌓이므로 그 전에 넣기로 했다(2026-10-10 결정).

## 결정

1. GitHub Actions 워크플로 하나(`.github/workflows/ci.yml`)가 develop·main 대상 PR에서 돈다.
2. 바뀐 경로로 모듈을 골라 그 모듈의 검사만 돌린다. 워크플로 파일을 고친 PR과 수동 실행은 모든 모듈을 돌린다.

   | 모듈 | 검사 |
   |---|---|
   | `tools/corpus` | `requirements-dev.txt` 설치 → pytest |
   | `ai-server` | `requirements.txt`·`requirements-dev.txt` 설치 → pytest(Ollama·Chroma 서버 없이, `main` import는 conftest가 임시 폴더로 격리) |
   | `backend` | JDK 21 → `./gradlew test`(H2 메모리 DB) |
   | `frontend` | Node 22 → `npm ci` → `npm run lint` → `npm run build`(테스트 스크립트 없음) |

3. 필수 검사는 결과를 모으는 잡 `ci-ok` 하나다. 바뀌지 않은 모듈의 잡은 건너뛰고(skipped), `ci-ok`는 실패·취소가 하나라도 있으면 실패한다.
4. develop 브랜치 규칙(ruleset)에 'PR 필수'와 '`ci-ok` 통과 필수'를 더한다(지금은 삭제·강제 푸시 금지만).

## 버린 대안

- 모듈마다 워크플로를 나누고 `paths` 필터를 건다: 바뀌지 않은 모듈의 워크플로는 아예 돌지 않아, 필수 검사로 지정하면 결과가 오지 않은 채 '대기'로 남아 머지가 막힌다(GitHub 문서의 알려진 동작). 필수 검사를 모듈마다 넣고 빼는 관리도 생긴다.
- 모든 PR에서 네 모듈을 다 돌린다: 문서만 바뀐 PR에도 AI 서버 의존성 설치(수 분)가 붙는다. 이 저장소는 문서 PR이 많다.
- 바뀐 경로 판단에 외부 액션(`dorny/paths-filter`)을 쓴다: `git diff` 한 줄로 되는 일에 제3자 액션 의존을 늘리지 않는다.

## 근거

- [실측] 2026-10-12 맥북에서 네 모듈 검사가 모두 통과: tools/corpus 140 passed, ai-server 89 passed · 1 skipped(라이브 Chroma 진단 도구), backend `gradlew test` 성공, frontend lint·build 성공.
- [실측] ai-server 의존성에 GPU 패키지(torch 등)가 없어 일반 러너에서 설치된다. 테스트는 Ollama·Chroma 서버를 부르지 않는다(conftest가 `CHROMA_HOST`를 지우고 임시 폴더에서 import).
- [원문] 액션 판: actions/checkout v7, setup-python v7, setup-java v6, setup-node v7(2026-10-12 각 저장소의 최신 릴리스, 실행 환경 node24).
- [판단] 결과를 모으는 잡 하나만 필수로 두면, 모듈이 늘거나 줄어도 브랜치 규칙을 고칠 필요가 없다.

## 결과

- PR 절차(`docs/workflow/PR-작성-및-머지-절차.md`, 루트 `AGENTS.md` §5)에 'CI `ci-ok` 통과 확인'을 더한다.
- 확신도: 높음. 확인: 이 워크플로를 처음 올리는 PR에서 네 모듈 잡이 모두 돌고 `ci-ok`가 통과하는지 본다(워크플로를 고친 PR이라 전부 돈다).
- 한계: 프론트엔드는 테스트가 없어 lint·빌드만 본다. 백엔드 통합 테스트는 실제 MySQL·FastAPI 없이 H2와 목(mock)으로 돈다. 데스크탑 GPU 환경의 동작(색인·생성)은 CI로 확인하지 않는다 — 12번 베이스라인과 데스크탑 종단 확인이 맡는다.
