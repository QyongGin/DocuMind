이슈 #98

OpenDataLoader JSON adapter smoke를 왜 만들었는가

이번 작업은 챗봇 답변을 바로 고친 작업이 아니다. PDF parser가 준 JSON 구조를 DocuMind RAG가 이해하는 표준 contract로 바꿀 수 있는지 확인한 작업이다. 즉, endpoint(엔드포인트)나 ChromaDB를 건드리기 전에 구조 정보가 어디까지 믿을 만한지 먼저 본 것이다.

작업 범위 로컬 Route A, 서비스 없는 정적 검증
핵심 산출물 JSON element -> ParsedBlock / SourceBlock / TableFact 후보
바꾸지 않은 것 upload, ChromaDB, 검색 순위, prompt, source 응답

한눈에 보는 결론

OpenDataLoader JSON은 표와 제목 구조를 보존하는 데 쓸 가치가 있다. 하지만 학과 카드처럼 좌우 병렬 영역이 하나로 합쳐져 나오는 경우도 있으므로, JSON을 켰다고 모든 문제가 자동으로 해결되지는 않는다.

OpenDataLoader JSON parser 원본 구조
ParsedBlock 표준 block 후보
SectionNode 제목 경로
SourceBlock 사용자 출처 원문
TableFact 행 / 열 / 값
Diagnostics confidence / fallback
후속 issue ListFact / CardFact / runtime 연결

예시 1. page 36 전형료 표

page 36은 OpenDataLoader JSON에서 table element 안에 `rows -> cells -> kids -> content` 구조로 값이 들어 있었다. adapter는 이 구조를 재귀적으로 읽어 `TableFact` 후보를 만들 수 있었다.

OpenDataLoader JSON 일부

{
  "type": "table",
  "page number": 36,
  "rows": [
    ["구분", "전형료", "면접고사료", "계"],
    ["비면접학과", "30,000원", "-", "30,000원"],
    ["면접학과", "30,000원", "20,000원", "50,000원"]
  ]
}

위 표시는 실제 JSON을 이해하기 쉽게 줄인 예시다. 실제 JSON은 각 cell 안에 paragraph kid가 들어 있다.

예시 2. page 43 면접 예상 질문

page 43은 `미리 보는 면접 질문` heading 아래에 `항공운항과` heading이 있고, 실제 질문들은 paragraph로 이어졌다. 그래서 `QuestionListBlock` 같은 사례 중심 구조보다, 제목 경로 아래 paragraph/list를 다루는 `ListFact` 후보가 더 자연스럽다.

Heading level 1

미리 보는 면접 질문

큰 섹션 제목이다. `SectionNode.path`의 첫 번째 축이 될 수 있다.

Heading level 2

항공운항과

하위 제목이다. 특정 문자열로 조건문을 만들지 않고 제목 경로로 보존한다.

지원동기를 말해보세요.

실제 질문 문장이다. 후속 `ListFact`가 다룰 수 있는 후보다.

실제 smoke 결과: page 43에서 `ParsedBlock=22`, `SourceBlock=22`, `SectionNode=4`, `TableFact=0`. 표가 아니라 heading 아래 paragraph/list 구조라서 다음 작업은 `ListFact` 설계가 맞다.

예시 3. page 51 학과 카드가 위험한 이유

page 51은 JSON을 켜도 좌우 카드의 제목과 라벨이 합쳐져 나왔다. 그래서 adapter가 무리하게 쪼개지 않고, confidence(신뢰도)를 낮추고 fallback diagnostic을 남기는 쪽이 안전하다.

adapter가 남기는 기록

  • possible_parallel_content_merge: 같은 라벨이나 문구가 병렬 영역에서 합쳐졌을 수 있음

다음 작업을 왜 분리해야 하는가

후속 작업 분리 이유 연결되는 실패 축
TableFact JSON adapter 정교화 현재 smoke는 첫 row를 header로 보는 수준이라 복합 header, merged cell, note/legend 관계가 부족하다. table_relation_loss
ListFact 설계 면접 예상 질문은 특정 문장 모양이 아니라 heading 아래 paragraph/list 구조로 처리해야 한다. retrieval_miss
CardFact / DocumentCard 설계 학과 카드처럼 병렬 layout이 합쳐진 구조는 bbox와 confidence 없이는 안전하게 분리하기 어렵다. source_contamination, scope_loss
runtime feature flag 연결 실제 upload/index/query에 연결하면 검색 순위와 source 응답 회귀 검증이 필요하다. trace_query_drift, index_consistency

초보 개발자용 비유 없는 설명

RAG는 문서를 잘라서 검색하고, 검색된 내용을 근거로 답변한다. 그런데 문서를 단순 text로만 다루면 "이 값이 어느 행의 값인지", "이 문장이 어느 제목 아래인지", "이 출처가 사용자에게 보여줄 원문인지"가 섞이기 쉽다.

이번 adapter는 OpenDataLoader가 준 JSON 구조를 DocuMind 내부 표준 부품으로 바꿔 보는 실험이다. `ParsedBlock`은 parser가 읽은 조각, `SourceBlock`은 사용자에게 보여줄 원문, `TableFact`는 표의 행/열/값, `Diagnostics`는 믿기 어려운 구조에 붙는 경고다.

이 구조가 있어야 나중에 답변이 틀렸을 때 "parser가 잘못 읽었는지", "검색용 text가 부족했는지", "source가 오염됐는지", "LLM이 근거를 무시했는지"를 단계별로 나눠서 볼 수 있다.

면접 한 문장: OpenDataLoader JSON을 바로 runtime에 붙이지 않고, 먼저 heading/table/list/page/bbox를 기존 RAG contract 후보로 변환하는 side-effect free adapter를 만들어 구조 보존 가능성과 실패 fallback을 검증했습니다.
